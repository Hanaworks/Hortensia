# Docker Manager 文档编写方案

日期：2026-10-30。状态：当前编写基线；已获用户同意按本方案逐份推进，产品需求与设计仍分别讨论确认。

本方案规定开发前需要编写的文档、每份文档的单一职责、内容边界、编写顺序和确认方式。按顺序逐份编写，讨论清楚后再推进下一份。

设计覆盖完整目标产品。用户明确：“先把完整的设计方案设计完成，首版是实现的时候选择的范围不是设计的时候的范围。”因此，需求和各设计文档按完整目标范围展开；首版与后续版本的实现取舍只在开发实施计划中安排，不能据此提前裁剪设计。

## 目标与依据

文档需要使后续开发者理解三件事：产品要解决什么问题，功能应该怎样工作，以及实现时应遵守哪些设计与验收约定。文档数量和细节以能够支持实际开发为准。

现有资料作为编写输入：

- [需求背景](requirements.md)：已经明确的产品方向和使用背景。
- [待定问题](open-questions.md)：需要在各份文档中逐步解决的信息缺口。
- [讨论脉络](conversation-notes.md)与原始对话：核对需求来源及纠偏。

已明确的个人自用、混合网络、网页编辑 Compose、Node Cross 和账号登录考虑继续保留。完整产品的功能边界由需求说明确认，技术栈、连接方式及配置存储在相应设计文档中讨论。

## 单一职责原则

每份文档围绕一个主要问题组织，有明确的负责内容和读者用途。同一功能可以出现在多份文档中，但每份只描述自己负责的层面。

采用以下约束：

1. **一个主要职责**：能用一句话说明本篇解决什么问题；章节都应服务于这个问题。
2. **明确包含与排除范围**：写清哪些内容在这里展开，哪些交给其他文档，并指向对应位置。
3. **每项规则有唯一维护位置**：完整定义只维护一处，其他文档引用；必要摘要应标明来源，不能独立修改成另一套规则。
4. **按职责拆分，按需要成文**：职责不同的内容分开组织，但不为每个小主题单独创建文件。后续内容过大时，才按功能或模块拆分子文档。

原方案中的“数据与接口”拆为数据设计和接口设计；“验证与交付”拆为测试与验收、部署与运维。二者分别解决不同问题，后续也会因不同原因变化。

## 文档清单与内容边界

以八份主要文档作为起点，需要独立维护其他职责时可以增补或拆分，并说明边界与依赖。按文档逐项完成，不同时创建整批正文。

| 文档 | 单一职责 | 包含内容 | 不包含的内容及归属 |
| --- | --- | --- | --- |
| 需求说明 `requirements.md` | 定义为什么做、需要什么、完整产品范围到哪里 | 产品目标、使用者与环境、统一术语、完整功能需求、目标范围与可选能力、非功能要求、非目标、业务验收要点 | 操作步骤与边界规则归功能设计；技术方案归架构；测试步骤归测试与验收；版本取舍和任务排期归开发计划 |
| 功能设计 `functional-design.md` | 定义用户操作时产品应如何表现 | 业务对象及关系、信息结构、操作条件与输入输出、正常及异常流程、业务状态和转换、冲突与权限规则、必要交互草图 | 组件或技术选择归架构；数据库结构归数据设计；请求格式与错误码归接口；完整视觉规范可随实现细化 |
| 架构设计 `architecture.md` | 定义系统由什么组成、各部分如何协作 | 系统边界、组件职责与依赖、部署拓扑、通信方向、关键执行链路、技术选型、信任边界、并发及恢复机制、技术取舍 | 不重新定义产品行为；表字段归数据设计；接口报文归接口设计；安装命令与操作手册归部署与运维 |
| 数据设计 `data-design.md` | 定义持久保存哪些信息及如何保持一致 | 持久化实体、关系、标识、字段、约束、索引、数据库事务边界、业务状态的存储表示、数据生命周期、备份清单及版本迁移结构 | 业务状态与转换归功能；执行、调度、故障恢复机制及协议选型归架构；交换契约归接口；备份恢复步骤归运维；验证场景归测试 |
| 接口设计 `api-design.md` | 定义组件之间交换信息的约定 | 接口和消息清单、调用前提、参数、返回值、错误码、事件格式、协议版本、鉴权要求、并发与重复请求的外部约定 | 不决定权限政策和产品行为；不把响应字段当数据库结构；不重复组件划分或内部实现算法 |
| 测试与验收 `test-plan.md` | 定义如何证明实现满足需求和设计 | 完整需求与用例对应、测试环境及数据、正常与失败场景、操作步骤、断言与通过条件、技术验证安排、结果与证据记录方式 | 不在测试中新增或修改产品规则；不决定版本范围；不承担部署使用手册；计划不冒充实测结果 |
| 部署与运维 `operations.md` | 定义软件如何安装、运行和维护 | 已约定的运行前提、部署配置项、初始化、启动停止、更新、备份恢复、排障、卸载和日常维护流程 | 不重新选择架构；不定义账号权限政策或数据模型；不替代验收用例或开发任务安排 |
| 开发实施计划 `development-plan.md` | 定义如何分版本实现完整设计并交付 | 首版与后续版本范围、实现阶段、任务和依赖、每项交付物、引用的设计与测试、任务完成条件、进度和工作量评估 | 不借实现阶段取舍改变完整目标设计；不承载新的产品规则；不重复接口、数据字段和业务规则 |

完整产品范围表由需求说明维护，版本实现范围表由开发实施计划维护；关键交互草图由功能设计维护。数据与接口即使使用相同字段名，也分别说明“如何保存”和“如何交换”，通过映射和引用衔接。

需求中的非功能要求至少检查运行规模、兼容环境、响应与容量、权限与敏感信息、可恢复性等维度；不适用的说明原因，未知数值保留待定。业务术语由需求说明统一，功能设计展开对象关系，各技术文档仅补充本篇专用术语，避免 Node、Stack、配置与运行数据在不同篇中含义漂移。

两份辅助记录随编写维护：

- `open-questions.md` 只负责未决问题、影响和解决时点；已解决的正式规则移入负责该规则的文档。
- `decisions.md` 只负责关键决策的背景、候选、理由、日期与状态；当前有效规则由对应主文档维护，决策记录链接到它。

README 负责导航与项目状态，HANDOFF 负责当前工作交接，原始对话负责保留来源；这三类材料不作为另一套产品规格。

## 容易重叠的内容如何归属

| 内容 | 完整定义的位置 | 其他文档如何使用 |
| --- | --- | --- |
| 某项能力是否属于目标产品、为什么需要 | 需求说明 | 各设计文档完整展开，开发计划分版本实现，不自行删减目标能力 |
| 某项能力在哪个版本实现 | 开发实施计划 | 引用已完成的需求和设计安排依赖，未在首版实现的能力继续保留完整设计 |
| 某项操作允许谁执行、失败后用户看到什么 | 功能设计 | 架构说明如何实现；接口引用权限和行为，定义返回方式；测试检查结果 |
| 业务对象有哪些状态、哪些转换允许发生 | 功能设计 | 数据设计定义如何持久化；接口定义传输表示。组件内部协作机制由架构维护，接口只定义相关阶段的交换表示，不另造一套业务状态 |
| 部署连接、组件故障如何处理 | 架构设计 | 功能设计保留用户可见的结果规则；接口细化交互约定；运维给出排查和恢复操作 |
| 数据保存、约束和迁移结构 | 数据设计 | 架构给技术背景，接口定义必要映射，运维引用版本与迁移前提编写步骤 |
| 执行事件、去重、并发和恢复 | 架构设计维护机制，功能设计维护用户可见规则 | 数据设计只定义所需记录、唯一键、原子更新范围及保留条件；接口定义交换约定，不由数据设计补定机制 |
| 通信协议选择与消息契约 | 架构设计维护协议选择，接口设计维护交换契约 | 数据设计只引用必要的持久语义；上游未定时保留条件模型，不承担协议定稿 |
| 性能或可恢复性目标 | 需求说明 | 架构解释实现方式，测试引用目标验证，运维说明操作前提；不在各处另设指标 |
| 一项需求满足时的业务成功标准 | 需求说明 | 功能设计将其展开为操作规则；测试引用该标准验证需求是否满足，不重新定义标准 |
| 一次具体操作的结果和异常行为 | 功能设计 | 接口约定如何表达该结果，测试引用操作规则补充数据、步骤和断言，不改写规则 |
| 安装、升级或恢复的实际操作步骤 | 部署与运维 | 测试引用并验证该流程，避免另写一套相互不同的操作步骤 |

以 Node Cross 为例：需求说明回答需要解决什么跨节点使用问题；功能设计定义用户怎样操作及操作结果；架构说明由哪些组件协作；数据设计定义需要保存的关系和记录；接口设计规定交互格式；测试验证这些约定；运维说明相关运行前提；开发计划安排实现次序。这个例子仅说明文档归属，不预设具体复制、存储或连接方案。

## 每份文档的输入与交付标准

| 文档 | 主要输入 | 本轮应交付到的程度 |
| --- | --- | --- |
| 需求说明 | 用户讨论、已知背景、实际使用场景 | 功能需求与范围可辨认，成功条件可理解，未知约束单独列出 |
| 功能设计 | 已确认的完整需求与范围 | 目标范围内各项功能的正常、失败与边界行为明确，可据此设计实现与验收场景 |
| 架构设计 | 需求约束、功能行为、实际环境 | 组件职责和协作可解释，关键选型有理由，技术疑问有验证安排 |
| 数据设计 | 功能中的业务对象与规则、架构的持久化安排 | 完整目标功能涉及的数据关系、约束、生命周期与一致性要求完整 |
| 接口设计 | 功能规则、组件边界、相关数据含义 | 完整目标功能所需的接口和协议可供对接，输入、结果、错误与事件无关键缺项 |
| 测试与验收 | 需求、功能及技术设计 | 完整目标需求及重要规则可追溯到用例，步骤和通过条件可执行 |
| 部署与运维 | 部署架构、运行约束、配置和数据要求 | 运行前提与操作流程明确，尚依赖实现验证的命令或参数清楚标注 |
| 开发实施计划 | 完整的当前有效设计与验收约定 | 版本范围和实现任务有清晰依据、依赖与完成条件，不用设计缺失来决定版本取舍 |

## 编写顺序与依赖

主线为：**需求说明 → 功能设计 → 架构设计 → 数据设计与接口设计 → 开发实施计划**。测试与验收从需求阶段开始积累；部署与运维在部署架构明确后编写，两者都在形成实施计划时提供交付依据。

这个顺序用于逐步收敛问题，不要求机械地完成上一份所有细节才能思考下一份：

- 需求阶段写业务验收要点，功能阶段明确正常与失败行为；测试文档引用它们，逐步补成可执行用例。
- 功能设计发现需求缺口，先回到需求说明补充；架构发现某项行为不可行或代价明显变化，应反馈给功能和范围设计。
- 会改变架构选择的技术疑问，可以单独安排验证；实验、环境准备和真实节点操作另行明确范围。
- 数据设计与接口设计相互核对含义和映射，逐项覆盖完整目标功能。接口对外字段可以不同于存储字段，不能互相代替。
- 部署与运维可以先明确前提与流程；需要真实安装和恢复演练才能确认的内容保留验证状态。
- UI 的信息结构和关键操作可以提前讨论；完整视觉、布局和控件细节随功能实现迭代。

## 每轮范围与待定问题

每轮开始说明正在编写哪份文档、哪些章节。可以按模块逐次讨论，但整份文档的完成标准是覆盖完整目标范围。尚未写到的模块属于本篇待完成工作，不能因为可能不在首版实现而留作未设计的占位项。

“完整”指已经明确属于目标产品的能力均得到相应设计，不等于全量复刻参照产品，也不等于纳入所有能想到的功能。候选能力是否属于目标范围需要在需求说明中明确；确认纳入后，其设计不受实现排期影响。

待定问题分为两类，并在 `open-questions.md` 中标注：

- **影响本轮结论的问题**：答案会改变当前范围、行为或关键设计。相关章节保持待定，依赖它的下游内容只能标为条件草案；不据此宣布该部分已确认或可开始实现。
- **可后续决定的问题**：不影响本轮交付，可以继续。记录影响内容与最晚决定阶段，避免一直保留为无期限的“以后再说”。

确认可以按章节进行，完整文档仍须完成全范围核对。产品设计完成后再进入实现范围与版本规划；可执行任务必须已有确认的行为与关键设计、可用验收条件，且没有阻塞它的未决问题。实际验证结果与设计是否成文分别记录。

## 每份文档的编写步骤

1. **整理输入**：读取现有资料和已确认的上游文档，列清已知事实、用户决定和未决问题。
2. **确定职责与提纲**：先写出本篇的一句话职责、包含与排除范围、上游输入、负责维护的规则及下游使用者，再安排章节。
3. **讨论关键问题**：只询问会明显改变本篇结论的信息；已有资料能回答的直接整理，不重复询问。存在取舍时说明选项、理由与影响。
4. **编写初稿**：把讨论结果写成连贯文档。未定内容保留为问题或标明建议，不暗中补成已确认结论。
5. **核对与修订**：检查是否覆盖职责、是否越界或重复定义、是否与引用文档一致、是否遗漏关键失败场景，并按用户反馈修改。
6. **确认当前结论**：记录确认日期、文档修订标识或具体章节、用户明确认可的结论与保留问题，再推进受影响的下游文档。确认可按章节进行；未回复、仅查看文档或同意开展编写，都不表示认可其中的具体方案。

助手负责整理资料、提出方案、成文和一致性检查；用户决定产品目标、实际使用边界和重要取舍。用户要求直接起草时，可以先写带明确待定项的草案。

## 文档格式与状态

每份主文档开头固定说明：

- 标题、更新日期和状态。
- 一句话职责与预期读者用途。
- 包含范围和明确排除的内容。
- 上游输入与引用文档。
- 本篇负责完整维护的规则或结构，以及依赖它的下游文档。

正文使用描述内容的章节名，表格用于范围和规则对照，流程与关系复杂时补简洁图示。引用应指向具体章节或稳定编号，避免只写“参见某文档”而无法找到规则。

状态统一为：

| 状态 | 含义 |
| --- | --- |
| 草案 | 正在整理或讨论，内容尚可调整 |
| 待确认 | 本轮内容完整，关键选择和剩余问题已列清 |
| 当前基线 | 相关结论已确认，后续设计和实现以此为依据；仍允许通过修订更新 |
| 已归档 | 已被替代或暂不采用，不作为当前设计依据 |

未决问题至少记录问题本身、影响哪份文档及章节、现有选项、是否阻塞本轮和应在哪一步决定。决策记录至少包含日期、问题、结论、理由和影响范围。

已确认规则发生实质变化时，先在负责该规则的文档中标明变更提议与原确认内容的区别，再列出受影响的下游章节、用例和任务。确认后更新当前规则和对应引用；尚未同步的下游内容标为“需复核”，不能继续按旧结论实施。文档整体状态与受影响章节分别说明，避免局部变化使所有内容都失去可用性。

只有改变目标、范围、行为或关键设计的修订需要重新确认相关结论；错字、排版和链接修复可以直接处理。下游发现上游规则缺失或不可行时，提出变更或记录待定问题，不在下游自行形成另一套规则；历史对话保留原貌。
