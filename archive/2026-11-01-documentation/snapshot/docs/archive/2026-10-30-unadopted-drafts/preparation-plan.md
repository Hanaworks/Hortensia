# Docker Manager 开发前准备计划

日期：2026-10-30。状态：准备计划已展开为需求与设计初稿，阶段结论尚未全部确认。

用户已明确现在开始编写文档和设计。本计划作为内容检查清单；各阶段可以先形成相互衔接的初稿，再根据实际环境与用户反馈修订。下面未勾选项表示相应结论尚未确认或验证，不表示没有编写相关文档。

本计划把项目从现有需求讨论推进到可以开始实现首个完整流程的状态。先明确要解决的问题和功能行为，再确定支撑这些行为的架构、数据与接口，最后形成可执行的开发任务和验收标准。

完整首版的范围需要明确；设计深度优先覆盖首个开发流程。后续功能可以先定义边界，相关细节在实现前补齐。UI 只提前验证影响操作和数据关系的部分，视觉、布局和控件细节随开发迭代。

## 当前基础

- 自托管，第一阶段主要供自己使用，兼顾以后分享给别人。
- 管理多个独立 Docker 节点，由用户指定部署位置，以 Node → Stack（Compose）组织管理；Docker 资源属于节点，不额外引入独立的 Service 管理层。
- 节点处于混合网络环境，可能包含局域网、云服务器和不同地点。
- 主体参考 Portainer，改善节点操作体验；在 Web UI 内完成 Compose 创建、编辑和部署。
- 遵循原生 Compose 行为；Node Cross 支持将配置用于其他节点部署，数据迁移可选。
- 账号方案需要评估简单内置账号与 SSO（OIDC）：可以内置账号加 OIDC，也可以直接使用 OIDC，尚未选定。
- 技术栈、是否使用 Agent、配置存储和完整首版范围均未定。项目目前只有准备文档。

需求以 [需求基线](requirements.md) 为准，未决问题集中维护在 [待定事项](open-questions.md)。本计划中的任务、产出和顺序是工作安排，不表示相应产品方案已经确定。

## 阶段安排

| 阶段 | 需要回答的问题 | 主要产出 | 完成标准 |
| --- | --- | --- | --- |
| 1 需求与范围 | 谁使用、在哪使用、首版做什么 | 需求基线、功能范围表、首个流程的验收场景 | 首版必需、后续候选和暂不支持的内容可明确区分 |
| 2 功能与流程 | 用户如何操作，系统如何回应 | 功能设计、核心流程及异常处理规则 | 关键操作的输入、结果、影响范围和失败反馈明确 |
| 3 架构与选型 | 各部分如何协作，选什么技术 | 架构设计、部署示意和关键决策记录 | 方案能覆盖首个流程及混合网络约束，重要取舍有依据 |
| 4 数据与接口 | 保存什么，各部分交换什么 | 数据模型、接口约定和操作状态设计 | 首个流程从界面到节点执行的链路可逐步对照 |
| 5 验证与交付 | 如何证明符合要求，如何安装和维护 | 验收计划、兼容范围、安装更新与恢复设计 | 关键行为有可观察的通过标准，交付方式可执行 |
| 6 开发拆分 | 按什么顺序实现，何时算完成 | 分阶段开发计划和开工检查 | 首个开发任务不依赖尚未决定的核心行为或架构 |

总体顺序为 1 → 2 → 3 → 4 → 5 → 6。验收场景从阶段 1 开始积累；架构遇到可行性疑问时安排针对性验证，再反馈修改功能设计，不把全部问题推迟到阶段 5。

## 阶段 1 需求与首版范围

### 准备任务

- [ ] 补齐运行背景：初期节点和 Stack 的大致数量、节点系统与处理器架构、Docker 与 Compose 使用情况、Manager 预计部署位置。
- [ ] 描述典型网络关系：Manager 能否连接节点，节点能否主动连接 Manager，是否需要经过代理或 VPN。
- [ ] 整理日常实际使用的 Portainer 功能，逐项标记沿用、调整、新增、暂缓，并区分首版必需与后续候选。
- [ ] 明确容器、镜像、网络、卷、日志、终端、Stack 和节点管理各自需要支持的操作；这些是评估范围，不默认全部进入首版。
- [ ] 明确已有容器和 Compose 项目是否只展示、允许操作，或支持接管，以及“接管”后由谁维护配置。
- [ ] 列出需要管理的配置材料：Compose 文件、环境变量、环境文件、挂载配置、构建上下文、私有镜像凭据等；分别决定首版支持与否。
- [ ] 定义 Node Cross 首版边界：复制配置、复制后部署、移动是否包含在内；运行数据和外部依赖分别如何处理。
- [ ] 明确账号需求：内置账号是否必需、OIDC 是否为可选接入、是否需要多个账号和不同操作权限。
- [ ] 确定首个完整开发流程，并用实际使用场景写出完成标准。

建议作为讨论起点的流程是：登录 → 接入节点 → 创建并编辑 Stack → 部署 → 查看结果；再接入第二个节点验证配置跨节点部署。具体切分和顺序在本阶段确定。

### 产出与完成标准

更新 `requirements.md`，形成 `feature-scope.md`。范围表至少记录功能、用户场景、处理方向、首版优先级和验收要点。首版必需项都有明确用途；尚未决定的事项注明影响范围和最晚决定阶段。

## 阶段 2 功能设计与操作流程

### 准备任务

- [ ] 设计节点接入、状态展示、切换和移除流程，明确移除管理关系是否影响节点上的实际资源。
- [ ] 设计 Stack 创建、编辑、校验、部署、更新、停止和删除中已纳入首版的操作，区分保存配置与执行部署。
- [ ] 设计 Node Cross：选择来源与目标、展示复制内容、处理目标差异、发起部署和查看结果；明确来源是否保留、两端是否独立及同名冲突规则。
- [ ] 规定目标端口、路径、外部网络与卷、环境变量、凭据和构建材料缺失时的提示与处理边界。
- [ ] 设计登录与账号设置流程，比较“内置账号加可选 OIDC”和“仅使用 OIDC”。确定首次管理员建立、允许哪些身份进入、账号关联、退出、禁用与恢复访问的规则。
- [ ] 为部署失败、节点离线、连接中断、重复点击和同时编辑写出用户可见结果；明确失败后已保存配置和运行资源分别处于什么状态，以及残留资源和重试的处理规则。
- [ ] 明确各操作是否允许取消、取消的生效时点和影响；不支持中止已开始的执行时，界面应说明关闭页面后的执行行为。
- [ ] 定义最低限度的信息结构，使用户在查看和执行操作时都能识别目标节点。仅对容易误操作或影响行为的流程补草图。

### 产出与完成标准

形成 `functional-design.md`。每个核心操作写清前置条件、输入、正常步骤、结果、失败分支和影响对象。功能范围中的首版必需项均能找到对应流程；没有依靠未说明的自动复制、覆盖、删除或重试行为才能成立的场景。

## 阶段 3 架构设计与技术选型

### 准备任务

- [ ] 根据网络关系比较节点接入方案，包括是否需要 Agent、连接由哪一侧发起、节点如何注册和重新连接；记录安装与维护成本。
- [ ] 划分 Web UI、管理端、节点执行部分的职责，明确 Docker 操作和 Compose 执行的位置、工作目录、依赖与权限。
- [ ] 决定配置由谁维护、保存在哪、哪一份具有权威性，如何处理磁盘外部修改，以及编辑内容与最近成功部署内容的关系。
- [ ] 设计部署任务的执行与状态反馈：同步或后台执行、进度日志、重复提交、并发操作，以及管理端重启或断线后的状态核对。
- [ ] 分别设计人的登录认证与节点身份认证。账号方案覆盖会话、凭据保存和 OIDC 配置；节点方案覆盖接入、凭据撤销和连接保护。
- [ ] 比较候选技术栈，依据开发维护难度、部署体积、现有经验、编辑器与终端需求、跨平台要求等选择，不把旧建议直接当作结论。
- [ ] 识别会改变架构的技术疑问，安排最小验证及通过标准，例如代表性网络下的接入和重连、附属配置的执行路径、OIDC 接入流程。

### 产出与完成标准

形成 `architecture.md`，包含组件职责、部署与连接关系、配置与任务的流向、失败恢复边界。关键决定写入 `decisions.md`，记录候选方案、选择理由和影响。首个流程涉及的技术栈与连接方式已确定，重要可行性问题已有验证结论，或明确改为暂不支持。

## 阶段 4 数据模型与接口约定

### 准备任务

- [ ] 根据已确定的功能定义节点、Stack、配置材料、部署任务、账号和外部登录身份的关系；设计所需的历史记录，避免默认引入完整版本管理系统。
- [ ] 规定唯一标识、同名范围、配置版本或并发修改检查、敏感信息的保存与读取方式，以及删除管理记录和删除实际资源的区别。
- [ ] 为首个流程定义界面到管理端、管理端到节点执行部分的请求、响应、错误、权限要求和状态反馈方式。
- [ ] 明确任务从提交、执行到结束的状态和转换条件，包括结果暂时未知的情况；定义重新连接后如何查询实际状态。
- [ ] 明确日志或终端等已纳入范围的实时通道如何建立、关闭和恢复，以及敏感内容的展示边界。

### 产出与完成标准

形成 `data-and-api.md`。用一次正常部署、一次失败部署和一次跨节点部署逐步核对数据与接口：输入从哪里来、记录如何变化、节点执行什么、界面显示什么均有对应约定。详细字段优先覆盖首个流程，后续功能保留明确边界。

## 阶段 5 验收验证与交付准备

### 准备任务

- [ ] 建立需求到验收场景的对应关系，写清准备条件、操作步骤、预期结果与失败判断。
- [ ] 准备代表性 Compose 样例，验证原生语义，以及首版支持的环境文件、路径、外部资源和附属文件行为。
- [ ] 覆盖配置编辑与部署、跨节点内容边界、目标冲突、重复提交、断线和重启后的任务核对；对不支持的输入定义明确反馈。
- [ ] 根据选定账号方案覆盖首次登录、未授权访问、登录失效、账号关联和恢复访问；OIDC 被纳入时增加身份服务不可用等场景。
- [ ] 定义首批支持的系统、架构和 Docker／Compose 版本范围，明确测试节点、示例数据与实际运行环境的隔离方式。
- [ ] 设计安装、初始化、更新、备份和恢复流程，区分管理器配置备份与应用运行数据迁移；记录更新失败时的处理边界。
- [ ] 将架构验证中仍未解决的问题落实为验证任务，不以“开发时再看”替代决定。

### 产出与完成标准

形成 `validation-and-delivery.md`。首版必需功能有可观察的验收标准，已纳入首个流程的技术疑问得到解决。测试计划写完与测试实际通过分别记录；本阶段无需提前实现产品验收测试，但必要的架构验证应有实际结果。

## 阶段 6 开发任务拆分与开工检查

### 准备任务

- [ ] 将实现划分为可以完整演示和验收的功能增量，写清依赖关系、实现范围、检查方法和完成标准。
- [ ] 优先详细拆分首个流程，后续阶段按功能里程碑描述；涉及 Node Cross 的配置边界在早期设计中考虑。
- [ ] 确定代码目录、开发启动方式、配置管理、测试与代码检查约定，以及后续 Git 和交付流程。
- [ ] 检查需求、功能、架构、数据与接口是否相互一致，集中解决会使首个流程返工的问题。
- [ ] 根据确认的范围和验证结果安排实现顺序，再评估工作量，不沿用旧讨论中的固定比例或未经验证的工期。

### 产出与完成标准

形成 `development-plan.md`。每个首批任务能指出依据的需求或设计、输入依赖、交付内容和验收方式。确认首个流程的设计与开发计划后，再开始应用脚手架、依赖安装和正式实现。

## 当前推进顺序

1. 已明确：个人自用优先、兼顾分享；混合网络；账号设计评估内置账号与 OIDC。
2. 已编写：功能范围、功能设计、架构、数据接口、验证交付、设计决策与开发安排初稿。
3. 下一步：结合现有初稿校正日常必需功能、账号模式、Stack 配置边界，并补齐实际运行环境，收敛关键方案后安排技术验证。
4. 可以延后：正式名称、完整视觉主题、后续功能的详细接口，以及未纳入首版的数据迁移实现方案。
