# 需求基线 v0.3

日期：2026-10-30。本文记录当前工作方向，不是完整规格，也不是已冻结的第一版功能清单。

## 产品目标

面向管理多台独立 Docker 主机的个人使用者，提供统一的网页操作入口，完成节点查看、Compose 配置维护、部署和跨节点配置复用。用户明确指定运行节点，管理器保留原生 Compose 行为，并让配置内容、执行结果和运行状态可以区分和追踪。

使用环境已明确包含局域网、云服务器或不同地点；具体规模、系统、处理器架构和网络可达关系尚待补充。产品可以在以后分享给别人使用，首版不因此自动扩展为多租户平台。

实际功能取舍见 [首版功能范围](feature-scope.md)，操作行为见 [功能设计](functional-design.md)。这些初稿中的新增规则属于推荐设计；本文件继续作为已确认需求的入口。

## 已明确的方向

| 编号 | 需求 | 后续验收方向 |
| --- | --- | --- |
| R01 | 自托管，统一管理多个独立 Docker 节点 | 可管理多台独立节点，节点间不依赖集群调度 |
| R02 | 以 Node → Docker 资源 / Stack（Compose）组织管理 | 操作时能够清晰识别资源所属节点 |
| R03 | 主体参考 Portainer | 以实际需要的功能为基线，不默认全量复刻 |
| R04 | Web UI 是 Compose 配置的日常操作入口 | 在 UI 中完成创建、查看、编辑配置和部署，无需先 SSH 创建文件 |
| R05 | 保持原生 Compose 语义 | 管理器不擅自改写配置或注入额外网络、卷等资源 |
| R06 | Node Cross | 能从已有 Stack 发起配置跨节点复制或重新部署，减少手工搬运 |
| R07 | 跨节点配置操作不以数据迁移为必备前提 | 可以独立完成配置复制；数据处理范围需明确告知 |
| R08 | UI/UX 随开发迭代 | 准备阶段不要求全部页面、布局和视觉定稿 |
| R09 | 第一阶段主要自己使用，兼顾以后分享给别人 | 首版范围与安装维护方式以个人自托管使用为出发点 |
| R10 | 节点处于局域网、云服务器或不同地点的混合网络环境 | 节点接入设计覆盖约定的网络关系和重连场景 |

R05 中的“额外资源”指管理器自行附加的行为。Compose 按自身规则创建的默认网络或声明的卷，应遵循原生行为。

R02 中的部署位置由用户指定；不额外引入独立的 Service 管理层。

## 账号与登录的设计方向

2026-10-30，用户提出可以考虑内置简单账号系统并支持 SSO（OIDC）接入，或者直接使用 OIDC。准备阶段需要比较这两种方案，具体选择尚未确定。

需要进一步明确本地账号是否必需、首次管理员如何建立、哪些外部身份允许登录、账号如何关联、登录服务不可用时如何恢复访问，以及是否需要多个账号和不同操作权限。个人自用优先不等于已经决定省略登录或只支持一个账号。

## 跨节点操作：先明确行为

需要支持的基本使用场景：打开节点 A 的一个 Stack，从界面选择节点 B，将所需配置用于 B 的部署。

建议进一步讨论的行为：部署前调整配置；复制后两端独立；保留来源 Stack。这些先作为候选规则，不当作已经确定的全部实现要求。

需要明确配置边界：Compose 主文件、环境变量、附属配置文件、构建上下文与运行数据如何区分。目标节点上的路径、端口或外部资源是否满足要求，也需要在后续流程中考虑。

## 文档约束

- 不以未经核实的 Dockhand、Dockge 等竞品能力描述作为项目事实。
- 配置落盘、数据库存储或集中保管，属于架构选择；落盘本身不妨碍 UI 编辑或跨节点操作。
- “后端简单”“UI 占 70%”等旧讨论不作为工作量估算依据。
- 本阶段不承诺数据迁移、跨节点自动调度、GitOps 或完整多租户能力。
