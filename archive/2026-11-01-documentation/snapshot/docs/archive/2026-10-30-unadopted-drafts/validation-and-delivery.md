日期：2026-10-30。状态：实质设计初稿，供讨论和后续实施使用。
本文依据 [需求基线](requirements.md)、[准备计划](preparation-plan.md)，配合 [功能设计](functional-design.md)、[架构设计](architecture.md) 和 [数据与接口](data-and-api.md) 阅读。

**当前证据状态：本文所有测试、技术验证、安装、升级与恢复演练均未执行；没有通过结果。** 本次只编写文档，未创建应用代码，未访问实际节点，未安装依赖或部署服务。
已确认的是个人自用兼顾分享、多独立节点、混合网络、UI 编辑原生 Compose 和 Node Cross 方向。下述首版范围、Agent、账号模式、兼容平台及交付方式均为建议，尚待用户确认。

## 1. 验收对象与记录规则

建议首个完整流程为：初始化并登录 Manager → 注册两个 Agent → 在节点 A 创建 Stack 并保存 → 部署并查看反馈 → 将指定 revision 复制到节点 B 的独立草稿 → 调整配置并显式部署。
Manager 为配置权威来源；部署使用不可变 revision，Agent 在每个 Stack 的固定目录执行。节点主动建立受 TLS 保护的反向连接。本文验收以该建议架构为前提，方案变化时同步调整。
建议首版只接受 Compose 主文件、环境配置和文本附件；具体文件角色、敏感标记及路径限制以功能和接口文档为准。

每个用例执行时记录：产品构建标识、Manager/Agent/Engine/Compose 版本、系统与架构、网络关系、样例 revision、操作时间、任务 ID、观察证据和结论。
用例状态使用“未执行 / 通过 / 失败 / 阻塞”；没有环境或产品实现时记录“未执行”，不得记为通过。
保留脱敏的界面截图、任务记录、执行输出及必要的资源清单；不得将真实密码、完整环境值或节点凭据放入验收材料。
命令成功和容器健康分别判断；Compose 命令退出成功不代表应用已健康，也不代表外部服务可访问。

## 2. 需求验收矩阵

以下所有行的执行状态均为“未执行”。需在实现后按步骤运行，并填入实际证据。

| 编号 / 映射 | 场景与准备 | 操作步骤 | 可观察的通过条件 |
| --- | --- | --- | --- |
| V01 / R01、R09 | 全新自托管实例与两个独立节点 | 按安装说明启动 Manager，完成初始化，分别接入 A、B | UI 可分别列出两个节点；不要求节点组成集群；安装材料包含必要配置与持久化位置 |
| V02 / R02 | 两节点均有同名 Stack | 切换 A、B，分别打开详情和执行确认界面 | 标题、资源列表和操作反馈均指明节点；在 A 的操作不作用到 B |
| V03 / R03 | 已确认的首版资源操作清单 | 逐项查看容器、镜像、网络、卷和日志，执行范围内基础操作 | 每项有明确结果和错误反馈；外部 Compose 项目的配置管理保持只读，其容器仅允许已纳入范围的显式启停等操作；接管及终端等后续功能不表现为可用 |
| V04 / R04 | 在线节点，无预建 Stack 文件 | UI 创建、编辑主文件、环境配置与文本附件，保存后部署 | 无需先 SSH 创建文件；保存形成草稿，部署关联固定 revision，后续编辑不改变已发出的任务输入 |
| V05 / R05 | 同一受支持样例与相同 Compose 环境 | 比较管理器部署与原生 Compose 配置解析及生成资源 | 服务、端口、声明卷和网络语义一致；无管理器自行注入资源；原生默认网络允许出现 |
| V06 / R05 | 含 build、include 或未支持输入的配置 | 保存并请求校验或部署 | 清楚指出不支持字段及影响；不静默移除、重写或假装部署成功；草稿可供修正 |
| V07 / R06、R07 | A 有指定 revision，B 无同名 Stack | 发起 Node Cross，核对复制清单并创建 B 草稿 | B 生成独立草稿并记录来源；A 保留；B 不自动部署；编辑 B 不改动 A |
| V08 / R06、R07 | B 存在同名 Stack | 向 B 复制同名配置 | 拒绝覆盖并提示改名；现有 B 配置与资源不变，不隐式合并 |
| V09 / R07 | 来源使用运行卷、bind 路径及私有镜像 | 查看复制预览，创建目标草稿后做部署检查 | 不复制运行数据或 Manager 凭据；目标依赖和凭据缺失明确列出；目标部署必须另行触发 |
| V10 / R08 | 首个流程已有可操作 UI | 从登录完成至跨节点草稿，在每次执行前核对目标和影响 | 不依赖未呈现的隐藏步骤；关键错误能在当前流程理解；不以视觉主题定稿作为验收条件 |
| V11 / R10 | 节点只能主动连接 Manager | 接入节点，断网，再恢复网络 | 节点可按约定连接并恢复状态；UI 标明离线；重连不创建重复节点或重复执行历史部署 |
| V12 / R04、R10 | Agent 离线 | 编辑并保存草稿，再尝试部署或其他节点执行操作 | 草稿保存成功；执行明确被拒绝，不能伪装成功或暗中等待节点回来执行 |
| V13 / AUTH | 选定账号模式，实例未初始化 | 执行首次管理员引导，再尝试重复引导 | 仅一个有效初始化结果；引导关闭后无法公开注册或抢占管理员身份 |
| V14 / AUTH | 已允许与未允许的身份 | 分别登录、退出、禁用账号，再用旧会话访问 | 只有显式允许身份能登录；统一 admin 权限边界明确；退出或禁用后会话按约定失效 |
| V15 / AUTH | 同邮箱、不同 issuer/sub 的 OIDC 身份 | 使用两个身份登录，尝试账号关联 | 不因同邮箱自动合并；以 issuer+sub 识别外部身份；关联需已认证账号显式发起并核验双方身份 |
| V16 / AUTH | OIDC 服务不可用或配置错误 | 尝试 OIDC 登录并按选定模式恢复访问 | 无认证绕过；local+optional OIDC 可用已配置本地账号；OIDC-only 走受控修复路径并记录结果 |

## 3. 故障、边界与敏感材料用例

这些用例与正常流程同等重要，均未执行。使用隔离测试节点与虚构敏感值，不以生产资源做故障注入。

| 编号 | 故障与步骤 | 可观察的通过条件 |
| --- | --- | --- |
| F01 | 重复点击部署；对同一请求重发 | 同一请求关联同一任务，Agent 不重复执行；不同的新请求仍受同 Stack 并发限制 |
| F02 | Agent 已接收任务但回执丢失，重启 Manager | 结果转为 unknown 或保持可核对状态；不自动创建新执行；重连后按任务 ID 查询原执行结果 |
| F03 | 执行中重启 Agent，保留其任务记录，再恢复连接 | 不能仅因进程消失就报告 succeeded；可确认的最终结果被回传，证据不足继续 unknown，并展示人工核对入口 |
| F04 | Compose 已产生部分资源后返回失败 | 任务为 failed，保留输出及对应 revision；展示可能的残留资源，不把失败解释为资源已恢复原状 |
| F05 | 提交后取消 queued，再对 running 请求取消 | 仅尚未执行且可确认撤销的任务为 canceled；running 不强制中止；关闭页面不取消节点执行 |
| F06 | 通过附件管理接口保存相对路径文本附件；改写附件路径为越界路径或符号链接逃逸 | 合法附件保持在配置包边界内；附件接口不能越界读写相邻 Stack 或宿主文件。这不禁止管理员在 Compose 中显式声明目标宿主绝对 bind 路径，其可用性另行检查 |
| F07 | Node Cross 来源含标记敏感的 env 与文本附件 | 预览覆盖每一份材料及敏感标记；按确认的复制规则逐项确认或排除；排除后目标明确缺失，不能悄悄补回 |
| F08 | Node Cross 来源 revision 选择后又被编辑 | 复制内容仍来自选定 revision；预览与生成草稿一致；不混入后来保存的环境配置或附件 |
| F09 | B 缺少 bind 路径、外部卷/网络，端口冲突或镜像凭据 | 展示能够预检的具体问题；最终 Engine/Compose 错误仍完整关联任务；不自动创建外部资源或复制来源数据 |
| F10 | 两个会话编辑同一草稿，先后提交 | 后提交者收到冲突及重新读取提示，不无声覆盖先提交者内容 |
| F11 | 已关联 OIDC 身份再次绑定其他账号，或禁用后重新登录 | 关联唯一性生效；不能借重绑定绕过禁用；错误不泄露其他账号的敏感详情 |
| F12 | 撤销 Agent 身份，旧连接重连并提交历史结果 | 旧身份不能重新授权执行；节点状态与历史任务保留可核对信息，重新接入须走受控注册 |
| F13 | 对 unknown 任务尝试只填说明解除，再验证旧执行停止并持久禁止重放 | 仅填说明被拒；无节点证据时继续阻止运行变更；满足证据条件才解除门禁，历史仍为 unknown，不伪造终态 |
| F14 | 编辑 Compose 顶层 name 或插值后，与固定 project_name 不一致 | 展示原生 `-p` 的固定执行值并阻止静默切换；不能产生另一套项目资源；跨节点目标名经用户明确确认 |

任务状态采用 queued、running、succeeded、failed、unknown、canceled；unknown 表示结果证据不足，不等同 failed，不自动重做。
用例还应分别观察“任务结果”“当前容器状态”“应用健康”三个维度，避免用其中一个覆盖另两个。

## 4. 技术验证任务与决策出口

下表是后续验证任务，不是已完成实验，也不要求本次安装依赖或访问外网。实现前确认运行环境，再决定最小验证程序与样例。

| 验证项 | 最小实验 | 通过标准 / 不通过时处理 |
| --- | --- | --- |
| P01 反向连接 | 在代表性局域网、云和异地网络中连接、断线、重连，检查 TLS 身份及撤销 | 约定网络可连通；重连身份稳定且撤销生效；不通过则明确代理/VPN前提或调整连接方案 |
| P02 Compose 目录语义 | 用主文件、env_file、文本 bind 附件及外部资源样例，在固定目录解析和执行 | 相对路径与项目身份可预测，无 revision 切换导致路径失效；不通过则修订目录模型后再实施 |
| P03 任务持久化 | 在接收、启动、执行完成与回传各边界断开并重启组件 | 原任务可核对；未确认结果保持 unknown；不能依赖自动重发命令恢复 |
| P04 OIDC | 对选定身份服务验证发现、回调、会话和身份关联，模拟服务不可用 | issuer/sub 稳定且校验完整，未允许身份被拒绝；恢复流程不绕过身份验证 |
| P05 配置与附件 | 校验文件角色、敏感标记、越界路径和跨节点预览 | 支持输入与拒绝输入均有确定结果，敏感材料不会漏出预览或未经确认进入目标 |
| P06 备份恢复 | 暂停写入，制作备份，在隔离实例恢复并重新核对节点 | 草稿、revision、账号和任务记录一致；旧会话失效；恢复不会重放任务或误部署 |

验证结论必须记录实际环境、证据和限制；失败应回写 [待定事项](open-questions.md) 与 [关键决策](decisions.md)，不能只写“以后处理”。

## 5. 兼容范围建议

建议首批面向 Linux Docker Engine，覆盖 amd64 与 arm64；这是建议待确认，不代表已支持或已验证。Manager 与 Agent 的交付架构也须逐项验证。
具体 Linux 发行版、Engine/Compose 版本区间、节点数量、Stack 数量与配置体量待确认；不编造性能、延迟或容量承诺。
每个拟支持组合至少执行正常部署、相对路径、Node Cross、断线重连和任务重启核对；未测组合标注“未验证”。
Docker Desktop、Windows 容器、远程 build 与高级 Compose 输入不默认列入首批兼容承诺，是否加入另行确定。

## 6. 安装与初始化交付设计

建议交付 Manager 与 Agent 的独立安装材料，说明镜像或程序来源、配置项、持久化目录、所需权限、连接方向和卸载影响；最终包装方式待选型确认。
Manager 安装步骤：设置访问地址和 TLS → 配置数据库及加密密钥持久化 → 选择账号模式 → 完成首次管理员引导 → 检查初始化入口已关闭。
local+optional OIDC 模式建议在受控初始化阶段建立本地管理员，再显式配置 OIDC 允许身份；不开放注册，新增身份须管理员允许。
OIDC-only 模式建议通过部署侧配置指定 issuer 与首个允许的 subject，引导成功后关闭初始化；无法预知 subject 时的安全核对机制须在实现前明确，不能用“首位登录者自动成为管理员”替代。
OIDC-only 恢复通过持有部署控制权的人修复配置及允许身份，停止服务后按恢复手册操作；不提供公开的认证绕过入口。
Agent 安装步骤：核对 Docker 与 Compose → 设置节点持久化目录和 Manager 地址 → 使用受限的一次注册材料接入 → 检查节点身份及连通性 → 注册材料失效。
首次接入展示节点名称、标识与能力，要求操作者核对；不要把安装完成直接等同节点已具备所有 Stack 的路径、外部资源和镜像凭据。
移除管理关系、卸载组件与删除应用运行资源分别说明；默认卸载流程不承担运行数据清理或迁移。

## 7. 备份、恢复与更新

Manager 的逻辑备份集合包含数据库、管理配置、配置附件及 revision、解密所需密钥和兼容版本元数据；密钥以单独受保护的材料保管，不与公开配置导出混放。若附件存于数据库外，也必须纳入同一一致性备份。
备份不包含容器运行数据、卷内容或宿主 bind 数据；Node Cross 同样不能替代应用数据备份。
建议备份窗口暂停配置写入、任务派发及任务结果落库，待在途写入结束再采集一致快照；Agent 可继续运行任务，恢复写入后补回结果。具体暂停机制需实现并验证。
备份文件含敏感配置及密钥，应限制读取并妥善保存；恢复前先验证版本兼容、材料完整和密钥可用。
恢复顺序：隔离旧实例写入 → 恢复数据库/附件/密钥 → 检查兼容元数据 → 使旧会话失效并登录核对 → 恢复节点连接 → 按任务 ID 核对未终结记录 → 允许新写入与执行。
恢复后核对节点身份和 Stack 工作目录映射；备份时点之后发生的实际部署需与 Agent 及 Engine 对账，不用旧数据库覆盖节点事实，不重放未知任务。
升级前保存可恢复备份，记录 Manager/Agent/数据格式兼容关系，暂停新执行并妥善处理运行中任务，再升级和核对首个流程。
升级失败只有在旧程序兼容当前数据格式时可直接回退；发生不可逆迁移时，须恢复升级前一致备份，并核对期间节点变化，不能仅替换旧镜像。
产品回退不等于应用部署回滚；恢复旧 Manager 或旧配置不会自动撤销节点上已发生的资源变化。

## 8. 交付完成门槛

设计初稿交付只说明验收和运维规则已写出，不表示产品已实现、方案已确认或测试已通过。
进入实现前应确认首版范围、账号模式、网络前提和首批兼容范围，解决会改变首个流程的技术验证项，或明确调整范围。
实际发布前应交付可复现安装说明、示例配置、兼容矩阵、备份恢复说明、升级回退限制和带证据的验收记录；所有失败与未验证项必须保留。
当前结论：文档设计已形成初稿，全部测试与演练仍未执行，尚不能据此宣称可安装、可部署或可恢复。
