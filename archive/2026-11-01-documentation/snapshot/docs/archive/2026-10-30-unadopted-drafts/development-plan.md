# Docker Manager 开发阶段安排

日期：2026-10-30。状态：基于设计初稿的开发安排，尚未进入实现。

本安排依据 [功能范围](feature-scope.md)、[功能设计](functional-design.md)、[架构设计](architecture.md) 和 [数据与接口](data-and-api.md)，以可完整演示的流程组织实现。当前先形成任务边界与验收依据；技术方案确认后再补具体代码路径、接口细节和执行命令，不把未知技术栈写成可直接执行的编码计划。

## 实现前需要解决的事项

- 校正首版范围，尤其是终端、外部 Stack 接管和高级 Compose 输入是否为必需。
- 确认登录模式、节点连接方案、配置来源与执行目录规则；确认首批平台和实际网络可达条件。
- 选定技术栈，完成 [验证与交付](validation-and-delivery.md) 中会改变架构的最小验证。
- 核对首批数据模型、执行状态和接口，确保未知执行结果不会导致第二次任务或破坏性操作。

这些事项已形成具体提议，见 [决策记录](decisions.md)。后续 UI 视觉、非首版能力和全部接口的穷尽设计无需在开始首个流程前完成。

## 实现顺序建议

| 阶段 | 可交付结果 | 主要工作 | 完成证据 |
| --- | --- | --- | --- |
| M0 技术验证 | 核心架构能够执行代表性场景 | 网络接入与重连、固定工作目录下 Compose 执行、任务记录恢复、选定身份方案、配置备份一致性 | 留存验证环境、步骤、结果和设计修订；未验证项不标记通过 |
| M1 登录与节点接入 | 可以登录并看到一台真实测试节点 | 项目基础结构、配置和数据库初始化、首次管理员、首个登录模式、节点注册与身份、状态与撤销 | 未登录不能管理，错误节点凭据被拒，断线状态正确；有完整启动说明 |
| M2 编辑到部署 | 在网页创建 Stack 并部署到测试节点 | 配置文件与变量编辑、保存版本、支持范围校验、固定目录、任务执行、进度与日志、失败反馈 | 原生行为对照通过；保存不触发部署；失败结果可查，配置版本可定位 |
| M3 跨节点配置复用 | 同一配置可调整后用于第二节点 | 来源版本选择、复制清单、敏感项选择、目标草稿、同名冲突与依赖检查、单独发起部署 | 目标可独立修改，来源不变，不自动带走运行数据或管理器凭据 |
| M4 日常资源操作 | 完成首版的常用管理 | 容器与镜像基础操作、网络卷查看、外部资源归属、Compose 停止与卸载 | 操作目标明确、归属边界有效、普通卸载不删除卷或 bind 数据 |
| M5 登录补齐与交付 | 可以独立安装、恢复和更新首版 | 另一登录模式（若纳入）、账号准入、配置导出、备份恢复、镜像构建、平台适配与使用说明 | 首版矩阵通过；干净环境安装成功；能从备份恢复并核对节点状态 |

M1—M3 是优先演示的核心。若选定 OIDC-only，M1 就必须包含 OIDC 登录，不能依赖未开放的本地账号绕过；若同时支持两种模式，M5 完成另一种模式及切换、恢复的验证。

## 首批任务划分

### T01 形成可重复的技术验证

输入：选定的网络与执行方案、代表性 Compose、测试节点。

交付：可重复步骤、实际输出和结论，证明连接断开后任务可以核对、相对路径保持稳定、登录或恢复路径可用。验证代码如需编写，应隔离标记为实验，是否转为正式实现另行评估。

验收：每项结论对应真实测试记录；不把本次文档检查当作节点或产品验证。

### T02 建立登录和节点管理的最小闭环

输入：账号模式、首次管理员规则、节点注册协议。

交付：应用启动和数据初始化、登录与退出、受保护的管理接口、单节点接入与在线状态。代码组织和必要检查随该闭环建立，避免先堆砌与流程无关的脚手架。

验收：有效用户能管理自己的节点，未知身份或节点被拒；节点移除管理关系不会删除其 Docker 资源。

### T03 实现配置保存与校验

输入：配置包边界、数据模型、版本冲突规则。

交付：Stack 草稿和文件编辑、显式敏感标记、不可变版本、校验结果、节点离线时的保存行为；配置材料与运行数据分开存放和展示。

验收：刷新后内容一致；两个编辑者不会静默覆盖；不支持的配置说明原因；保存不启动容器。

### T04 实现固定版本的部署任务

输入：T02、T03，任务接口及节点执行约定。

交付：目标校验、提交与幂等检查、执行目录、任务日志与持久记录、成功失败未知状态、重连核对和操作互斥。

验收：重复请求不会导致额外执行；管理端断线或重启后能定位原任务；部署失败不抹去旧成功版本，节点状态与任务结果分别展示。

### T05 实现 Node Cross

输入：T03、T04，复制内容与凭据规则。

交付：选择来源版本、目标节点与项目名、复制清单与目标调整、独立草稿、单独部署及结果关联。

验收：来源保持不变；目标同名不会覆盖；明确排除运行数据；敏感项选择与缺失提示有效；相同复制请求重复提交不生成多个目标 Stack。

其余首版功能按 M4、M5 的验收边界继续拆分，避免在核心方案尚未校正时编写大量具体代码任务。

## 交付与变更规则

每个任务同时带上相关验证和简短说明。实现中发现需求或架构变化，先修订对应设计与验收，不只修改代码；本地实际结果优先于此前未验证的假设。

当前不提供固定工期。用户使用规模、输入复杂度、技术验证和最终范围明确后，再估算各阶段工作量。完整首版完成以验收与交付结果为准，不以写完全部文档或实现全部旧建议为准。
