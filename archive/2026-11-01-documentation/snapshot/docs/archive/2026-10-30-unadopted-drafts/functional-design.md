# 功能设计初稿

日期：2026-10-30。以下为推荐设计，尚未用户确认。
已明确的需求以 [需求基线](requirements.md) 为准；本文将其展开为可评审的具体行为，不代表范围已经冻结。
范围取舍见 [功能范围](feature-scope.md)，连接与执行机制见 [架构设计](architecture.md)，实体与接口约定见 [数据与接口设计](data-and-api.md)。

## 1. 使用目标与设计选择

面向个人自托管使用，同时使其他人能独立安装使用。管理多个独立 Docker 节点，覆盖局域网、云服务器和不同地点的混合网络。
核心闭环是：接入节点 → 在 UI 创建 Stack → 保存 Compose 配置 → 明确部署到一个节点 → 查看执行与运行结果 → 复制配置到另一节点。
保持原生 Compose 语义；管理器不擅自注入网络、卷或调度规则。Compose 自身创建默认网络、声明卷的行为正常保留。
部署位置由用户选择；一个 Stack 绑定一个节点，不引入独立 Service 管理层，不做跨节点自动调度。

| 问题 | 可选方式与取舍 | 本文采用的推荐方式 |
| --- | --- | --- |
| 登录 | 仅 OIDC 简化口令管理，但依赖外部身份服务；内置账号便于首次使用和恢复 | 内置管理员 + 可选 OIDC，可配置为 OIDC-only |
| 配置维护 | 直接维护节点文件接近手工习惯，但跨节点复用与历史追溯更复杂 | Manager 保管草稿与版本，部署时向目标节点提供固定版本 |
| 跨节点使用 | 直接移动需同时处理源清理与数据；复制能独立交付配置能力 | 从明确版本复制为目标独立草稿，分别部署和维护 |

这些方案用于形成一套可讨论的完整设计；账号模式和首版范围仍需用户选择。

## 2. 信息结构与共同展示规则

全局入口包括节点列表、最近任务和账号设置；节点详情包含概览、Stack、容器、镜像、网络与卷。
Node → Stack 是配置管理主线；容器、镜像、网络、卷是节点上的实际资源，既可能属于受管 Stack，也可能来自外部。
任何资源详情、编辑页和操作确认都显示节点名称与 Stack/project_name，避免切换节点后误操作。

| 对象 | 用户看到的核心信息 | 主要入口 |
| --- | --- | --- |
| Node | 名称、连接状态、最近联系时间、Docker/Compose 能力与错误 | 接入、重连、查看资源、注销 |
| Stack | 名称、节点、project_name、草稿版本、最近部署版本、运行摘要 | 编辑、保存、部署、执行记录、Node Cross、删除 |
| Revision | 创建时间、创建者、配置摘要与来源 | 从任务查看执行依据、作为复制来源 |
| Task | 操作、目标、提交时间、状态、步骤、结果与可用日志 | 查看进度、排查、核对结果 |
| 实际资源 | 节点、名称、状态、归属、最近观测时间 | 查看与允许的日常操作 |

执行状态与运行健康分开：部署任务成功只说明本次执行完成；容器随后退出或健康检查失败仍会展示异常。
断线时展示最近观测值及时间，并标明当前状态未确认，不把缓存状态当作实时状态。
页面和编辑器布局可以随开发调整；上述对象归属、操作结果和错误信息必须保持可见。

## 3. 登录与账号

启用本地账号时，首次启动通过受部署侧一次性材料保护的初始化流程创建管理员；初始化完成后关闭该入口，不提供公开注册。OIDC-only 可直接通过部署配置指定允许的 issuer 与 subject 引导首个管理员，无需先创建本地账号；不能将首位任意登录者自动设为管理员。
获准登录的账号在首版均具备管理员权限；节点隔离、只读角色与细分 RBAC 放到后续。
OIDC 接入需要管理员配置身份提供方及明确的准入规则；身份提供方认证通过不等于自动获准进入管理器。
外部身份使用 issuer + subject 识别，不仅凭同名或相同邮箱自动合并本地账号。
已有本地账号的实例切换到 OIDC-only 前，必须验证指定外部身份可登录。OIDC-only 的恢复由有部署控制权的人修复身份配置；若提供临时恢复本地账号的机制，须由服务器侧显式操作并留痕，不能在身份服务故障时自动开启。
退出登录或会话失效会阻止新的写操作；已接受的后台任务继续执行。未保存草稿保留在页面并提示重新登录后再保存。
登录失败给出可操作的提示，账号设置和任务日志不显示口令、会话令牌、OIDC 密钥或节点接入凭据。

## 4. 节点接入与状态

新增节点时填写名称并完成节点身份配对；网络连接方向与部署方式由架构文档定义，UI 不假设所有节点可被公网直连。
配对成功后检查 Docker 可用性、Compose 能力和节点执行条件，分别显示连接成功与是否具备部署能力。
连接状态至少区分未连接、在线、离线和需要处理的认证错误；部署能力不足应给出具体缺项。
节点离线时仍可查看已保存配置、编辑草稿和发起配置复制；不能新执行部署、容器操作和资源删除。
重连后刷新实际资源，并优先核对未结束任务；不能因重新连接而自动重做状态未确认的操作。
同一节点身份重复接入应提示现有节点，避免将同一执行端误当作两个独立节点。
注销节点前要求先处理关联 Stack 和未结束任务；注销不清理 Docker 资源，也不等于卸载节点侧程序。

## 5. Stack 创建与编辑

创建 Stack 时选择节点、显示名称和 Compose project_name；项目名默认从原生配置输入解析，再由用户明确确认，执行时作为可见的 `-p` 参数记录。同一节点的 project_name 必须唯一，并检查可观测的外部 Compose 项目冲突。
显示名称可修改；project_name 和绑定节点在创建后固定，改变部署位置使用 Node Cross，避免重命名意外产生另一套资源。
编辑页支持 Compose 主文件、环境变量和文本附件；保存后即使未部署也能再次打开继续修改。
环境变量按用途提示敏感值，默认遮罩；授权用户可以显式查看和编辑，日志与比较界面默认脱敏。
文本附件按相对路径组织，保持在 Stack 的稳定工作目录内；禁止通过绝对附件路径或 `..` 写出该目录。
Compose 中的绝对 bind 路径是目标节点依赖，管理器既不复制该路径数据，也不自动创建或改写业务目录。
相对文件和 bind 路径依据稳定工作目录解析；发布新 revision 时切换文件内容，不能因 revision 目录变化悄悄改变相对 bind 的位置。
首版限制为 Compose + 环境变量 + 文本附件；build 上下文、多文件 include 等高级输入暂缓，遇到时明确阻止部署并说明原因。
不能静默删除未知字段、移除不支持的引用，或将原生 Compose 改写成管理器专用格式。
保存执行格式和附件路径检查；部署前执行目标 Compose 校验。无法确认的外部依赖列为提示，不能承诺检查通过就必然部署成功。
保存与部署是两个动作。保存更新草稿版本号，不触发节点执行；退出有未保存变更的页面时提示处理。
多人或多页编辑使用版本校验；提交时草稿已变化则返回冲突，保留当前输入供比较，不默默覆盖较新的保存。

## 6. 部署与历史

点击部署后展示目标节点、project_name、与最近部署版本的差异，以及端口、路径和外部网络/卷等依赖提示。
用户确认时锁定所选草稿版本，生成不可变 revision 和任务；若草稿已更新，则要求重新查看差异后提交。
每次任务记录所执行的 revision、发起者和目标。后续编辑只改变草稿，不能改变已提交任务的内容。
节点离线、能力不足、同 Stack 存在未结束的变更任务，或发现外部同名项目时，提交被拒绝并说明原因。
执行遵循该 revision 的原生 Compose 配置；涉及删除不再声明的容器等额外选项须显式说明，不隐含加入破坏性参数。
执行页展示任务阶段、可用日志和错误；部署失败后保留 revision、草稿和现场，不假定资源已经自动回滚。
成功后更新最近成功部署版本并刷新资源；新 revision 部署失败时，另行显示最近尝试版本及结果。
首版可从执行记录查看对应 revision，并将其用于 Node Cross；部署前的差异确认只比较本次输入与最近成功部署依据。完整历史浏览、任意版本比较和恢复为草稿的界面按功能范围后置；将来重新部署旧配置也不代表还原镜像内容、卷或数据库数据。

```mermaid
flowchart LR
  A[编辑草稿] --> B[保存并检查]
  B --> C[预览差异与依赖]
  C --> D[固定 revision 并提交任务]
  D --> E[执行 Compose]
  E --> F[记录执行结果]
  F --> G[独立刷新运行健康]
```

## 7. Node Cross

入口位于来源 Stack；先选明确的已保存草稿版本或历史 revision，再选目标节点、目标名称和 project_name。
复制对象为 Compose、变量和文本附件的快照，记录来源 Stack/revision；复制完成即成为目标的独立草稿，来源后续编辑不自动同步。
默认保留来源 Stack、容器和运行状态；复制不自动部署，也不提供隐含的“移动并清理源节点”行为。
管理器会话、节点凭据和 OIDC 配置不进入复制包；Compose 内含的业务敏感变量逐项提示，默认不复制敏感值，目标部署前补齐。
复制不包含镜像二进制、卷内容、bind 数据或其他运行数据；界面在确认前和完成后都明确展示这个边界。
目标节点可离线接收草稿；在线部署前重新检查目标能力。来源节点离线时，可使用 Manager 已保存的版本。
目标同名 project_name 不允许覆盖；用户改名或取消，不把已有目标 Stack 当作隐含更新对象。
复制后允许修改附件、变量、端口、路径及外部资源绑定；来源节点名称和路径不能被当作目标可用性的证明。
确认页列出绝对 bind 路径、相对路径用途、发布端口、external 网络/卷和镜像访问依赖，要求用户核对目标环境。
复制成功后进入目标草稿页，通过普通部署流程执行；目标失败不改变来源，用户可调整后再次部署。
数据迁移是独立可选能力，本阶段不创建迁移任务，也不对复制出的应用承诺业务数据完整可用。

## 8. 资源与外部项目

容器列表支持查看状态、详情和日志，以及启动、停止、重启已有容器；操作明确指出所属节点与受管 Stack。
对受管 Stack 容器直接操作后，实际状态可能偏离配置期望；后续 Compose 部署会按配置重新处理，界面给出提示。
镜像支持列表、详情、拉取，以及删除未被容器引用的镜像；首版不默认提供强制删除或批量清理全部资源。
网络与卷首版支持查看详情、关联容器和使用情况；终端、手动创建/修改网络卷等能力后置。
日志注明节点和容器、采集时间及连接状态；掉线后提示中断，重新连接不伪造连续日志。
通过 Docker/Compose 标记发现的外部项目可展示名称、资源和状态，但标明“外部项目，配置未受管”。
外部项目的接管、配置编辑和 Compose 部署暂缓；不凭容器信息推导出一份可安全回写的 Compose。
外部容器允许上述日常操作；不能因为不属于受管 Stack 就自动删除或纳入其他 Stack。

## 9. 任务、重复提交与并发

| 状态 | 含义 | 后续行为 |
| --- | --- | --- |
| queued | 已接受、尚未开始执行 | 可取消；取消与开始执行竞争时，以实际接受结果为准 |
| running | 节点已开始执行 | 持续查看进度；首版不支持强制取消 |
| succeeded | 已确认本次执行成功 | 刷新资源，独立判断运行健康 |
| failed | 已确认执行失败或未开始前已终止 | 展示原因和已有副作用，人工决定是否重试 |
| unknown | 无法确认执行是否完成或结果丢失 | 核对原任务，禁止自动重试或破坏操作 |
| canceled | 已确认取消且没有开始执行 | 可在重新检查后提交新任务 |

同一提交标识的重复请求返回原任务；重新点击不能创建第二个相同操作，改配置后明确重试才是新任务。
同一 Stack 的部署、down 与关联容器状态变更串行执行；其他 Stack 可以独立处理，但节点级冲突仍需执行前检查。
排队期间节点离线时不继续启动执行；返回明确未执行结果。已下发而无法确认是否开始的任务进入 unknown。
断线、Manager 重启或节点执行端重启后，依据原任务标识查回执行记录；只有明确终态证据才将 unknown 收敛为成功或失败。
无法恢复结果时保留 unknown，展示人工核对入口和已有资源；不能凭“容器看起来在运行”判定该部署任务成功。
unknown 未核对前禁止对关联 Stack 做部署、down、删除等变更，允许查看和保存草稿。无法取得最终结果时，只有确认旧执行不再产生副作用并由 Agent 持久禁止再次执行该任务，才可人工解除门禁；原任务保留 unknown 和核对证据，不改写成成功。
关闭页面、退出登录或日志连接中断不取消后台任务；重新打开可按任务记录继续查看。
执行超时不等于执行失败；能够确认未开始或已停止的才记 failed，否则记 unknown。

## 10. 删除与清理

删除入口先区分“注销管理”和“停止并移除 Compose 资源”，不能用一个含糊按钮同时承担两种行为。
注销管理移除管理关联并按保留策略处理配置历史，已有 Docker 资源继续存在，后续以外部项目展示。
Compose down 使用明确的已部署配置版本；提交前列出目标节点、项目和预期影响，成功后 Stack 配置仍可编辑和再次部署。
默认不删除卷、不删除 bind 数据、不移除镜像；首版不提供顺带清理这些数据的选项。
存在 queued/running/unknown 关联任务时禁止注销和 down；必须先取消可取消任务、等待结束或完成结果核对。
down 部分失败时保留记录并展示尚存资源，不显示“已清理干净”；后续处理仍需重新核对。

## 11. 关键验收示例

| 场景 | 可验证结果 |
| --- | --- |
| 节点在线，在 UI 输入 Compose 并保存 | 重新打开内容一致；节点尚无部署变化 |
| 提交 revision A 后立刻编辑并保存 B | 任务只执行 A；草稿显示 B，并提示尚未部署 |
| 目标节点离线 | 保存和复制可完成；新部署被拒绝，不能留下等待上线后自动执行的隐含任务 |
| 同一部署请求因网络重发两次 | 返回同一任务，节点只执行一次 |
| 部署中断线，随后重新连接 | 任务先显示 unknown，再按原执行记录核对；不自动重跑 |
| 容器部署成功后健康检查失败 | 任务成功与运行异常同时可见 |
| A 复制到 B，且 B 缺少外部卷或 bind 数据 | 来源无变化；目标明确提示依赖，不能宣称数据已迁移 |
| 两个页面同时保存同一草稿 | 较旧版本提交收到冲突，输入仍可保留比较 |
| 输入不支持的 build/include | 明确解释部署限制，保存内容不被静默删改 |
| 对 Stack 执行 down | 配置仍存在，卷和 bind 数据未被主动删除 |
| OIDC 认证通过但身份不在准入范围 | 登录被拒绝，不自动创建可管理节点的账号 |

## 12. 本轮需确认的选择

- 账号采用内置管理员 + 可选 OIDC，还是仅 OIDC；是否接受首版所有获准账号具备相同管理权限。
- 是否接受首版配置边界，以及外部项目接管、终端、网络卷手动修改的后置安排。
- Node Cross 的敏感变量是否采用默认不复制值，以及同名目标不覆盖、来源默认保留的规则。
- 哪些实际节点和示例 Stack 作为首批验收环境；复杂构建、平台架构和存储依赖是否影响首版边界。
