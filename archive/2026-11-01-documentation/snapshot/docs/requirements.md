## 产品目标

提供自托管的多节点 Docker 管理程序，以 Portainer 的主体能力和操作形式为参照，改善节点之间的管理体验。用户既能直接管理独立容器，也能在 Web UI 中维护 Compose 和部署 Stack，并方便地将已有配置用于其他节点。

节点保持独立，运行位置由用户指定。用户能够清楚辨认正在管理的节点、应用配置和运行资源，减少登录服务器维护配置及手工搬运配置的工作。

产品设计先覆盖完整目标需求，再在实现阶段分版本交付。“完整”指目标产品已纳入的能力得到完整设计，不自动等同于复刻 Portainer 的全部平台和功能。

## 统一术语

| 术语 | 本项目中的含义 |
| --- | --- |
| Node / 节点 | 被统一管理的一个独立 Docker 运行环境，通常对应一台服务器；具体接入方式由架构设计决定 |
| Docker 资源 | 容器、镜像、网络、卷等实际运行或存储对象，操作时需要明确所属节点 |
| 独立容器 | 可以直接创建和管理、不要求由某个受管理 Stack 创建的容器 |
| Stack | 以 Compose 配置组织的一组应用资源；这里是产品管理概念，不预设其存储结构或集群实现 |
| Compose 配置 | 用于描述应用部署的配置及相关输入；需要管理哪些文件、变量和构建材料，在需求范围中确认 |
| Node Cross | 将已有应用配置用于另一节点部署的能力；复制、重新部署、移动等具体操作范围尚需明确 |
| 配置材料 | 部署所需的声明、环境配置和相关文件；与运行过程中产生的数据区分，具体边界待确认 |
| 运行数据 | 应用使用或产生的业务数据，例如卷或宿主挂载目录中的数据；是否迁移是独立选择 |
| Service | Compose 文件中的服务定义可以存在；产品不额外引入独立的 Service 管理层 |

| R12 | 支持容器启动、停止和删除 | 用户可以管理容器的运行与移除，操作范围和结果清楚 |

R08 是设计过程约束，不是待实现的独立产品功能。R01—R10 沿用原编号；R11—R16 来自本次用户明确答复。上述条目确认了列明的能力，未自动确认其下所有配置细节和操作规则。

## 账号与登录的设计方向

2026-10-30，用户提出可以考虑内置简单账号系统并支持 SSO（OIDC）接入，或者直接使用 OIDC。准备阶段需要比较这两种方案，具体选择尚未确定。

需要进一步明确本地账号是否必需、首次管理员如何建立、哪些外部身份允许登录、账号如何关联、登录服务不可用时如何恢复访问，以及是否需要多个账号和不同操作权限。个人自用优先不等于已经决定省略登录或只支持一个账号。

## 跨节点操作：先明确行为

需要支持的基本使用场景：打开节点 A 的一个 Stack，从界面选择节点 B，将所需配置用于 B 的部署。

需要进一步确认的需求包括：只需要配置复制还是也需要移动；是否需要部署前调整；两端以后是否有关联；来源是否需要保留或清理。具体默认行为、冲突处理和操作流程在功能设计中展开，不在本篇预设答案。

需要明确配置边界：Compose 主文件、环境变量、附属配置文件、构建上下文与运行数据如何区分。目标节点上的路径、端口或外部资源是否满足要求，也需要在后续流程中考虑。

## 产品边界

- 当前目标是多个独立 Docker 节点，运行位置由用户指定，不引入独立 Service 管理层或自动集群调度作为产品前提。
- 参考 Portainer 不自动引入其所有环境类型、Swarm 或 Kubernetes 管理体系；超出当前目标的能力需要明确修改产品范围。
- 配置跨节点操作不依赖数据迁移。数据迁移属于可选方向，需要说明是否纳入完整目标及支持的数据类别。
- 全局搜索、模板、GitOps、通知、细粒度权限或多租户等能力需要逐项作范围决定；未确认不等于永久排除，也不等于已安排到某个版本。
- UI 的信息结构和功能行为需要设计，完整视觉和控件细节允许随实现迭代。
- 文件、数据库或集中配置保管属于实现选择；后台落盘不与网页编辑或跨节点使用天然冲突。
