## 初稿 2026-11-03 01:41:54

结合那段会话最后的要求，我建议增加一份 **《文档编写导语》**，作为你和 AI 开始编写、修订文档时共同阅读的入口，可以放在 `docs/INTRO.md`。

它负责说明**主骨架、内容归属、参考资料和使用方式**；现有实施方案继续负责本轮任务、编写顺序、准备、检查和进度。两者各自维护对应内容。

导语开头可以这样写：

> 本项目以 **req42 作为需求内容的主骨架，以 arc42 作为架构与设计内容的主骨架**。其他指南、模板和成文案例用于补充对应位置的内容、表达方式和细化程度。所有补充资料都应融入统一的文档结构，并保留来源。
>
> 项目需求、用户确认、设计决定及实现和验证记录提供具体内容依据；外部资料帮助组织、解释和检查这些内容。编写者应区分已确认要求、候选设计、当前实现与验证结果，具体规则、参数和策略根据项目情况确定。
>
> 设计沿着系统与模块结构逐层展开：先说明整体组成、职责和依赖，再选择需要深入的组件，补充内部协作、公开能力、接口、数据与行为约定。内容可以写在所属章节中，也可以独立成文；独立规格应能从对应架构或模块说明中找到，公共约定由相关模块引用。
>
> 参考不同资料时，统一使用项目的术语、标识、章节层级和同类内容的表达方式。同一项精确定义保留一个主要维护位置，其他文档通过必要摘要和链接承接。来源记录应说明具体借鉴了什么。
>
> 编写前，先阅读相关项目材料与上游设计，再查阅适用指南及必要案例。随着需求和架构逐步明确，重新判断需要展开的内容、深度和文档安排；发现遗漏时同步调整实施方案。写后既检查正文，也检查原提纲是否充分覆盖当前阅读和实施需要。交付时明确本轮已覆盖内容及剩余缺口。

这段导语后面，应紧接一张**带层级的参考表**，将引用会话中选定的资料放到明确位置：

| 地位 | 资料 | 在本项目中的使用方式 |
|---|---|---|
| **需求主骨架** | [req42](https://req42.de/en/req42-at-a-glance) | 组织目标、范围、功能、质量要求、约束、术语及相关规划内容。 |
| **架构与设计主骨架** | [arc42](https://docs.arc42.org/section-5/) | 组织整体结构、模块逐层展开、接口关系、运行协作、部署、共同机制和设计决策。 |
| **模块规格补充** | MIS | 在对应模块说明下，补充公开操作、输入输出、状态、前提、异常和操作语义。 |
| **专项内容补充** | NASA Documentation Guidance | 在已有结构中，补充数据、接口、测试、运维及开发计划的适用内容。 |
| **正文范本** | [OpenTelemetry API／SDK](https://opentelemetry.io/docs/specs/otel/trace/sdk/)、GamePhysics MIS 案例 | 学习完整规格的组织衔接，以及生命周期、并发、超时和边界行为怎样写清楚。 |
| **按需专项参考** | AUTOSAR 模块规格 | 需要进一步细化接口、参数和配置表达时查阅。 |
| **组织与表达辅助** | Google Technical Writing、Diátaxis、C4 | 分别帮助正文组织、按阅读用途安排内容，以及检查图示表达。 |

这里应明确：**MIS 的内容落在 arc42 所组织的模块说明之下；NASA 的专项内容也应承接已有需求和设计。** 这是我们选定的组合方式。arc42 本身支持逐层展开重要组件，同时没有规定一种统一的具体接口模板，因而可以在对应位置采用这些补充写法。[arc42 第 5 章](https://docs.arc42.org/section-5/)

对 Docker Manager，可以用一个简短例子说明这条阅读路径：

> 整体架构 → Manager／Agent／Web → 需要深入的子模块 → 模块提供与依赖的能力 → 具体数据、接口和行为约定 → 对应验证场景。

例如，任务协调需要展开时，先确定 Manager 与 Agent 各自负责什么，再细化提交、授权开始、结果确认和恢复的约定；已有数据和接口定义通过引用承接。

采纳这份导语时，原方案也要同步调整三处：

1. **参考分工**：将接口、测试、运维等逐篇准备要求，明确接回主骨架与相关设计。
2. **推进安排**：在整体架构形成、关键模块展开或范围变化后，重新评估设计深度和剩余文档工作。
3. **完成判断**：分别说明“预定文件已起草”“当前阶段内容已覆盖”和“仍需补全的设计”。

这样，导语提供稳定的共同依据，实施方案根据项目进展持续调整；它们之间通过引用保持一致。

## 随后修正版 2026-11-03 01:56:34

是，这张表仍把资料按用途并列，容易让人理解成“写到模块就切换 MIS，写到接口就切换 NASA”。**它没有把 req42、arc42 持续参与后续编写的关系表达出来。**

应该按“正在展开什么内容”列行，明确每一项在主骨架中的位置，再列辅助参考：

| 正在编写的内容 | 持续参考的主骨架及关联内容 | 用于补充的资料 |
|---|---|---|
| 需求与功能 | **req42**：目标、范围、功能、支持模型、质量要求与约束 | Google Technical Writing 帮助组织和表达 |
| 总体架构 | **arc42**：上下文、方案策略、组成、运行、部署、共同机制、决策与风险 | C4 帮助表达和检查图示 |
| 模块详细设计与实施规格 | **arc42**：继续展开组件内部结构、职责、依赖、接口及运行协作，并承接共同机制和质量要求 | MIS 补充操作语义；OpenTelemetry、GamePhysics 提供正文范本 |
| 接口设计 | **arc42**：接口所属组件、提供与使用关系、运行交互、共同约定及质量场景 | NASA IDD、MIS 补充契约细节；AUTOSAR 按需提供实例 |
| 数据设计 | **arc42**：模块的数据职责、共同数据机制、一致性及相关决策 | NASA 数据字典补充字段、表示与约束 |
| 测试与验收 | **req42 的需求与成功标准 + arc42 的质量场景、运行过程和风险** | NASA STP 补充测试组织、环境、执行与结果记录 |
| 部署与运维 | **arc42**：部署关系、启动停止、异常恢复及共同机制 | Diátaxis、NASA SUM 帮助组织操作步骤和查询内容 |
| 开发实施计划 | **req42 的范围、路线与风险 + arc42 的结构、决策、质量要求与技术风险** | NASA 开发计划指导补充任务、依赖、资源与交付安排 |

导语中的核心约定也应直接写成：

> **req42、arc42 持续指导相关文档的编写与修订。进入模块、接口、数据、测试或运维等具体内容时，仍须查阅主骨架中的适用章节及关联设计，在此基础上使用专项资料补充细节。文档拆分不会改变这种归属关系。**

这里强调的是**持续查阅和落实适用内容**，不要求每份文档重复全部章节。Google Technical Writing 等表达指导也可以贯穿各篇使用。

例如，编写 Agent 的任务执行规格时，应先沿 arc42 理清它的内部组成、依赖和运行协作，再用 MIS 展开操作语义，用 OpenTelemetry 范本帮助写清超时、并发和关闭行为；新增设计同时回填相关架构说明。
