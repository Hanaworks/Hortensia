# Docker Manager 需求说明

日期：2026-11-02。版本：0.9。状态：待审阅；节点管理与迁移参考 PVE，Docker 操作参考 Portainer；迁移后验证及按用户选择删除来源已确认，存储搬运细节暂缓讨论。

Docker Manager 是一个自托管的多节点 Docker 管理器。用户在同一个 Web 界面中管理内外网中的独立节点及其 Docker 资源，使用分组和标签组织节点，直接编写和部署 Compose。Node Cross 用于将 Stack 迁移到另一节点；独立的 Copy、Apply 类操作用于复制配置及将配置应用到指定目标。迁移希望按需携带存储数据，前期允许通过手动打包和复制数据衔接。产品以 Portainer 的基础管理能力为参照，并提供 docker run 转 Compose 的配置工具。

本文面向用户、设计者和开发者，定义目标产品需要具备的能力、使用场景及成功标准。它覆盖完整目标范围，具体版本的实现顺序留给开发实施计划；组件划分、技术选型、数据库和接口格式由后续设计展开。

## 一 产品目标与使用背景

用户管理的是多台相对独立的 Docker 节点，并自行决定应用运行在哪个节点。日常部署通常使用 Compose，以便查看和修改配置。管理器需要同时保留节点视角和应用配置视角，让用户知道自己正在操作哪台节点、哪些资源，以及操作会带来什么变化。

产品要解决三个主要问题：

1. **日常管理集中在 Web 内完成。** 创建、查看、修改配置和部署不要求用户先登录服务器手工创建配置文件。
2. **多节点操作保持连续。** 用户能够了解多个节点的情况、定位资源，并按意图选择迁移部署位置，或复制配置用于另一份部署。
3. **配置表达与部署结果一致。** 使用 Docker 和 Compose 原本的能力，管理器不擅自注入额外网络、卷或应用部署配置。

2026-11-02 的补充明确了以下方向：

- 多人使用，按节点和操作授权；获准部署任意 Compose、创建容器的用户视为相应节点的可信运维人员。
- 节点管理和迁移的使用体验参考 PVE；Docker 资源操作与 Compose 管理参考 Portainer，具体参照分工见第四节。
- Node Cross 类似 PVE migration，表达部署位置迁移；复制配置和应用配置属于独立的 Copy、Apply 类操作。“来源保留、两端独立”适用于 Copy，不再作为 Node Cross 的定义。
- 迁移完成后增加验证，验证通过后由用户选择是否删除来源；删除不由迁移成功自动触发。
- 希望 Node Cross 能连同所需存储数据一起迁移；前期可先提供配置处理能力，允许用户手动打包、复制和恢复数据。只有配置复制能力时，不将其命名为已完成的迁移。
- 节点分布包含内外网，预计通常不超过 20 个；20 个作为设计和验证的参考规模，不设置为产品硬上限。
- 节点运行 Agent，由 Agent 主动连接管理端；部署环境须提供这一方向的可达路径。
- 增加节点分组、标签，以及将 docker run 命令转换为 Compose 配置的小工具。
- 当前以 Linux、FreeBSD 这类 Unix-like 环境为使用背景，优先实现可用 Docker CLI／Compose 下行为一致的操作；不提前增加复杂的跨平台适配要求，具体兼容版本随实现验证。
- Compose 配置按 Docker 原生方式处理；不提供 Build、Dockerfile 或构建上下文的管理与构建执行功能。
- 存储迁移目标及前期手动搬运方式继续保留，迁移细节暂缓讨论，不作为当前功能设计的前置条件。

下文是这些方向的需求细化稿。操作清单、质量要求和边界处理供本轮审阅；仍需作出的选择集中列在第九节。

## 二 使用者与运行环境

### 使用者

管理职责分为管理器自身的管理和节点资源的使用。负责管理器的人员维护账号、节点接入和授权；其他用户在获准的节点上查看或操作资源。一个用户在不同节点可以拥有不同的操作权限。

2026-11-02 用户确认采用可信运维人员协作模式，不要求同一节点上的不可信租户强隔离。管理器仍须严格执行节点和操作授权；任意部署权限属于对该节点的高信任授权，不能把界面中的操作拆分当作主机级安全隔离。

这里描述的是权限需求，不固定角色名称或角色数量。是否采用预设角色、可组合权限或用户组，在功能设计中根据这些需求确定。

### 运行环境

管理对象是独立 Docker 节点。节点加入管理器后，应用仍按用户指定的位置运行，不因接入管理器而自动形成调度集群。

| 条件 | 当前要求或需明确的内容 |
| --- | --- |
| 部署归属 | 管理器由使用方自托管；用户通过 Web 界面访问 |
| 管理规模 | 预计通常不超过 20 个节点，以约 20 个节点作为设计和验证基线；不设置 20 个节点的硬上限，更大规模的能力通过测试评估；每节点资源量和同时在线用户数待明确 |
| 节点操作环境 | 以 Linux、FreeBSD 这类 Unix-like 操作和接入环境为背景，前提是具备可用 Docker CLI、Compose 及目标 Docker 访问能力；优先统一命令行和文件操作约定，不提前为各平台分别建立适配要求，具体运行组合随实现验证 |
| 网络条件 | 覆盖公网、内网及混合部署；已确认 Agent 主动连接管理端，不要求节点有公网入口或节点之间直连，使用方须提供 Agent 到管理端的可达路径；具体协议和部署由架构设计展开 |
| 访问与授权 | 多用户访问；资源的可见范围和可执行操作受授权控制 |
| 配置入口 | 日常通过 Web 管理 Compose 配置；后台保存形式和执行位置由设计确定 |

功能验收至少使用两个节点和权限不同的用户，覆盖跨节点行为及访问限制；规模验证以约 20 个节点为基线，并包含内外网连接条件。超出该规模时不因固定数量限制而拒绝接入，实际性能与容量仍需验证。

## 三 术语与管理对象

| 术语 | 本项目中的含义 |
| --- | --- |
| Node／节点 | 被管理的独立 Docker 运行环境，资源操作有明确的目标节点 |
| Stack | 在某一节点上，围绕一份 Compose 应用配置管理的一组资源及其配置 |
| Compose service | Compose 配置中的服务定义；可以在 Stack 内查看，不增加独立于节点和 Stack 的全局 Service 管理层 |
| Docker 资源 | 容器、镜像、网络、卷等节点上的资源，既可能属于 Stack，也可能独立存在 |
| Stack 配置 | 用于部署的 Compose 定义、环境配置及受管理的附属配置；具体文件支持范围见第九节 |
| 运行数据 | 应用运行时产生或依赖的持久数据，例如卷或绑定目录中的业务数据，区别于部署配置 |
| Node Cross／迁移 | 将 Stack 的部署位置从来源节点转移到目标节点，按需携带数据；迁移后验证，通过后由用户选择是否删除来源 |
| Copy／复制 | 在目标建立独立配置，保留来源，后续配置维护与部署互不自动同步 |
| Apply／应用配置 | 将选定配置用于明确目标的部署；本稿沿用 R05 的部署规则，不隐含迁移或来源清理，最终入口名称可随交互调整 |
| 节点分组与标签 | 用于组织、查找和筛选节点的管理信息，不改变节点的实际部署位置 |
| 外部资源 | 管理器未创建、未完整掌握配置或由其他方式维护的节点资源 |

基本组织关系为 Node → Stack／Docker 资源。跨节点视图本身不改变归属；迁移需要显式处理来源与目标的部署关系，不能仅修改节点字段就视为已搬迁。

Copy 的“两边独立”指配置维护和部署操作独立，不保证应用数据天然隔离。例如两份配置仍引用同一外部数据库时，应用可能继续共享数据。Node Cross 则以部署位置转移为目的，保留来源作为回退材料不等于默认维持两份活动部署。

根据用户进一步说明，产品参照分为两个层面：

| 功能部分 | 本项目需要覆盖的内容 | 处理方式 |

| 多节点查看 | 汇总授权范围内的节点状态和资源概况，按节点定位和筛选 | 参考 PVE 的多节点管理组织方式，具体页面布局随交互细化 |

| Copy 与 Apply | 复制独立配置，或将选定配置应用到明确目标 | 复用配置及部署能力，不改变来源运行位置，不隐式清理来源 |

Portainer 官方资料包含 [Docker 资源管理](https://docs.portainer.io/user/docker)、[Web 创建 Stack](https://docs.portainer.io/user/docker/stacks/add) 和[跨环境复制 Stack](https://docs.portainer.io/user/docker/stacks/migrate)。本项目以自己的使用体验和行为要求为依据，不以“Portainer 不支持跨节点复制”作为需求前提。

节点及操作权限是本项目已提出的要求。参考权限设计时，应注意 Portainer 的细粒度角色控制在其文档中归属于 Business Edition，不能把它全部当作 Community Edition 的基础能力。[Portainer 角色说明](https://docs.portainer.io/admin/user/roles)

### 当前范围之外和可选扩展

当前管理模型不包含自动跨节点调度、独立的全局 Service 层或 Kubernetes／Swarm 集群编排。当前不提供镜像 Build、Dockerfile 编辑和构建上下文管理，部署使用已经构建好的镜像。

存储数据迁移纳入 Node Cross 的目标能力，由用户按需选择；其自动化实现可以后置。前期允许交付配置处理及手动搬运数据的衔接流程，目标见 R15。只有 Copy／Apply 时按实际能力交付；即使不需要搬运业务数据，Node Cross 仍需具备部署切换、迁移验证和来源处置流程。存储搬运细节继续暂缓，不据 PVE 类比承诺内存状态转移、在线热迁移或零停机。

两节点持续同步、GitOps、应用模板市场、完整主机管理及企业身份集成尚未纳入本轮基础范围。Node Cross 的迁移后验证和可选来源删除已纳入目标，不再列为范围之外。

## 五 功能需求

### R01 自托管与访问

使用方能够自行部署和运行管理器，通过 Web 完成基础管理流程。用户登录后按授权访问管理功能，管理器支持账号维护和权限调整。

成功标准：在受支持环境中可完成安装、初始化和登录；权限不同的用户得到相应的管理范围。安装方式及身份认证实现留给设计确定。

### R02 节点接入与管理

具备权限的用户能够添加内网或公网中的节点、验证连接、查看节点状态和基本信息，并维护接入配置。节点安装 Agent 并主动连接管理端，以覆盖混合网络场景；具体身份注册、通信协议和部署方式由架构设计展开。节点不可达时，界面应能区分“无法取得当前状态”和“节点中没有资源”。

从管理器移除节点表示解除管理关系，不应隐含删除该节点的容器、Stack 或业务数据。

成功标准：至少两个独立节点可被识别和分别管理；其中一个不可达时，仍能管理其他可达且已授权的节点。

### R03 节点视角与多节点查看

用户能够查看自己获准访问的节点及资源概况，按分组、标签筛选节点，从汇总信息进入具体节点、Stack 或容器；也能在节点内按资源类型查看和筛选。分组和标签管理见 R14。涉及修改的操作必须明确目标节点，切换视图不能使操作作用于另一节点。

成功标准：相同名称的 Stack 位于不同节点时，用户可以区分并定位；汇总结果不暴露未授权节点和资源。

### R04 Stack 配置编辑

用户能够在 Web 中创建、查看和修改 Compose 及环境配置，并把已有配置粘贴或导入到编辑流程。单个或多个 Compose 文件、环境文件、附属运行配置及其引用按所使用 Compose 版本的原生规则处理；文件组合顺序、变量解析和路径关系不由管理器另造规则。受管理配置应能再次打开继续维护，不要求用户预先在节点上手工建文件。

配置保存与实际部署的关系需要清楚：用户应知道当前编辑内容是否已经应用到节点。多人编辑同一份配置时，不能静默覆盖他人已经保存的修改。运行配置文件在管理器中的组织、导入与跨节点携带方式由功能设计说明；构建上下文和 Dockerfile 不属于本项目提供的能力。

成功标准：完成一次创建、保存、重新打开和修改；无需先 SSH 编辑文件。配置错误能够定位到相关内容或给出可理解的反馈，不能悄悄丢弃不支持的内容。

### R05 Stack 部署与生命周期

用户能够在选定节点上部署配置，查看 Stack 及其容器的状态，并完成配置更新、重新部署、启动、停止和删除。操作应说明对运行中资源的影响；删除 Stack 与删除持久数据的含义需要区分。

成功标准：一次部署从提交到结果都有可见反馈，能够区分请求已接受、执行结果和当前运行状态；部署失败时能找到错误信息及受影响对象。保存新配置不应被误报为已经部署成功。

### R06 原生 Compose 行为

管理器按照受支持的 Docker／Compose 行为部署用户配置，不擅自添加应用网络、卷或改变配置含义。环境变量、项目名称、文件组合等影响部署结果的输入需要清楚可见，并在设计中规定一致的处理方式。

多文件组合、覆盖、引用和路径处理遵循所使用 Compose 版本的原生语义，不为管理器定义另一套合并或替换方式。[Docker 多 Compose 文件说明](https://docs.docker.com/compose/how-tos/multiple-compose-files/)

镜像构建是明确的范围例外：本项目不执行 Compose build 或管理 Dockerfile、构建上下文。遇到依赖构建才能部署的配置，应提示用户准备可用镜像，不静默删除或改写 build 配置，也不自动触发构建。现有镜像的部署和 Dockerfile 构建能力分别处理。

Compose 自身按规则创建的资源属于原生行为。例如没有显式声明网络时，Compose 可以创建默认网络；本需求禁止的是管理器额外添加的部署行为，并非禁用 Compose 的默认规则。[Docker Compose 网络说明](https://docs.docker.com/compose/how-tos/networking/)

成功标准：在相同节点条件、Compose 版本、配置、环境和项目参数下，对照原生部署，应用资源和关键配置的语义一致。不支持的配置应明确说明限制，不静默改写成另一种部署。

### R07 Node Cross 迁移与验证

用户从节点 A 的一个 Stack 发起迁移，选择节点 B，核对配置、数据和目标依赖，使该 Stack 的部署位置转移到 B。目标是由 B 接替相应部署角色；仅在 B 新增一份独立部署属于 R17 的 Copy／Apply。

迁移需要说明来源与目标的当前状态、计划改变的对象、尚未满足的条件和失败后的处理依据。来源退出活动部署角色属于迁移切换的设计范围，具体停止时点和可接受中断尚未确定；不得把 Copy 的“从不改变来源”约束套用到迁移。目标同名或资源冲突须显式处理，不能静默覆盖。

**迁移执行与迁移验证分开。** 执行结束后验证目标配置、预期资源和运行状态、可检查的数据依赖，以及来源的切换状态；需要业务确认的项目由用户确认。命令退出成功、容器启动和业务健康不是同一结论。没有验证、验证失败或结果未知时，不能报告“迁移已验证完成”，也不能进入来源删除。

验证通过后，由用户选择保留或删除来源。删除选择必须说明影响的是来源管理配置、运行资源还是持久数据，并按 R05、R10、R11 分别检查；不把“删除来源”默认解释为递归清空所有数据。用户保留来源时仍可完成迁移；清理失败单独显示，不能抹去迁移与验证的记录。失败或失联时按阶段核对两端，不盲目重启来源、重做迁移或清理任一端。

成功标准：B 已达到本次约定的部署状态，来源不再承担迁移后的活动部署角色，迁移验证有明确范围和证据；之后用户可选择保留来源或发起有明确范围的删除。具体存储一致性、切换和回退机制待设计补全，不能用配置复制验收替代本项。

### R08 容器管理与诊断

用户能够查看授权节点上的容器列表、详细配置及运行状态，完成独立容器的创建和生命周期操作，并按权限查看日志、运行统计或进入控制台。

对于属于 Stack 的容器，界面应显示所属关系，说明直接操作与 Stack 配置之间的影响，避免用户误以为修改运行资源必然同步回 Compose 配置。

成功标准：用户能够定位某节点的异常容器，查看诊断信息并执行获准的操作；没有控制台权限的用户不能通过其他入口取得交互式执行能力。

### R09 镜像与仓库访问

用户能够查看节点上的镜像、标签及使用情况，拉取所需镜像并进行标签、删除或清理操作。使用需要认证的镜像仓库时，管理器应支持相应访问配置，并限制凭据的查看和使用权限。

本项目使用已有镜像进行部署，不提供 Dockerfile 构建或其他镜像 Build 操作。

成功标准：可从允许访问的仓库拉取指定镜像，失败时说明原因；清理时清楚显示作用范围和结果，不把删除镜像等同于删除应用运行数据。

### R10 网络与卷管理

用户能够查看、创建和删除节点上的网络与卷，查看可取得的资源关联信息。属于 Stack 或被容器使用的资源需要体现其关联；信息不完整时应说明，不能把未知关联当作没有关联。

删除持久数据的操作需明确对象和后果，并要求用户作出对应选择。Node Cross 携带存储数据的需求由 R15 定义；独立的卷文件浏览和编辑功能仍需另行确定。

成功标准：资源操作作用于选定节点和对象，结果可查看；卷删除及数据影响与一般资源解绑可以区分。

### R11 多用户与节点及操作权限

管理器能够区分用户，并限制每个用户能访问的节点及能执行的操作。需要区分资源查看、配置读取与修改、部署、生命周期操作、删除、控制台和授权管理等不同能力；具体权限项和组合在功能设计中定义。

权限限制同时作用于界面和实际请求。日志、配置、环境变量、凭据及导出内容可能包含敏感信息，不能因为用户可以查看资源概况，就自动允许读取所有敏感内容。

跨节点流程按实际动作检查两端权限：Copy 需要来源配置读取或使用权限及目标配置维护权限，Apply 还需目标部署权限。Node Cross 除配置与目标部署授权外，还需来源切换涉及的运行控制权限；验证读取诊断或敏感配置、删除来源资源和删除数据分别检查相应权限。携带数据还需相应来源数据访问、目标写入或恢复权限。一个阶段的成功不授予下一阶段权限；迁移者没有来源删除权限时仍可保留来源，由获准人员另行清理。用户有 A 节点权限，不代表有 B 节点权限；分组、标签也不隐式扩权。执行中撤权的处理在功能设计中明确。

成功标准：用不同账号验证同一节点不同操作、不同节点不同权限以及 Node Cross 两端授权；直接请求接口也不能越权，拒绝请求不能造成未授权操作的副作用。

### R12 已有资源的查看与配置接管

接入一个已有容器、网络或卷的节点后，管理器应能在授权范围内展示这些资源，并区分可操作范围与配置掌握情况。资源可见不等于完整 Compose 配置已经可编辑。

对于已有 Compose 项目，若无法取得完整配置，应说明所缺资料；只有配置来源和接管行为明确后，才提供相应编辑、重新部署或 Node Cross 能力。导入或接管不得自动改写正在运行的资源。

成功标准：已有资源不会仅因不是管理器创建而全部不可见；配置缺失时，界面能解释限制，不把不完整信息当作可直接复制的完整 Stack。

### R13 操作反馈与管理器维护

用户能够查看部署和重要修改的目标、发起者、时间、结果及必要错误信息，避免多人操作后无法辨认发生了什么。断开浏览器或节点连接后，系统需要区分操作失败与暂时无法确认结果，不能直接把未知状态报告为成功。

管理器应具备更新、配置备份与恢复的交付办法。管理器自身的配置和业务记录，与被管理应用的运行数据分别说明；备份管理器不能被表述为已备份所有应用数据。

成功标准：能够追查一项重要操作，并依据实际记录理解其结果；按后续交付约定能恢复管理所需信息。记录内容、保存周期及具体恢复步骤在相应设计和运维文档中确定。

### R14 节点分组与标签

具备相应权限的用户能够创建、修改和删除节点分组与标签，将节点归入分组或赋予标签，并按这些信息查找、筛选节点。分组或标签变更只影响管理组织，不自动移动、停止或删除节点上的应用；删除分组或标签不等于移除节点。

分组是否允许多重归属、是否支持层级、标签的命名和组合方式在功能设计中细化。分组和标签先作为组织功能；如需要按组授权，应明确规定授权变更规则，不能由普通的归类操作隐式获得额外权限。分组列表、标签和资源计数遵守用户的可见范围。

成功标准：能够按部署位置、用途等信息组织内外网节点，并组合筛选找到目标；改变归类不会改变运行资源或绕过已有授权。

### R15 Node Cross 携带存储数据

目标是让 Node Cross 迁移时，按需将 Stack 所需存储数据带到目标节点，减少手工搬运。数据准备与部署切换需要衔接；迁移验证及可选来源删除遵循 R07，不默认建立两端持续同步。

前期可以先实现配置处理，并允许用户手动打包、传输和恢复所需数据；这不要求前期同时提供自动归档或上传下载功能。仅完成 Copy／Apply 或用户声明数据已准备时，不将其报告为完整迁移已经验证成功。

**本项细节暂缓讨论。** 支持的存储类型、数据量、传输方式、数据一致性、可接受的中断以及恢复行为均未定，不因迁移目标就默认允许任意停机，也不承诺在线迁移。待后续重新展开本项时再确定，不阻塞 Copy／Apply 及其他功能的设计。

成功标准：当前配置处理允许用户自行准备目标数据，并区分配置准备、数据准备、迁移执行和迁移验证。来源数据删除只在验证通过且用户明确选择后按授权范围执行。自动搬运与数据完整性验证的具体标准待支持范围确定后补充，不将本项记为已经完成设计或验证。

### R16 docker run 转 Compose

用户能够在 Web 工具中粘贴 docker run 命令，得到可查看、编辑和复制的 Compose 配置，也能将结果带入创建 Stack 的编辑流程。转换和部署是独立动作，工具只解析命令文本，不执行输入命令、不触发 shell 展开或自动部署；后续保存和部署仍遵守节点权限。

常用转换范围应覆盖镜像与容器名称、端口、环境变量、卷和绑定挂载、网络、重启策略、用户、工作目录、入口与启动命令等。具体参数映射以 [Docker run 参数](https://docs.docker.com/reference/cli/docker/container/run/)和 [Compose service 定义](https://docs.docker.com/reference/compose-file/services/)为依据，在功能设计中明确支持清单。

不能等价转换或尚未支持的参数要逐项提示，不能静默丢弃。引用的环境文件、宿主机路径、外部网络等依赖需要保留并提示准备，不能虚构其内容或假设目标节点已存在。对于变量、命令替换、引号和续行等 shell 语法，明确可解析的范围；无法确定的内容交由用户补充，不读取执行环境来猜测。转换结果需要区分已映射内容、运行方式差异与待人工调整项，不宣称所有命令都能无损转换。

成功标准：典型命令生成可解析的 Compose 配置，镜像、端口、变量、挂载及启动参数符合已声明的映射规则；未转换项可见，用户能够修改并进入 Stack 编辑流程。输入包含命令替换或其他 shell 操作时不执行其中内容；仅转换不会在任何节点创建资源。

### R17 独立的 Copy 与 Apply

Copy 将选定的已保存配置及受管理文件复制为目标节点上的独立 Stack 配置；来源保持不变，后续两端修改与部署不自动同步。Copy 成功只代表目标配置已保存。Apply 将选定配置应用到明确目标，沿用 R05 的部署、冲突及结果规则；它不隐含来源停止或删除。

复制内容、目标调整和外部依赖须可检查。目标同名时不静默覆盖；已保存完整配置可以在来源离线时用于 Copy，但这不能证明来源已停止，也不能据此完成 Node Cross。目标配置含原文中的敏感值，按两端配置权限处理；管理器的连接和仓库密码不随配置复制。

成功标准：用户能明确区分迁移、复制和应用配置；Copy 后来源保持原状，目标配置独立；Apply 的部署结果单独报告。重复提交同一次 Copy 不创建多个目标，目标部署失败不改变来源。

## 六 主要使用场景

### 场景 A 接入并管理节点

管理人员接入内网与公网中的独立节点，按用途或位置设置分组和标签，为用户配置访问范围。用户登录后了解获准访问的节点状态，通过分组或标签找到目标，再进入节点查看资源。其中一个节点离线时，其状态明确，其他节点仍能继续管理。

### 场景 B 在 Web 内维护一个 Stack

用户选择节点，输入 Compose 和环境配置，保存并发起部署。用户查看结果，发现需要修改后重新进入编辑流程，理解修改是否已保存、是否已应用。整个日常流程不需要先登录服务器手工维护配置文件。

### 场景 C 迁移部署位置并验证

用户打开 A 的 Stack 发起 Node Cross，选择 B，准备配置与所需依赖，按确定的切换方案迁移。执行完成后验证 B 的目标状态和 A 的切换结果，验证通过后由用户决定是否删除来源。若失败、失联或验证不通过，显示已完成阶段和两端已知状态，不自动清理来源或假定可以直接回退。

### 场景 D 按权限协作与排障

一名用户只获准查看某节点资源，另一名用户可以部署和操作。前者能够获取允许的诊断信息，但无法修改配置、执行控制台命令或向未授权节点复制配置。

另用两名均有配置编辑权限的用户验证协作：两人先后打开同一配置并提交修改时，系统不会把后保存的内容静默覆盖到另一人的修改上。

### 场景 E 接入已有资源

用户接入一个已经运行应用的节点，能够查看资源和关联情况。对于配置来源不完整的项目，管理器说明其管理范围，并引导补充必要配置；接入本身不改变原有部署。

### 场景 F 带数据部署到另一节点

用户希望把 A 上应用的配置及所需数据迁移到 B。前期允许自行打包、传输和恢复数据，之后仍按 R07 进行切换、验证和来源处置；仅完成配置准备不能代替这些步骤。具体存储处理、数据一致性和中断要求暂缓展开，不由本场景预定技术流程。

### 场景 G 将安装命令转换为配置

用户从应用安装说明中取得一条 docker run 命令，粘贴到转换工具，检查生成的 Compose 和未转换项，补充目标需要的路径或环境值，再将配置带入 Stack 编辑流程。用户可以只复制结果退出，转换本身不连接节点执行命令或部署。

### 场景 H 复制配置并独立部署

用户通过 Copy 把 A 的选定配置保存为 B 上的独立配置，调整目标差异，再通过 Apply 部署。A 的配置和运行状态不变，B 的失败不触发 A 停止或清理；两端后续按各自配置维护。

## 七 质量要求与验收方向

以下目标采用可观察场景描述。节点规模以约 20 个作为设计和验证基线，网络覆盖内外网；每节点资源量、并发用户、响应时间及数据迁移量仍需结合第九节明确。20 个节点不是产品硬上限，也不据此承诺任意规模的性能。

| 编号 | 要求 | 验收方向 |
| --- | --- | --- |
| Q01 操作对象清晰 | 用户在多节点、同名资源和多个页面之间操作时，能识别目标及影响范围 | 用两个节点的同名 Stack 走查查看、编辑、删除和复制，验证对象没有混淆 |
| Q02 行为可解释 | 配置、保存内容、已部署内容和当前运行结果有明确关系 | 对照 R04—R07、R17，区分保存、复制、部署、迁移执行、验证及来源清理的结果 |
| Q03 权限有效 | 未授权用户不能通过页面、直接请求或跨节点流程获得受限数据或执行受限操作 | 覆盖节点、操作及两端授权组合；后端拒绝请求，目标资源无越权变更 |
| Q04 失败可判断 | 网络中断、执行失败和无法确认结果有可区分的反馈 | 中断连接后检查显示和记录；无法确认时不报告成功，不因自动重试制造隐蔽的重复副作用 |
| Q05 多人修改可控 | 用户不会在不知情的情况下覆盖他人配置 | 两人先后打开并提交同一配置，冲突得到提示或被明确解决；解决机制不在需求中固定 |
| Q06 兼容边界清楚 | 优先使用 Unix-like 环境中一致的 Docker CLI／Compose 行为，遵循所使用版本的原生语义，不提前扩展平台适配，明确不提供 Build 能力 | 在实际选用的运行组合上验证单文件、多文件和附属运行配置，记录已验证的环境；遇构建依赖明确提示且不自动构建，不静默删改配置 |
| Q07 敏感信息受控 | 凭据、环境配置和日志的访问遵守权限，管理器生成的错误与记录避免不必要地泄露敏感值 | 检查配置查看、复制、导出和错误反馈；诊断与控制台权限覆盖可能暴露敏感数据的路径 |
| Q08 管理可恢复 | 管理器必要数据能够备份和恢复，恢复范围与步骤明确 | 在隔离环境进行备份恢复演练，核对账号、授权、节点及 Stack 配置等约定对象 |
| Q09 日常操作可用 | 在约 20 个内外网节点的参考规模下，资源查看、分组筛选、编辑与部署反馈能够支持正常管理 | 以 20 个节点开展规模验证，补充资源数、并发用户和网络条件后确定时间及负载标准；更大规模另行测试，不设置固定 20 节点限制 |
| Q10 迁移结果可核对 | 配置准备、数据准备、部署切换、迁移验证和可选来源清理可区分；存储搬运机制暂缓 | 复制或目标部署成功不等于迁移已验证完成；验证未通过不得进入来源删除，通过后按用户选择处理 |
| Q11 转换结果可信 | 支持范围内的 run 参数有明确映射，未转换项和语义差异可见，转换不执行输入内容 | 用带引号、变量、挂载、启动参数及不支持选项的命令检查输出，并验证 shell 表达式未被执行、没有自动部署 |

部署命令完成、容器运行和应用业务健康是不同的观察层次。验收时需要按场景说明判定哪一层，不能把请求已接受或容器已启动统一当作应用业务可用。

## 八 约束与成功标准

已确认采用 Agent 主动连接管理端。具体技术栈、配置存储及通信协议由[架构设计](architecture.md)提出方案；候选技术仍需审阅和实现验证。用户不必预先完成整套 UI 视觉设计；需要明确的操作行为先在功能设计中说明，具体布局随实现细化。

本产品的核心成功标准是：有权限的用户能够从一个入口管理多个独立节点，在 Web 内维护并部署 Compose，明确选择 Node Cross 迁移或独立的 Copy／Apply。迁移后验证，通过后由用户选择是否删除来源；Copy 保留来源并产生独立目标配置。节点和操作权限在各阶段持续有效。

在此基础上，用户能够组织内外网节点，利用命令转换工具获得可继续编辑的配置，并在跨节点部署需要旧数据时选择适用的数据准备流程。前期手动搬运数据是允许的交付方式；完整目标中的自动迁移能力仍需按支持范围设计和验证。

后续测试至少围绕以下需求组合展开：

| 验收主题 | 对应需求 | 应看到的结果 |
| --- | --- | --- |
| 接入、查看与节点隔离 | R01—R03、R11、Q09 | 内外网节点可管理，约 20 节点基线下功能可用，操作和数据可见性符合授权 |
| 创建、编辑与部署 | R04—R06 | Web 流程完整，保存与部署可区分，语义符合原生 Compose |
| Node Cross 迁移 | R07、R11、Q10 | 目标接替、来源切换和验证结果可核对；验证通过后由用户选择是否删除来源 |
| Copy 与 Apply | R17、R05、R11 | 来源不变、目标配置独立，复制与部署分别报告，冲突和授权不被绕过 |
| 日常资源管理与诊断 | R08—R10 | 能完成草案中列出的基础操作，作用范围与反馈明确 |
| 已有资源 | R12 | 可见范围和配置掌握程度清楚，接入不触发非预期修改 |
| 失败、协作与恢复 | R04、R11、R13、Q04—Q09 | 未知结果不误报成功，修改冲突可处理，管理信息可恢复 |
| 节点组织 | R03、R11、R14 | 分组和标签可维护、可筛选，归类不影响运行资源或隐式扩权 |
| 携带存储数据 | R07、R11、R15、Q10 | 当前允许手动准备数据，不以准备声明代替迁移验证；自动搬运细节与完整验收暂缓 |
| run 转 Compose | R04、R16、Q11 | 支持的参数映射正确，未转换项可见，结果可编辑并用于 Stack 创建，转换本身不执行命令 |

这些是验证目标，尚不代表实现或测试结果。具体用例和测试记录在后续文档中维护。

## 九 待明确事项

| 问题 | 需要明确的内容 | 对后续工作的影响 |
| --- | --- | --- |
| 实际运行与容量验证 | 已明确以 Linux、FreeBSD 这类 Unix-like 环境中的一致使用行为为目标、内外网混合及通常不超过 20 个节点；实际版本组合、每节点资源量、并发用户和具体网络约束随设计与验证落实 | 先推进统一行为的设计与实现；不把提前列全系统和处理器兼容矩阵作为开工条件 |
| 运行配置的管理方式 | 单个或多个 Compose 文件、环境文件及附属运行配置均遵循原生语义；仍需设计文件组织、导入、依赖定位与跨节点携带方式，明确目标端需已有的资源 | 功能设计落实已定原则，不再把“是否按原生处理多文件”或“是否支持 Build”列为待定 |
| 账号与权限细节 | 已确认可信运维协作；功能设计已提出操作组合、账号生命周期、敏感配置访问及执行中撤权的行为建议 | 审阅具体行为，架构据此确定认证授权机制，不再重复确认信任边界 |
| 基础功能细化 | 镜像导入导出、卷文件浏览等是否属于实际需要；已有 Compose 项目如何提供配置并接管 | 保持基础范围可读，在相关功能设计时补全；镜像构建已明确不在范围内 |
| 操作与数据的维护 | 删除关联数据的选择、冲突处理、操作记录保留、管理器备份恢复范围 | 功能、数据、测试与运维设计共同使用的规则 |
| Node Cross 切换与验证细化 | 已确认迁移后验证、通过后由用户选择是否删除来源；具体切换顺序、验证项目及业务确认、失败回退仍需设计 | 不能以现有 Copy 模型表示完整迁移；相关接口和测试保留这一设计缺口 |
| 存储迁移细节，暂缓讨论 | 保留迁移目标和前期手动搬运方式；存储类型、数据量、中断要求及具体机制暂不确定 | 不阻塞其他功能设计，不默认任意停机或零停机；后续重新展开该项时再处理 |
| 分组和标签细节 | 分组层级与归属、标签结构、维护权限以及是否参与授权 | 功能设计展开组织和筛选行为，避免归类影响权限的规则不清 |
| 命令转换范围 | 目标 shell 语法、常用参数映射、不支持参数的反馈，以及生成配置衔接编辑器的方式 | 功能设计建立转换支持清单与示例，验收按清单检查，不承诺任意脚本转换 |

以上问题不阻止已明确内容的设计。涉及其中某项时，在对应主文档作出决定并回填本篇；不以未决问题为由自行缩减目标，也不填入未经确认的数字或规则。
