# Docker Manager 功能设计

日期：2026-11-02。版本：0.5。状态：待审阅；多节点管理与迁移参考 PVE，Docker 操作参考 Portainer；迁移后验证及按用户选择删除来源已确认，存储搬运细节暂缓。

本文把[需求说明](requirements.md)展开为用户能够执行的操作、操作前提、结果和异常处理，供后续架构、数据、接口与测试设计使用。基本路径是：登录并选择节点，管理 Stack 和 Docker 资源，按意图迁移部署位置或复制配置独立部署，也可通过命令转换工具准备新的 Compose 配置。

需求中已经确认的范围继续适用。本文新增的分组结构、权限组合、编辑冲突处理和删除流程属于本稿建议，可根据审阅调整；第十二节集中说明影响较大的选择。本稿不确定技术栈、节点连接协议、数据库或界面视觉布局。

## 一 管理对象和功能入口

节点是资源归属和授权范围的基础。Stack 属于一个节点，包含用于部署的配置及其关联资源；容器、镜像、网络和卷也可独立存在。Compose service 保留在 Stack 内，不增加全局 Service 管理层。

功能组织采用用户提出的参照分工：整体节点管理、节点切换和迁移体验参考 PVE；进入节点后的 Docker 资源操作与 Compose 管理参考 Portainer。下表将这一方向落实为本项目的入口和上下文，具体布局随交互细化。

| 入口 | 用户要完成的任务 | 必须保留的上下文 |
| --- | --- | --- |
| 节点总览 | 查看获准访问的节点，按名称、分组和标签定位 | 节点身份、连接状态、信息更新时间 |
| 节点详情 | 查看 Stack、容器、镜像、网络、卷及节点操作记录 | 当前节点；切换资源类型不改变节点 |
| Stack 详情 | 查看、编辑、部署、控制、Node Cross 迁移、Copy 和移除 | 节点、Stack、配置版本、操作类型及相关记录 |
| 命令转换 | 输入一条 run 命令，检查和修改生成的 Compose | 原命令、转换结果、未解决项目；带入创建流程后才选择部署对象 |
| 管理设置 | 维护账号、授权、节点接入、分类、仓库访问及管理数据备份 | 操作人的管理权限及修改影响范围 |

列表行和操作确认中使用“节点 + 对象名称”定位对象，实际身份不能只依赖可重名的显示名称。用户切换节点后，已经打开的编辑或操作窗口仍绑定原对象；提交前再次显示该对象，不能把未提交操作转移到新节点。跨节点汇总只显示获准访问的信息，包括计数、筛选选项和操作记录。

## 二 登录和权限

### 账号生命周期

本稿建议先提供本地账号：安装初始化时创建首位管理员，随后由管理员创建、停用账号、调整授权和重置登录凭据；用户可以修改自己的登录凭据并退出登录。企业身份集成不在本轮范围。初始化不能在已完成后被匿名重复执行；不得通过停用或降权移除最后一个可用管理员。

登录失效或账号停用后，拒绝新的管理请求并关闭受限实时订阅。编辑器应提示登录状态变化，保留当前页面未提交内容的机会，但不能因重新登录绕过保存时的授权和版本检查。会话有效期、凭据存储和恢复办法由架构与运维设计落实。

### 节点范围与操作权限

节点访问范围和操作权限共同决定是否允许一次操作，所有入口使用相同规则。页面隐藏按钮只是提示，实际请求、任务执行和实时流仍需要校验。用户不能通过节点分组、标签或自行提交对象标识获得额外授权。

| 权限组 | 允许的行为 | 不随之自动获得的能力 |
| --- | --- | --- |
| 资源概览 | 查看授权节点、资源摘要、状态及非敏感统计 | 完整配置、环境值、日志、控制台 |
| 配置读取 | 查看和导出 Stack 原文、受管理运行文件及完整资源配置 | 编辑、部署；不得借此读取连接凭据或仓库密码 |
| 配置维护 | 新建、导入、保存、接管和移除管理器中的 Stack 配置 | 执行部署和删除运行资源；完整编辑需要同时具备配置读取 |
| 部署与容器创建 | 部署、更新 Stack，创建独立容器，使用获准的仓库凭据 | 修改账号、节点接入和授权；属于高信任操作 |
| 运行控制 | 启动、停止和重启既有 Stack／容器 | 创建、重新部署或删除资源；控制台另行授权 |
| 诊断读取 | 读取应用日志及受限诊断输出 | 交互式控制台；日志可能包含应用敏感值 |
| 容器控制台 | 在授权节点的容器中打开交互执行会话 | 管理器系统设置；属于高信任操作 |
| 镜像及网络维护 | 拉取、标记、创建网络等对应操作 | 删除持久数据；仓库凭据的使用还需单独授权 |
| 资源删除 | 删除容器、镜像或网络，执行 Stack 运行资源移除 | 删除卷中的持久数据 |
| 卷维护与数据删除 | 创建卷；另行授予删除卷及其数据的能力 | 自动化存储迁移，本稿未定义该流程 |
| 系统管理 | 账号、授权、节点接入、分组标签、凭据配置和管理数据维护 | 不隐含对应用数据执行迁移或清理 |

这些是可理解的授权组合，不要求每组只能有一个开关。数据与接口设计应把查看、创建、修改和删除等具体动作列清。普通账号默认没有节点权限；管理员明确授予节点和动作。可提供“观察者”和“节点运维”快捷模板，保存前展示实际授权内容；模板名称不改变底层动作规则。系统管理员能调整授权，因此属于管理信任范围。

**已确认的使用边界：** 2026-11-02 用户选择可信运维人员协作，按节点和操作授权。获准部署任意 Compose、创建容器的用户视为相应节点的可信运维人员，本轮不提供同节点不可信租户强隔离。Docker 的主机目录挂载等能力可能使这类用户取得主机级访问，授权时应按这一实际能力理解。[Docker Engine 安全说明](https://docs.docker.com/engine/security/)

管理器必须严格校验其自身入口的节点与动作权限。权限表描述管理器允许发起的动作，不承诺已获任意部署能力的人无法通过应用运行机制达到其他效果。

节点身份是管理与授权对象，不自动构成宿主机隔离。Manager 与受管节点同机、或多个 Docker 环境共享宿主机时，需要满足[架构设计](architecture.md)第九节的部署信任约束。

### 权限变化和敏感信息

提交操作和实际执行前均检查权限；等待中的操作若已失去权限，终止并记录原因。本稿建议已经开始的 Docker 操作继续取得结果，不因权限撤销盲目中断或回滚；撤权立即禁止后续新操作、控制台输入和受限输出订阅。已运行命令产生的后台进程不承诺被自动终止。需要停止应用时，由仍有权限的人另行操作。

Copy 检查来源配置读取及目标配置维护权限，Apply 还需目标部署权限；这两项不改变来源运行状态。复制尚未提交就失去来源权限时，拒绝该次复制提交；已合法建立的独立目标配置按目标授权管理。

Node Cross 另外检查来源切换所需的运行控制权限。迁移验证按实际读取的资源、配置和诊断信息授权；验证通过不自动获得删除权。来源配置、运行资源和持久数据的删除分别检查相应权限，并由用户选择。每个尚未开始的阶段重新检查授权；已开始操作按既定规则取得结果，不能因撤权自动触发来源重启或清理。

完整配置、日志和控制台均可能暴露敏感值，不能作为普通概览返回。仓库与节点连接凭据单独维护，普通配置导出不包含其密码。管理器生成的记录使用凭据引用和脱敏错误；用户自行写入 Compose 或环境文件的秘密仍随相应配置读取权限保护，不能宣称自动识别并消除所有敏感信息。

## 三 节点接入和组织

有系统管理权限的用户创建节点记录，取得限定该节点的注册信息，并在节点安装 Agent、配置管理端地址和信任信息。Agent 主动接入后验证访问目标。连接检查分别报告能否建立连接、能否访问 Docker、Compose 是否可用，以及可取得的版本与基本信息；检查失败保留配置供修改，不把“已保存节点记录”显示成“可部署”。主动连接方向已由用户确认，注册与通信机制见[架构设计](architecture.md)；不要求内网节点有公网入口或节点之间可以直连，但需要 Agent 能访问管理端。

节点状态区分“待验证”“可连接”“不可连接”和“信息过期”；同时显示最近成功观察时间。离线时可查看已保存配置及标明时间的历史信息，不能显示为零容器或全部停止。一个节点失败不阻塞其他节点的查询。修改连接目标必须重新验证，避免将同名节点误认为原目标。

本稿建议采用**平级分组，每节点至多归属一个组；标签可有多个**。未分组节点仍可正常管理；分组与标签仅用于组织筛选，不参与授权继承。系统管理权限负责维护分类，普通用户只看到与自己获准节点相关的分类及数量。移除组使节点回到未分组，移除标签只取消关联；这些动作不改变部署位置和授权。名称唯一性、长度等数据校验在数据设计中统一。

移除节点仅解除管理关系。执行前列出管理器中关联的 Stack 配置和历史记录，让用户选择保留离线记录或明确删除相应管理配置；默认保留。节点上正在执行且结果未明的任务必须先核对或交由管理员处理，不能以移除节点掩盖任务状态。节点上的容器、网络、卷和业务数据不随移除而删除。重新接入时校验实际目标并显式关联旧记录，不仅按显示名自动合并。

## 四 Stack 配置准备与编辑

### 文件与部署输入

一个 Stack 保存一组受管理配置文件和部署输入。编辑器能够新建、粘贴、上传和下载文件，并保留文件名与相对目录；本稿不增加 Git 仓库管理。文件组织包括 Compose 文件、用于变量解析的环境文件、service 的 `env_file` 以及用户明确提供的附属运行配置。它不包含 Dockerfile、构建上下文或自动收集的业务数据目录。

用户能看到并调整：Compose 文件的选取和顺序、项目目录、最终项目名、变量输入来源、选用的 profiles 和必要的运行配置引用。新增 Stack 的界面名称可以不同于实际项目名，部署前必须显示最终项目名；同一节点不能把两个受管理 Stack 绑定到同一实际项目。所有首次部署还须检查节点上已有的未接管项目；存在同名项目时，改名新建或进入第七节的显式接管流程，不能直接用新配置更新它。离线或无法核实项目身份时可以保存草稿，但不能据此认定没有冲突并部署。修改已绑定项目名应作为新建项目处理，不伪装成原 Stack 的普通改名。

Compose 多文件合并及各引用的路径基准遵循原生规则；不同机制如多个 `-f` 文件与 `include` 的路径处理不能被统一改成“相对每个文件”。保留输入文件，解析预览只用于解释和校验，不覆盖用户原文。[Compose 多文件合并](https://docs.docker.com/compose/how-tos/multiple-compose-files/merge/)、[include 的路径处理](https://docs.docker.com/reference/compose-file/include/)

变量解析环境必须来自用户可识别的部署输入。管理器不能把自身进程中的无关环境变量偷偷用于部署。用于 Compose 插值的环境输入与传给容器的 `env_file` 分开显示；它们按原生优先级参与解析，而不是合为一张无来源变量表。实际执行应显式建立对应环境，并使预览和部署使用相同输入。[Compose 变量解析](https://docs.docker.com/compose/how-tos/environment-variables/variable-interpolation/)

用户明确上传的附属配置可作为文件随 Stack 保存；路径引用本身不授权管理器遍历主机或读取任意文件。配置中引用的绑定目录、外部卷、网络、外部服务和未上传的文件列为依赖，并区分“已检查”“缺失”“未验证”。部署所在目录如何在节点上准备，由架构说明；其内容必须支持 Web 创建文件的完整流程。涉及下载或节点读取的引用，校验其访问范围和凭据，不自动把它转化为永久受管理文件。

### 保存与多人编辑

打开配置时取得一个明确版本。保存时比较该版本是否仍是当前版本；若别人已保存，拒绝静默覆盖，并提供查看差异、重新载入和保留自己内容后重新编辑的方式。本稿不引入实时协同编辑或自动合并。

可以保存暂时无效的草稿，但必须标出错误，不能进入部署。每次保存产生可识别的新版本；一次部署固定引用所提交的文件与输入快照，不在执行中改用后来保存的内容。历史保留数量由数据设计确定，至少能解释当前草稿、最近成功提交到节点的配置以及尚未核对的操作输入。

页面分别显示编辑器未保存内容、已保存版本、最近成功执行部署的版本和最近一次操作。只显示“已保存”不表示“已部署”；最近一次部署成功也不表示应用目前健康。即使版本相同，镜像标签指向或外部资源改变也可能影响运行结果，因此版本一致不能代替运行检查。

## 五 Stack 部署和生命周期

### 部署与更新流程

1. 用户选择节点和 Stack，保存本次配置，检查即将部署的版本、项目名、文件组合及环境输入。
2. 管理器检查授权、节点连接、Compose 可用性和配置有效性；展示能确定的镜像、挂载和外部依赖问题。不能检查的条件注明原因，不声称所有条件已就绪。
3. 展示本次动作及已知影响，包括可能重建容器、端口或资源名冲突；部署预检不承诺精确模拟所有 Docker 副作用。用户明确提交后创建一条操作记录。
4. 开始执行前再次核对目标、权限及配置快照。对同一 Stack 的部署、停止、启动和删除等冲突动作，本稿建议拒绝并发提交并返回当前操作入口；配置仍可编辑保存，之后另行部署。
5. 持续提供阶段、输出和结果。完成后刷新可取得的运行状态，分别展示操作结果、容器状态和 Docker 提供的健康状态。

部署必须禁止构建。含 `build` 的原文可保留为草稿，系统提示不会执行它；用户需为本次启动的服务提供可用镜像，并按不构建方式校验和执行。只有构建来源、或执行策略要求构建而无法满足时，拒绝部署并指出服务及原因；不删掉字段后冒充原配置。Compose 提供 `--no-build` 作为禁止构建的原生选项，实际选用版本仍需验证。[Compose up](https://docs.docker.com/reference/cli/docker/compose/up/)

新配置部署失败可能已经产生部分资源变化，不自动宣称恢复旧版本。页面保留失败输入、错误与观察到的对象；最近成功版本仅作为历史依据。用户先核对当前状态，再修正配置并重试。镜像拉取和依赖检查也可能失败，错误定位到本次阶段，不能统一显示成“配置错误”。

### 启动、停止与移除

启动和停止作用于已存在的 Stack 运行资源，不隐含应用未部署的配置；如果资源尚未创建，引导用户执行部署。日常控制使用最近成功部署的项目身份和配置依据，不能拿当前未部署草稿决定要控制哪些服务。发生部分部署失败后，必须结合该次输入和当前资源重新核对范围。

| 用户动作 | 默认结果 | 需要另外选择的影响 |
| --- | --- | --- |
| 停止 | 停止现有容器，保留配置、容器和数据 | 不清理资源 |
| 启动 | 启动现有容器 | 不应用未部署配置、不构建镜像 |
| 重新部署 | 使用明确选定的已保存版本执行更新 | 拉取或重建等选项及已知影响在提交前显示 |
| 移除运行资源 | 移除该项目的容器及原生 Compose 对应网络，保留管理配置 | 删除卷必须另行选择、授权和确认；默认不删镜像 |
| 解除配置管理 | 删除或解除管理器中的配置关联 | 运行资源继续存在；先说明后续配置维护能力会失去 |

“删除 Stack”入口应先让用户选择以上实际动作，不把运行资源、管理配置和数据删除捆成一个不明后果的按钮。删除数据需要列出具体卷及已知使用关系；关系未知不等于未使用。外部卷和网络不随 Compose down 自动删除；匿名卷即使保留，也不能保证后续 up 自动重新挂载。绑定目录不由 Stack 删除流程递归清理。[Compose down](https://docs.docker.com/reference/cli/docker/compose/down/)

涉及同一资源的容器操作和 Stack 操作也需要协调，不能通过另一个入口绕过冲突控制。用户在管理器之外执行 Docker 命令仍可能造成竞争；重新读取状态并显示 Docker 实际结果，不承诺独占主机。

## 六 Node Cross 迁移与独立配置复用

### 操作意图

| 操作 | 用户期望的结果 | 来源处理 |
| --- | --- | --- |
| Node Cross | 将部署位置迁移到目标节点，执行后验证 | 来源退出迁移后的活动部署角色；验证通过后由用户选择是否删除 |
| Copy | 在目标保存一份独立配置 | 不改变来源配置或运行状态，两端后续独立 |
| Apply | 将选定配置部署到明确目标，复用第五节 | 不隐含来源切换、删除或数据搬运 |

Node Cross 的迁移含义及迁移后验证、可选删除已由用户确认。Copy、Apply 是与之分开的操作概念，最终按钮名称可调整。PVE 是迁移意图的参照，本稿不由此承诺热迁移、内存状态转移或零停机。

### 迁移与验证

迁移流程需分别呈现准备、执行、验证和来源处置的结果。以下给出行为边界；存储搬运、切换顺序和失败回退的完整机制仍待后续设计，不以这些阶段名称表示已经完成技术设计。

1. **准备。** 固定来源与目标、配置版本及迁移范围，列出目标名称、路径、外部依赖和数据准备要求。明确本次是迁移；目标已有同名项目时要求解决冲突，不隐式覆盖。准备配置本身不能停止来源。
2. **执行迁移。** 按已确定并展示的切换方案处理两端，使目标达到预期部署状态，来源退出相应活动部署角色。来源停止、目标启动及数据处理的先后不在存储方案未定时预设；不能把现有 Copy 加一次 Apply 当作完整迁移实现。
3. **迁移后验证。** 执行结束后进行单独验证，展示配置与资源是否符合所选输入、目标运行状态、可检查的依赖、来源切换状态及需用户确认的业务项目。验证记录绑定本次迁移和实际检查对象，注明检查时间、证据及范围；用户声明已准备数据不等于管理器验证过数据完整性。
4. **选择来源处置。** 验证通过后展示保留与删除选项。保留不自动重启来源，也不形成 Copy 的双份部署；删除列出具体配置、运行资源及持久数据范围，按第五节规则确认与授权。用户未选择时不删除。持久数据删除不得隐含在普通来源清理中。

执行成功但尚未验证时显示“迁移执行完成，待验证”；验证失败或结果未知时不允许进入来源删除。迁移已验证通过但用户选择保留来源，可以报告“迁移已验证，来源保留”；用户选择清理后单独显示清理结果，清理失败不被隐藏，也不把迁移历史改写为从未发生。

验证后若两端配置或相关资源发生变化，不能直接沿用旧验证结论执行删除；需要重新核对影响并取得相应选择。失联时保留阶段和结果未知状态，先核对两端，再决定继续或回退；不自动启动来源或删除目标来假装事务回滚。管理器之外的操作仍可能改变节点状态，验证不承诺持续独占节点。

### Copy 内容与步骤

用户从来源 Stack 发起复制，默认选择当前已保存版本，并明确显示它是否为最近成功部署版本；用户也可选取可用的最近成功版本。未保存的编辑内容需要先保存。来源运行状态与配置复制分开判断：完整配置已在管理器保存时，可以从离线来源准备复制；需要从来源补取的文件则不能假装已经取得。

1. 检查来源配置读取权限，列出所选版本、受管理文件和外部依赖。
2. 用户选择有配置维护权限的目标节点，输入目标 Stack 名称和实际项目名。只有具备目标部署权限时，才提供后续部署动作。
3. 建立目标预览，保留原始文件、目录关系和输入顺序，让用户调整变量、绑定路径、端口、容器名和外部依赖。来源内容不会随预览编辑改变。
4. 检查目标实际项目名及已知资源冲突。目标已有同名项目时，本稿采用改名新建或退出，不提供隐式合并、接管或覆盖；固定 `container_name`、端口、外部资源名称仍需单独处理。
5. 提交前展示最终文件与输入、尚未验证的依赖，以及“本次只复制配置，未复制运行数据”。说明目标配置按目标节点的配置读取权限开放，可能对另一批获准用户可见。需要旧数据时，用户可先保存目标配置，手动准备数据后再部署。
6. 提交复制时重新检查两端所需权限，并在目标建立独立配置。来源版本若已变化，说明本次使用的旧版本，允许重新取最新内容或明确继续该版本。
7. 用户通过 Apply 按第五节部署目标并查看结果。复制保存成功与目标部署成功分别记录；目标失败时保留配置供修复，来源仍不被停止、修改或清理。这两步不报告为 Node Cross 迁移成功。

重复点击或网络重发同一次复制提交，应返回已创建目标的记录；用户另行发起一轮复制则重新检查名称和权限。复制创建与部署是两个可分别恢复的步骤，不允许重试部署时再偷偷新建另一份 Stack。

### 配置复用与迁移的数据边界

| 内容 | 当前处理 |
| --- | --- |
| 受管理 Compose、环境及附属运行文件 | 随选定版本复制，包含原文中的敏感值；需要对应读取权限 |
| 管理器中的仓库或连接凭据 | 不复制密码和授权；在目标重新选择获准使用的凭据引用 |
| 镜像 | 保留镜像引用，按目标原生拉取行为处理；不承诺跨节点传镜像或标签内容不变 |
| 外部网络、卷、绑定路径和远端服务 | 列为目标依赖；名称相同不代表内容已复制或依赖独立 |
| 卷和绑定目录的运行数据 | 当前不自动复制；用户可手动打包、传输和恢复 |
| 自动化存储迁移 | 保留 R15；存储类型、停机、一致性、进度和恢复机制暂缓设计，迁移验证及来源处置遵守 R07 |

Copy 后的独立性指配置维护与部署动作独立。两端仍引用相同数据库或远端存储时，业务数据可能继续共享；目标预览应帮助用户检查这类引用。迁移需要沿用这些依赖检查，但成功条件还包括切换和迁移后验证。用户标记“数据已自行准备”仅表示其确认，不能显示成管理器已验证数据完整，也不能据此标记迁移验证通过。

## 七 Docker 资源管理与已有项目

### 容器和诊断

容器列表提供名称、镜像、状态、所属 Stack、可取得的端口和健康信息。概览不返回环境值等完整配置。创建独立容器时，用户选择镜像并填写名称、端口、环境、挂载、网络、重启策略、用户、工作目录和启动命令；提交前显示实际输入，执行 Docker 原生校验。创建不会暗中生成一个 Stack；希望持续维护 Compose 的用户可走第八节。

启动、停止、重启和删除显示节点及容器；不能把“停止”默认为删除。删除运行中的容器需明确停止或强制的实际影响。Stack 所属容器直接控制后刷新 Stack 状态，但不回写 Compose；后续重新部署仍按配置执行。容器日志、统计与控制台分别受权限控制，失联显示流中断和最后更新时间；重连不重放此前控制台输入。控制台关闭不表示容器停止，也不保证已启动的进程退出。

### 镜像、网络和卷

镜像显示标识、标签、大小和可取得的使用关系；拉取输入包含镜像引用与获准的凭据。标签操作区分新增引用和删除引用，不能把删掉一个标签表述为镜像内容必然释放。删除与清理展示范围，执行前检查当前使用关系并保留 Docker 最终拒绝信息。不会自动扩展成 Build、镜像导入导出或仓库托管服务。

网络与卷提供列表、详情、创建和删除。创建表单支持名称、所选原生驱动及其参数，网络按需提供子网等原生输入，卷不新增文件浏览器。未知驱动或不支持参数明确反馈，不能偷偷改为另一驱动。列表标出可识别的 Stack 或容器关联；删除规则复用第五节的数据与资源区分。清理候选项可能变化，不能把预览当作执行时的绝对保证。

### 发现与接管

接入已有节点后，先显示观察到的 Docker 资源；根据可用 Compose 标记关联项目，但不宣称已取得完整原始配置。原始文件不可得时，显示“配置来源不完整”，仍按权限提供可确定的资源查看和控制，不从运行信息静默还原一份所谓原配置。

接管流程由用户选择项目、提供 Compose 及必要运行文件和输入，再检查实际项目名、资源关联及已知差异。无法验证的项目明确标注；发生冲突时先解决，不能默认接管同名但无关资源。确认接管仅建立管理关系，不启动部署、停止或重建。首次部署继续执行第五节的影响确认，不能以“接管成功”证明配置与当前资源完全一致。项目关系不明确时，保留资源级管理即可。

## 八 docker run 转 Compose

### 输入与处理流程

转换工具面向已登录用户，只处理文本，不要求节点执行权限。首期建议支持一条 Unix shell 风格的 `docker run` 或 `docker container run` 命令，识别普通引号、转义、反斜杠续行及常见短选项组合；不支持任意脚本、管道、重定向、命令串联或自动执行 shell 展开。出现无法可靠分词的输入时，定位原因并要求修正，不猜测后继续输出“转换成功”。

处理分为解析、参数映射、结果检查和编辑。输出同时显示 Compose、已映射项、需要用户补充的依赖，以及不能转换的选项或语义差异。未知选项无法确定是否携带参数时停止完整转换，避免把后面的值错当作镜像。可显示已确定的片段，但必须标为不完整，不能直接进入部署。

输入中可确定为字面量的 `$`，在 Compose 输出中按插值规则转义；需要宿主 shell 展开的变量、命令替换、通配符或当前目录，不能使用管理器机器的环境代入。提示用户填具体值或明确改成 Compose 变量。原文和结果可能含密码，默认不写入通用操作日志；只在用户保存为 Stack 后按配置权限保存。[Compose 插值](https://docs.docker.com/reference/compose-file/interpolation/)

### 建议支持清单

下表规定功能映射目标，具体语法测试由转换实现的支持清单维护。仅出现 YAML 字段不代表已经证明两种启动方式完全等价。[Docker run 参数](https://docs.docker.com/reference/cli/docker/container/run/)、[Compose service 定义](https://docs.docker.com/reference/compose-file/services/)

| run 输入 | Compose 输出或反馈 |
| --- | --- |
| 镜像、`--name` | `image`、`container_name`；生成可编辑的 service 名，提示固定容器名可能冲突 |
| `-p`／`--publish`、`--expose` | `ports`、`expose`，保留主机地址、端口范围和协议，不把 expose 当作发布端口 |
| `-e`／`--env` | `environment`；保留空值与具体值区别，只有名称未给值时要求明确变量来源 |
| `--env-file` | 建立待核对的文件引用，提示上传或准备文件并核对解析差异；不能仅改成 `env_file` 就认定等价 |
| `-v`／`--volume`、`--mount` | 按类型生成 `volumes` 或适用配置，保留只读等支持选项；未支持子选项逐项报告 |
| `--network`／`--net` | 内置 bridge、host、none 用 `network_mode`；既有自定义网络用显式名称及外部网络引用；复杂附加参数未覆盖时报告 |
| 未指定网络 | 建议显式生成 `network_mode: bridge`，保留 run 的默认桥接意图；说明改用 Compose 默认项目网络会改变行为 |
| `--restart`、`-u`／`--user`、`-w`／`--workdir` | 对应 `restart`、`user`、`working_dir`，参数值先验证支持范围 |
| `--entrypoint` 和镜像后的命令参数 | `entrypoint`、`command`，保留解析后的参数边界，不拼接成待执行 shell 字符串 |
| `-i`／`--interactive`、`-t`／`--tty` | `stdin_open`、`tty`；说明 Web 部署不会自动附着终端 |
| `-d`／`--detach` | 作为原命令的执行方式说明，不生成虚假的 YAML 字段 |
| `--rm`、附着方式或其他未覆盖选项 | 报告生命周期差异或未转换项，不静默丢弃；有差异时结果保持“待处理” |

run 的环境文件与 Compose 的 `env_file` 在行内注释、引号和插值方面存在差异。例如 `VALUE=hello # world` 不能在转换后悄悄丢掉值的一部分。未取得并核对文件内容时，结果保持待处理，保留原文件；可在适用版本使用 `format: raw` 等方式保留值，但必须通过支持清单中的差异样例，不能把它当作未经验证的通用修复。[run 环境文件](https://docs.docker.com/reference/cli/docker/container/run/#set-environment-variables--e---env---env-file)、[Compose env_file](https://docs.docker.com/reference/compose-file/services/#env_file)

命名卷必须保留实际名称，避免自动变成带 Compose 项目前缀的另一份卷。本稿建议对原命令引用的命名卷生成 `external: true` 和明确 `name`，并提示目标必须先存在该卷；用户想新建时显式改成由 Compose 管理。这是选择保留已有数据引用的转换策略，不能说与 run 在卷不存在时的创建行为完全相同。[Compose 卷名称与外部卷](https://docs.docker.com/reference/compose-file/volumes/)

自定义网络同样保持实际名称并要求目标已有；不把它替换成一个新项目网络。未指定网络时生成 bridge 是本工具的映射建议，不改变用户手写 Compose 仍按其原生默认网络处理的规则。[Compose 网络定义](https://docs.docker.com/reference/compose-file/networks/)

### 结果的使用

用户可以复制或下载结果，也可带入新建 Stack 编辑器。转换工具不连接节点执行命令、不自动创建资源。对于未解决变量、缺失文件和语义差异，显示具体待处理项；用户修改后可以继续编辑草稿，部署仍需完成第四、五节校验。确认看过提示不能代替补全必需输入。

例如，`docker run -d --name web -p 8080:80 nginx:alpine` 应得到含相应镜像、名称、端口和明确 bridge 网络模式的单 service 草稿，并说明 `-d` 属于运行方式。带有 `--rm` 的同类输入则必须额外显示自动删除语义未保留，不能得到同样的无提示结果。示例是预期行为，不代表转换器已经实现。

## 九 操作状态与恢复

管理动作有可追踪的操作记录，至少包含操作者、节点、对象、动作、提交时间、配置版本或输入摘要、阶段、结果及可供核对的错误。原始命令和完整环境值不自动记入普通摘要。操作记录能从对象页找回，页面关闭或刷新不等于任务被取消。

| 状态 | 含义 | 用户可以做什么 |
| --- | --- | --- |
| 已接受，尚未开始 | 请求已记录，尚未开始对节点执行 | 查看前置条件；仍能保证未开始时可取消 |
| 执行中 | 正在执行本次操作 | 查看阶段与受权限保护的输出；不把关闭页面当成取消 |
| 已成功 | 已取得该动作定义的成功结果 | 查看运行状态；不据此推断业务健康或数据迁移完成 |
| 已失败 | 已确认错误，可能有部分副作用 | 查看对象现状和错误，修正后显式重试 |
| 结果未知 | 失联或恢复后无法确认是否执行完成 | 先重新连接、检查对象和可取得的执行记录；不得盲目重发 |
| 已取消 | 已确认该次请求未开始，或所支持的取消步骤已结束 | 查看取消范围；当前不承诺撤销已开始的任意 Docker 操作 |

已接受可进入执行中、失败或未执行取消；执行中可进入成功、失败或结果未知。重新获得可靠结果后可将未知更新为实际结果并保留核对依据；仅看到对象存在不能证明整个操作成功。无法确认时继续标未知，并允许有权限的人留下人工核对说明，不能伪造成功。

重复提交同一次请求返回既有操作；用户明确重试是新操作，并关联原记录。操作期间失联时保留未知状态，恢复后核对；对状态未知且可能仍在运行的冲突动作暂不允许直接启动第二次。管理员核对和解除占用的具体证据与接口在架构设计中补全，不能只靠超时宣布完成。

当前仅保证执行前的取消；执行开始后如无已验证的中断语义，不提供“取消且回滚”的承诺。用户需要停止应用时，应在确认现状后使用对应控制动作。

## 十 管理数据备份与恢复

系统管理员能够备份账号及授权、节点记录、分组标签、Stack 配置及部署关联、仓库与连接配置，以及恢复所需的凭据保护材料。文件中的敏感内容和密钥如何一起安全恢复，由数据与架构设计确定；不能只备份一张数据库而遗漏受管理文件或必要密钥。

备份界面显示覆盖范围和生成结果。恢复前检查备份可读性、版本及目标管理器状态；恢复可能替换管理信息，必须展示范围并防止与正在运行的管理任务并发修改。具体替换与兼容策略在数据设计落实后形成可执行步骤。

恢复管理数据不会自动重新部署或清理应用。节点连接、资源身份及任务结果需要重新核对，旧“执行中”记录不能恢复为新的无条件执行命令。应用卷和绑定目录的备份不包含在管理器元数据备份成功中；存储迁移继续按 R15 暂缓。

以下是文档走查和后续测试设计的输入；软件尚未实现，表中结果不是测试通过记录。

| 场景 | 必须可观察的结果 | 覆盖需求与章节 |
| --- | --- | --- |
| 登录后管理约 20 个混合网络节点，一个离线 | 仅显示授权节点，离线数据带时间，其他节点可操作，节点数量不被硬限制为 20 | R01、R02、R03、R14；第二、三节；Q01、Q03、Q09 |
| Web 创建含多文件和环境配置的 Stack | 输入来源和文件顺序可见，保存后可重开，使用原生规则；缺失依赖不能伪装齐全，已有同名项目不得被普通新建流程更新 | R04、R06、R12；第四、五节；Q02、Q06、Q07 |
| 两名编辑者先后保存同一版本 | 第二次保存提示冲突，已保存内容不被静默覆盖；解决后另行提交 | R04；第四节；Q05 |
| 新配置保存后部署失败 | 草稿、最近成功部署版本和失败操作分别可见；已有资源按实际观察展示 | R05、R13；第五、九节；Q02、Q04 |
| 来源离线但完整配置已保存，Copy 到目标 | 可准备独立目标，现场读取依赖明确不可用，来源不变；不报告迁移成功 | R17；第六节；Q01、Q02、Q04 |
| 目标同名或固定端口冲突，Copy 提交被重复发送 | 同次提交不创建两份目标，不覆盖既有项目 | R17、R13；第六、九节；Q04 |
| 来源可读但目标不可部署，或 Copy 中撤权 | 各阶段授权、执行与输出访问不绕过权限 | R17、R11；第二、六节；Q03、Q07 |
| Node Cross 执行完成后验证未通过或状态未知 | 显示阶段与证据，不进入来源删除，不盲目回退或制造双端活动部署 | R07、R11；第六节；Q02、Q04、Q10 |
| 迁移验证通过后用户保留或删除来源 | 选择与范围可追踪；保留不自动启动，清理独立授权与报告，相关状态变化后重新核对 | R07、R10、R11；第六节；Q03、Q10 |
| 用户手动准备目标业务数据 | 区分用户确认与检查证据，不声称验证了数据完整，不绕过迁移后验证 | R15；第六节；Q10；自动搬运用例暂缓 |
| 直接请求受限配置、日志或控制台 | 后端拒绝；普通概览不能成为取得秘密的旁路 | R08、R11；第二、七节；Q03、Q07 |
| 清理镜像、移除 Stack 或卷 | 对象与影响明确，持久数据删除单独选择并授权，未知关联不视为无关联 | R05、R09、R10；第五、七节；Q01、Q04 |
| 接管配置来源不完整的已有项目 | 能查看已知资源，缺失输入需补齐，接入和接管不自动部署 | R12；第七节；Q02、Q06 |
| 转换含引号、变量、挂载、环境文件或不支持选项的 run 命令 | 不执行输入；参数边界、缺失依赖和语义差异可见；含行内注释等环境值不得静默改变，结果经用户处理再部署 | R16；第八节；Q07、Q11 |
| 任务中断后重连，或管理数据恢复 | 区分失败与未知，不盲目重发；恢复配置与节点资源核对后再操作 | R13；第九、十节；Q04、Q08 |

实际测试需补充节点环境、Compose 版本、资源量及并发用户。Linux、FreeBSD 等 Unix-like 背景按可用 Docker CLI／Compose 与目标 Docker 的实际组合验证，不把平台名称本身当作已完成兼容证明。

## 十二 设计选择与后续衔接

| 事项 | 本稿处理 | 后续动作 |
| --- | --- | --- |
| 多人使用的信任边界 | 用户已确认可信运维人员协作，按节点和操作授权；不提供同节点不可信租户强隔离 | 架构落实身份、授权与节点连接边界 |
| 节点分类 | 建议平级单分组、多标签，不隐式授权 | 用户可随审阅调整；数据设计落实关系 |
| 账号与授权 | 建议本地账号、节点范围与动作组合，提供便利模板 | 架构展开会话与授权执行；具体动作在接口设计统一 |
| 配置与运行分离 | 建议版本检查、保存不部署、操作固定输入、冲突动作不并发 | 架构与数据设计落实执行协调、快照与历史保留 |
| Copy 冲突 | 建议独立新建，冲突改名或退出，不直接覆盖目标 | 接管走独立流程，Apply 沿用部署规则 |
| Node Cross | 已确认迁移后验证，通过后由用户选择是否删除来源；本稿展开阶段与权限边界 | 补全切换、验证项目与回退；存储搬运机制继续暂缓，不能沿用 Copy 成功条件 |
| 命令转换 | 建议有限 shell 语法与显式支持清单，差异必须可见 | 后续建立参数及语法测试样例，不承诺任意脚本转换 |
| 节点连接与执行位置 | 用户已确认 Agent 主动连接管理端；保留原生 Compose 和 Web 文件管理要求 | 架构说明展开节点执行位置、通信与配置存储 |
| 数据、接口和运维细节 | 本文确定可见行为，保留记录格式、保留期限和备份兼容策略的设计空间 | 按文档实施方案依次展开；不借未定细节改变产品行为 |
