# Docker Manager 部署与运维

日期：2026-11-02。版本：0.1。状态：待审阅。本文是部署设计与待验证操作流程；项目目前只有文档，没有应用发布包、安装脚本或可执行的管理恢复入口。本文不代表已经验证的安装手册。

Docker Manager 的运维对象包括 Manager、节点 Agent、管理数据、身份凭据与任务记录。应用容器和业务数据由各自 Docker 环境运行和保存。维护管理器时，应能说明哪些管理能力暂时不可用、已有操作如何处理，以及应用是否受到影响。

本文面向安装和维护人员，依据[架构设计](architecture.md) v0.3、[数据设计](data-design.md) v0.3、[接口设计](api-design.md) v0.1 和[测试与验收](test-plan.md) v0.1。可信运维协作、Agent 主动接入及迁移后验证与可选来源删除沿用用户已确认要求；单实例部署、服务形态和具体运维机制仍属设计建议。

## 一 使用本手册的前提

流程 O01—O10 给出前提、操作次序、预期结果及失败处理。实际执行前，所用版本必须提供下面的发布清单，并用该版本的命令、界面或本机入口替换逻辑操作说明。本稿不编造程序名、下载地址、镜像标签、服务名、默认端口或环境变量。

| 发布时必须提供 | 需要能确认的内容 |
| --- | --- |
| Manager 与 Agent 发布物 | 构建标识、获取来源、完整性校验、支持的 OS／架构和部署形态 |
| 安装与服务文件 | 安装、启动、停止、重启、日志查看和卸载方式，所需运行身份及权限 |
| 配置参考 | 实际参数名、格式、默认值、单位、允许范围、修改后何时生效及秘密交付方式 |
| 兼容清单 | Manager／Agent 协议、数据结构、Docker CLI／Compose／Engine 的已验证组合 |
| 管理和恢复入口 | 初始化引导、维护模式、身份替换、备份检查、本机恢复与账号恢复的入口和权限 |
| 更新说明 | 支持的升级路径、预期中断、结构变更、回退条件及相应备份要求 |
| 验证记录 | 对应构建的安装、接入、升级、备份恢复与故障测试结果 |

目前这些项目仍待实现和验证。普通 Docker 诊断命令在第二节单独列出；它们只能检查已有 Docker 环境，不安装或启动本项目。

## 二 部署位置 网络与环境准备

### 部署形态

| 位置 | 部署内容 | 运行条件 |
| --- | --- | --- |
| Manager 主机 | 一个活动 Manager，可内置 Web 静态文件，配合直接 TLS 或反向代理入口 | 浏览器和所有 Agent 可达；管理数据库、配置内容、密钥材料及记录可持久保存 |
| 节点执行环境 | Agent、可用 Docker CLI 和 Compose、明确目标 Engine 的受控访问 | Agent 可主动访问 Manager；运行身份能读取任务输入、写管理工作目录并操作该 Engine |
| 浏览器 | Web 管理界面 | 能访问 Manager；不保存唯一配置副本，不直接访问 Docker socket 或 Agent 凭据 |
| 外部依赖 | 镜像仓库、网络、存储和应用服务 | 节点按应用配置访问；管理端可达不代表这些依赖可达 |

建议 Agent 先作为 Unix-like 系统服务运行；具体服务管理器随实际支持平台选择。容器化 Agent 需要另外验证 CLI、Agent 文件路径与 daemon 挂载路径一致，再列为支持形态。Linux、FreeBSD 等按实际 CLI／Compose 与 Engine 组合验证，平台名称本身不是兼容证明。

Manager 默认放在独立可信环境。与受管节点共享宿主机时，具有该宿主机任意部署能力的人员也须被信任管理整套基础设施；目录或进程分开不能提供额外的主机隔离。同一宿主机上的多个 Node ID 同样不产生独立安全边界。部署时记录真实的信任范围，节点权限仍由 Manager 检查。

### 通信检查

| 路径 | 准备与验证 |
| --- | --- |
| 浏览器 → Manager | 确认访问地址、TLS 信任、身份认证、请求大小和流式连接；若用代理，校验原始来源和转发配置 |
| Agent → Manager | 从 Agent 实际运行网络验证 DNS、路由、端口和证书；连接方向主动向外，无须假定节点有公网管理入口 |
| Agent → Engine | 固定目标 endpoint 或 context 及认证方式，确认实际 Engine 身份；不要依赖某个登录用户后来切换的全局 context |
| 节点 → 仓库及外部依赖 | 按实际配置检查所需访问、凭据用途和依赖状态，不把未知显示成已就绪 |

Agent 不要求 A 与 B 直接互通。Node Cross 的未来数据传输路径尚未设计，不能从现有管理通道推导数据已经能跨网搬运。完全无法访问 Manager 的节点，需要先由部署方提供这一方向的网络路径。

协议仍待定稿；若采用 WebSocket，反向代理需要正确处理升级、长连接与超时，并在大输出下保证控制消息不被阻塞。代理限额应与应用和 Agent 的有效限额一致，不能只调大代理超时掩盖任务恢复问题。

### 现有 Docker 环境的只读诊断

在拟运行 Agent 的身份、环境和目标连接参数下，可逐条执行：

```sh
docker version
docker compose version
docker context show
```

记录 CLI、Compose 和 Server 端信息；只有 Client 输出时，继续检查 Engine 的可达性或权限。context 名称只是连接线索，实际目标仍须由 Agent 的 Engine 身份观察核对；若部署使用明确的 context／host 参数，上述诊断也应指向同一目标。[Docker version](https://docs.docker.com/reference/cli/docker/version/)、[Compose version](https://docs.docker.com/reference/cli/docker/compose/version/)、[Context show](https://docs.docker.com/reference/cli/docker/context/show/)

这些检查不验证稳定工作目录、文件挂载和应用部署。首次环境验收还需要测试计划 T10—T12 的实际文件与原生行为对照；使用远端 Engine 时尤其要核对文件在哪台机器、daemon 能看到哪条路径。

## 三 持久数据和目录规划

以下名称是目录角色，不是已实现的路径或配置键。安装记录须把每个角色映射到实际绝对路径、存储设备、运行身份和备份责任。

| 目录或数据角色 | 保存内容 | 生命周期与保护 |
| --- | --- | --- |
| Manager 管理库 | 账号授权、节点、版本引用、操作、审计和恢复记录 | 由活动 Manager 管理，不能多实例未经协调写入 |
| Manager 配置内容库 | 不可变 Compose、环境和附属运行文件 | 与数据库引用一起备份；物理去重不改变读取权限 |
| Manager 密钥和部署配置 | 凭据解密材料、TLS／信任配置、运行配置 | 限制访问，记录恢复所需版本；不将明文秘密写入通用日志 |
| Agent 身份与任务目录 | 节点身份、连接材料、持久任务、事件、结果与本地占用 | 升级和普通重启必须保留；复制到另一运行 Agent 不能作为接入方式 |
| Stack 稳定工作目录 | 明确受管理的部署文件及实际项目目录 | 不随 revision 改变；配置落地清单与业务数据分别处理 |
| 暂存与输出 | 上传、任务临时认证环境、解析暂存和受限输出 | 有限预算及明确清理条件；不能删除活跃或未知任务的必要证据 |
| 应用业务数据 | 卷、绑定目录或外部服务数据 | 单独制定备份与恢复方式，不属于管理库备份 |

不要把受管理文件同步理解成清空整个工作目录。配置和可写业务目录混放时，部署前识别覆盖冲突；未列入管理清单的业务文件不能被“整理目录”递归删除。

接管已有项目时保留经核对的原目录和项目身份。改变目录或挂载路径需要显式验证；仅移动 Manager 的配置归档，不会迁移节点业务数据。迁移 Manager 主机时也须同时处理运行配置、密钥与完整内容引用，不能只带走数据库文件。

## 四 首次安装和节点接入

### O01 建立 Manager 与首位管理员

**前提：** 有适用版本的发布清单、可信安装来源、确定的访问地址和持久路径；操作者拥有部署主机控制权。尚无这些发布物时，本流程用于实现与验证准备。

1. 记录本次部署的构建、系统、访问地址、运行身份和目录映射，确认不存在另一个仍有执行权的活动 Manager。
2. 安装匹配的 Manager 发布物及所需依赖；按实际运行身份创建和检查持久目录的访问条件，保存部署配置与密钥材料的恢复方式。
3. 配置浏览器和 Agent 可到达的入口、TLS 信任与代理，并核对第十二节所列的限额类别；实际端口和参数以版本配置参考为准。
4. 启动 Manager，先检查进程、存储可读写和初始化状态。未初始化时，仅通过部署侧受控的一次性引导材料或等效本机入口创建首位管理员。
5. 正常登录，确认初始化入口已关闭，首位管理员存在且没有默认开放所有节点动作；节点授权随后按实际需要设置。
6. 检查退出与重新登录、管理配置持久性及日志脱敏。完成后记录 installation 标识、构建与初始化时间，秘密材料单独保管。

**预期结果：** 一个可认证访问、可持久保存管理信息的 Manager，尚未接入节点时不虚构节点可用状态。

**失败处理：** 初始化响应丢失时先检查初始化状态并尝试正常登录，不重复清空数据库或重新开放引导。存储或密钥初始化不完整时保留错误阶段，修复后核对；不能以每次重启重建空库的方法处理启动故障。

### O02 接入一个 Agent 节点

**前提：** Manager 可用；管理员有节点管理权；已验证 Agent 到 Manager 以及 Agent 到目标 Engine 的访问。安装者有权在实际执行环境配置运行身份和持久目录。

1. 在 Manager 建立待接入节点，记录 Node ID、名称及预期 Docker 目标。签发限时、一次性且限定该节点的注册材料。
2. 在节点安装适用 Agent、CLI 和 Compose；固定 Engine 目标与实际工作目录，配置 Manager 地址及服务端信任，不跳过证书校验。
3. 通过版本支持的受保护方式交付注册材料，启动 Agent。注册成功后确认产生独立身份和连接凭据，原注册材料已消费。
4. 核对 Manager 中的 Agent 身份、Engine 身份、连接代次、Docker／Compose 版本与能力，确认不是同名但不同的环境，也不是重复纳管。
5. 先查看现有资源与连接状态。已有 Compose 配置缺失时保持“配置来源不完整”，不要因接入就接管、重建或部署。
6. 分配节点与动作权限。在专用测试对象上完成获准的查询、保存、Apply 及断线恢复检查，再把已验证组合列入支持记录；日常业务不作为首次破坏性测试对象。

**预期结果：** 节点身份和目标已核对，能力与权限可见；Agent 主动接入，接入本身没有修改既有应用。

**失败处理：** 注册返回丢失、材料已消费时，管理员检查并撤销孤立身份，再签发新材料；不能仅凭 Node ID 重新取回秘密。连接成功但 Compose 或 Engine 不可用时分别处理，不显示“可部署”。Engine 改变或疑似重复身份时先停止开放新变更，按 O08 核对。

## 五 日常维护 身份和凭据

### O03 检查运行状态及进行普通重启

**前提：** 已能取得管理端、节点和操作记录；操作者有相应诊断及维护权限。

1. 先检查 Manager 是否可认证访问、持久存储是否正常、各节点最后观察时间及是否有 unknown 操作。区分“进程存活”“节点连接”“Engine 可用”和“应用健康”。
2. 检查新请求拒绝、控制及输出队列、磁盘余量、暂存和日志增长、未确认结果、备份完成时间、证书和凭据有效性。阈值使用已部署版本配置和负载基线。
3. 需要重启时，使用待实现的维护入口暂停受影响范围的新变更受理与开始许可，保留查询和结果回传。等待已开始操作结束；无法结束的任务先核对处置，不通过强杀假定它们未执行。
4. 使用所部署版本的服务控制方式重启，保留原持久目录、身份和任务记录。普通重启不换 installation 或 recovery，不重新注册已有效的 Agent。
5. 重启后先核对任务、占用和实际目标，再恢复该范围的新操作；对未知任务按 O08 处理。刷新资源观察并保留真实采集时间。

**预期结果：** 原配置、身份和历史仍在，操作没有因重启自动重做；管理端短时不可用不被表述为应用已经停止。

**失败处理：** 若重启后出现空节点、空配置或重新初始化提示，先检查是否使用了错误目录、运行身份或挂载，不继续创建一套新身份覆盖原记录。应用本身是否继续运行由 Engine 观察确认；已批准的节点操作可能在 Manager 中断时继续完成。

### O04 调整权限 轮换凭据与改变接入地址

**前提：** 操作者有对应账号、授权、节点或凭据管理权；已记录受影响节点和未结束操作。

调整用户权限时展示节点和具体动作，提交后确认授权版本更新，受限订阅与终端输入被关闭。已经批准开始的动作按既定范围取得结果；后续新阶段与新请求使用当前授权。始终保留至少一个可用系统管理员。

仓库密码更新生成新值版本。先配置新版本及其节点／用途授权，用受控拉取验证，再按任务生命周期撤销或清理旧值；历史输入继续引用原版本，不能把等待任务静默改用新密码。若旧值疑似泄露，先撤销并接受依赖任务失败或需重试的结果，不为完成任务继续扩大发放。

Agent 凭据正常轮换与身份替换分开处理。轮换应保留节点与原任务身份，按版本提供的交接流程验证新凭据并撤销旧凭据；如果当前实现没有可靠交接能力，先暂停该节点新开始、处理未结束任务，再用受控本机安装流程替换。旧 Agent 不可控或疑似重复时先撤销并隔离旧执行者，再配对新身份；旧任务证据保留并显式关联。

改变 Manager 地址或 TLS 证书时，先验证各节点到新入口的路由和信任，更新受控部署配置，再检查重连与旧入口处置。地址变更不能让两台 Manager 同时获得控制权，也不能靠临时关闭证书验证完成迁移。正常地址或证书变更不自动改变 installation／recovery；若同时恢复备份则改走 O07。

**预期结果：** 新权限或凭据有效，旧控制能力按选择被撤销，任务及审计可追溯。

**失败处理：** 某节点无法使用新凭据时保持不可执行并核对，不能让多个有效身份反复抢占连接。连接材料丢失时使用受控替换，不从普通界面导出全部秘密。密钥轮换涉及已有密文解密能力，须保留仍被数据和备份引用的恢复材料；具体轮换工具待发布物提供。

## 六 更新和失败回退

### O05 更新 Manager 或 Agent

**前提：** 取得实际版本的兼容清单、更新说明、可验证发布物及当前可恢复备份。没有已验证的升级路径时，不把替换程序文件当作可支持升级。

1. 对照当前和目标构建、数据库结构、消息与文件格式、Agent 能力，确定升级顺序。根据兼容窗口选择 Manager 先行或逐节点先行，不预设所有版本都可混用。
2. 对 Manager 变更暂停新变更受理和开始许可；对单节点 Agent 变更暂停该节点，其他节点按其状态继续工作。等待活动任务完成，未知任务完成核对或明确保持受限。
3. 通过 O06 创建并验证升级前备份，另保留部署配置、密钥材料、旧发布物和版本清单。确认备份覆盖当前需要恢复的数据格式。
4. 停止待更新服务，保留数据和任务目录，安装目标版本。若涉及结构升级，记录每一步及成功状态；升级流程不能调用 Docker 重新部署应用，也不能把未知操作改成待重新执行。
5. 以维护状态启动，检查数据结构、内容引用、密钥解密和协议能力，先查询再核对未结束任务。Agent 更新后确认身份、Engine 和原任务键仍正确。
6. 通过适用 T32 及关键冒烟检查后，逐步恢复对应节点和用户访问；保存更新记录及残留不兼容项，不将未验证组合加入支持清单。

**预期结果：** 管理数据和任务历史可解释，已支持节点恢复操作；不兼容节点仍可诊断但不会收到不支持的动作。

**失败处理：** 记录失败阶段并保持受限。若数据结构或内容格式已经改变，旧程序未必能读取；只有更新说明明确支持原地回退时才沿该路径处理。否则隔离失败实例，使用兼容旧版本及升级前完整备份按 O07 恢复，生成新 recovery 并核对节点，不能直接把旧程序指向半升级数据。

回退期间节点可能已有比备份更新的操作或资源，恢复管理信息不回滚这些应用变化。需要修复应用时，先完成核对再创建新的明确操作，不自动重放旧命令。

## 七 管理数据备份

### O06 创建和检查可恢复备份

**前提：** 系统备份权限、可用备份功能、足够存储和明确保管位置；已区分管理数据与应用业务数据。备份频率、保留、可接受数据损失和恢复时间由使用需要及演练结果确定，本稿不填未经确认的数值。

1. 明确备份范围和当前构建，检查数据库、内容库、密钥材料和部署配置的所在位置。应用卷、绑定目录业务数据另行备份，不能以管理备份代替。
2. 使用版本提供的一致备份入口。实现应先建立持久准备记录，暂停可能破坏快照的内容回收，再取得数据库一致视图并固定其内容引用；不要手工在线复制单个数据库文件充当完整备份。
3. 等待复制和校验完成，取得 BackupManifest。核对数据库快照、被引用文件及摘要、数据和内容格式版本、installation／recovery、必要密钥版本及恢复方式。
4. 确认备份状态为可用，而非仅看到包文件存在；保存构建和部署配置。密钥可以受保护地单独保管，但必须能与备份清单对应且可取得。
5. 将备份放在访问受限、与被保护实例故障范围相区分的位置；验证下载权限和存储完整性，定期选择样本按 O07 在隔离环境演练。
6. 按保留策略清理过期备份；删除前确认相应密钥和内容是否仍被其他保留备份或恢复任务需要。备份任务释放占用不等于可以删除正常版本仍引用的配置文件。

**预期结果：** 一份有完整清单、内容与恢复材料的可用备份；是否能在所选环境恢复还需演练证据，管理备份完成不表示业务数据已备份。

**失败处理：** 生成中断时保留阶段，先恢复或明确终止该备份，再解除对应准备屏障和占用。不能仅因时间较久就直接清理被固定的文件。缺文件、摘要不符、密钥缺失或存储不足时标为失败／不可恢复，不覆盖最近可用备份；只清理本次可确认的临时产物。

### 备份范围速查

| 内容 | 管理备份处理 |
| --- | --- |
| 账号授权、节点、Stack、版本、操作、审计与恢复记录 | 保存一致视图；恢复后账号和权限须复核 |
| 被版本、输入或必要历史引用的配置文件 | 与快照清单一起保存，不能只备份当前编辑版本 |
| 加密凭据及所需密钥材料 | 保存可恢复关联，材料分开保护也须能共同取得 |
| 部署配置、信任材料及构建信息 | 作为重建环境的必要记录保留；实际秘密按权限保管 |
| 会话、旧注册材料、许可和观察缓存 | 即使出现在快照中，恢复后也作废或标为历史，不能恢复成当前控制能力 |
| Agent 本地任务与未确认结果 | 节点上保留以供核对；不是 Manager 配置主库的替代品，也不能假定管理备份已包含所有新结果 |
| 应用卷、绑定目录业务数据、外部数据库、镜像仓库 | 不自动包含，另按应用需要备份和恢复 |
| 浏览器未提交编辑、终端输入和实时流 | 不作为管理备份的恢复对象 |

## 八 管理数据恢复

### O07 从备份恢复并重新开放执行

**前提：** 有兼容的发布物、完整备份与密钥、受控的恢复主机及本机恢复权限。需要实际恢复工具、只读检查入口和节点重新配对流程；它们当前尚未实现，以下次序用于规定交付和演练要求。

1. **确定恢复目标。** 记录备份时间、构建、installation、原 recovery 和可能丢失的管理记录，保留当前故障数据及节点任务证据。先只读检查备份完整性、格式支持和密钥是否可用，失败则停止替换。
2. **隔离旧控制端。** 停止或可靠隔离原 Manager 及可能重启它的服务控制，阻止其继续签发许可；确认恢复实例不会与原实例同时控制节点。已获许可的 Agent 动作可能继续，需在后续逐项核对。
3. **在受限模式重建。** 在独立恢复位置导入数据库、内容、部署配置及必要密钥，检查对象归属、唯一约束、文件与摘要。普通用户访问和节点新执行保持关闭，不能用空文件或空密码补齐缺失内容后假装恢复成功。
4. **建立新恢复代次。** 生成新的 recovery，作废旧浏览器会话、未使用注册材料、连接凭据与旧开始许可。历史 Operation、AgentTask 和审计保留原创建标识；普通重启与这一步不同。
5. **恢复受控管理访问。** 本稿建议由具有恢复主机控制权的维护者通过一次性本机恢复会话进入检查，先复核备份中的管理员、账号状态和授权，防止较旧权限重新生效。该会话只用于恢复管理，不能把常规匿名初始化重新打开，也不能通过直接清空数据库字段重设管理员。
6. **逐节点重新核对。** 用受控安装／配对流程核实 Node、Agent、实际 Engine 和新的恢复代次，轮换连接材料，保持原 Agent 任务目录。收集全部未结束及未确认旧任务，包括备份中不存在的任务；保留为历史核对记录，不给旧任务换新标识再执行。
7. **核对绑定与序号。** 将 Agent 保留的已批准部署序号纳入恢复；不能从旧备份的小计数重新分配。范围不明则该绑定保持不可执行；经身份、旧任务和实际项目核对后，可按数据设计显式建立新绑定并保留旧历史，这本身不触发部署。
8. **重新观察应用。** 采集当前资源、工作目录和受管理文件差异，旧缓存保留原时间。应用可能比备份新，也可能仍在运行；管理恢复不自动回滚配置、重建容器或恢复卷中数据。
9. **逐步开放。** 对完成身份、任务、权限及内容核对的节点恢复新操作，对未核对节点继续限制；关闭一次性恢复会话，记录恢复结果、残留缺口和应用数据的另行恢复情况。验证稳定后生成新基线备份。

**预期结果：** 恢复实例是唯一活动控制端，旧控制材料失效，管理配置与节点实际状态之间的差异已解释；可执行范围只包含核对完成的节点和动作。

**失败处理：** 缺失文件、密钥或任务依据时保留具体缺口及受限状态。不能仅按显示名关联节点，不能仅凭容器存在判断旧任务成功。某节点旧执行者无法确认停止时，先在真实环境隔离或处置，再按 O08 核对；不要直接点击解除占用。

恢复过程中断后从恢复记录继续，不再次导入旧数据覆盖已取得的新证据。若决定放弃本次恢复，也必须确认哪一个实例拥有控制权及其凭据状态，再选择受支持的恢复路径；不能把旧 Manager 直接开回网络当作通用撤销办法。

## 九 故障定位与未知任务

### O08 核对未知操作而不重复执行

**前提：** 已有 Operation 或请求键信息，操作者有系统恢复及相应节点读取／控制权限。节点不可达时先保留信息，不以重装或清空任务目录代替排障。

1. 从请求键或对象历史找到原操作，记录原 task_key、固定输入、节点／Engine／binding、许可、连接代次、最后阶段及事件缺口。
2. 从当前可信 Agent 取得持久记录、许可接受情况、执行者实例和结果；PID 单独不足以证明同一进程。Manager 查无记录或 Agent 返回未找到，都需要检查备份时间、记录磁盘及身份是否发生变化。
3. 对照 Docker 资源与受管理文件的当前观察。文件落地本身可能影响已挂载配置，不能因为未见 Compose 完成就认定没有副作用；同名容器存在也不证明整项部署成功。
4. 有可靠结果时补报并持久确认，保留原事件键；结果确认丢失只重传结果。旧部署迟到成功只补历史，不能覆盖较新成功引用。
5. 无法取得可靠终态时保留 unknown。若需解除冲突占用，先确认旧执行者不再可能继续、旧请求已被排除，并保存处置与观察依据；再通过受控核对入口解除相应操作自己的占用。
6. 需要修复资源或重试时，由当前有权用户提交新的明确操作并关联原记录；保留失败及未知历史，不通过改写状态伪造原命令成功。

**预期结果：** 能取得可靠结果的任务得到归档，不能确定的仍明确未知；只有有证据的占用被解除，后续动作与原任务分开。

**失败处理：** 旧 Agent 不可控时先隔离执行者及控制路径；磁盘丢失时记录证据缺失。仅凭等待超时、清掉锁文件或强制修改数据库均不足以证明可以安全重做。

### 常见症状与检查顺序

| 症状 | 先查什么 | 处理与完成依据 |
| --- | --- | --- |
| Web 无法访问或反复登录失败 | Manager 进程、入口路由、证书、代理来源配置、存储、账号状态和时钟 | 修复对应入口或凭据；不要清空数据库重新初始化；正常认证及受限请求验证后结束 |
| Agent 离线 | 节点到 Manager 路由、DNS、TLS、代理超时、身份撤销及协议版本 | 逐层恢复，核对原身份和任务后再开放动作；不能将离线显示成零资源 |
| Agent 在线但无法访问 Docker | 服务运行身份、目标参数、Engine 认证、实际身份和能力 | 使用相同身份与目标诊断；不靠放开所有 socket 权限或切换到其他 context 掩盖问题 |
| Compose 找不到文件或挂载内容不符 | 文件包布局、项目目录、稳定工作目录、Agent 与 daemon 的真实路径、外部文件漂移 | 对照原始输入与实际挂载，显式修复；不移动业务目录使错误表面消失 |
| 预检被拒绝或缺少依赖 | structure／target 模式、部署和凭据使用权、完整预览读取权、目标依赖 | 按实际需要授权或补齐输入；不要让后台先读秘密再返回拒绝 |
| 复制成功但目标没有容器 | Copy 结果及是否另行提交 Apply | Copy 只保存独立配置；用户明确部署后再跟踪目标操作 |
| 迁移执行后不能删除来源 | 验证批次、结论、对象是否变化、用户选择与删除范围权限 | 完成有效验证和选择；失败／未知时不绕过来源保护 |
| 操作长期 running／unknown | 许可、两端任务、执行者、事件和结果确认 | 按 O08 核对；不自动重复部署或按超时清占用 |
| 大日志后界面卡顿 | 输出缓冲、慢消费者、控制队列、截断标记和磁盘 | 控制输出或关闭对应订阅，保留关键结果；不要扩成无界缓冲 |
| 管理或节点磁盘不足 | 正式内容引用、活跃任务、备份占用、输出和暂存策略 | 先限制无法可靠记录的新任务，按受控策略释放可清理内容；保留未知任务证据 |
| 备份一直生成中 | 准备屏障、快照、固定引用、目标存储和校验阶段 | 明确恢复或终止本次备份后释放其占用；不要按包是否存在判断可用 |
| 更新后数据或节点不见 | 数据目录、挂载、运行身份、结构升级状态和恢复记录 | 核对原数据与版本，不创建同名节点覆盖；失败按 O05／O07 处理 |

收集排障资料时记录构建、环境、目标与操作标识、阶段、脱敏错误、必要观察和重现步骤。秘密正文、完整环境、终端输入和未经审查的备份不进入普通故障报告；需要受限内容时按原权限单独提供。

## 十 移除节点和卸载

### O09 解除管理关系或停止使用管理器

**前提：** 操作者明确是解除管理、卸载程序，还是删除应用资源；已处理未结束和未知任务，并确定需要保留的管理记录和备份。

移除单个节点按以下顺序：

1. 暂停该节点新变更和开始许可，等待或核对正在执行的操作，保存必要结果与任务证据。
2. 在 Manager 解除节点关系，撤销其注册和连接能力；按明确选择保留离线历史或删除管理配置，记录影响。
3. 在节点停止并禁用 Agent 服务，确认没有遗留执行者仍在执行已批准任务。再按发布物说明卸载程序。
4. Agent 身份、任务目录、Stack 工作目录及业务数据分别列出处理选择。默认不把卸载解释为递归清空工作目录；已不再需要的敏感连接材料可按实际保留策略清理。
5. 从 Engine 核对应用和数据仍按预期存在，确认旧 Agent 不能再连接。以后重新接入使用明确的身份关联与接管流程，不仅凭同名自动认领。

停止使用整套 Manager 时，先对所有节点完成任务核对和控制权撤销，按需要导出可继续维护的原始配置及完整管理备份，再停止并禁用 Manager。应用后续由谁维护、原始配置与数据在哪里，需要有明确交接；卸载管理器不会自动执行应用 down。

**预期结果：** 被移除组件失去管理权，应用资源和数据的保留／删除与用户选择一致；有意保留的配置仍能找到。

**失败处理：** 节点暂不可达时可先撤销管理端控制材料并记录未完成的本机处置，但不能宣称其旧进程已停止。无法核对的任务和证据继续保留；删除工作负载属于另外的授权操作，不能夹带在卸载脚本中。

## 十一 跨节点操作的运维边界

### O10 区分配置复用和部署迁移

**前提：** 已明确此次意图、两端权限、所需配置和外部依赖；使用的版本能力清单说明实际支持哪些操作。

Copy 先保存目标独立配置，来源不变；检查目标路径、项目名、端口、外部网络／卷和凭据引用，再由用户明确 Apply。目标数据需要手动准备时，记录准备范围与用户确认；这不是管理器验证过数据完整的证明。

Node Cross 则要求部署位置切换，执行结束后验证，通过后再由用户选择保留或删除来源。来源配置、运行资源和持久数据的删除范围分别说明，保留来源不自动把它启动成第二份部署。验证过期、失败或未知时保持来源保护，清理失败单独记录。

**当前限制：** 切换顺序、存储搬运、一致性、业务验证项目和回退尚未定稿，当前不能给出可执行迁移操作手册。不要用“Copy、Apply、手工删来源”拼成已支持的 Node Cross；即使用户手动搬过数据，也仍需满足已支持迁移流程的验证与处置条件。

**失败处理：** 已明确的 Copy／Apply 问题按单节点配置和操作规则处理。未来迁移发生中断时，保存两端阶段与证据，按最终方案核对；不盲目重启来源或删除目标作通用回退。

## 十二 配置与保留参考

以下是发布配置必须覆盖的项目清单，实际键名、文件格式、默认值和热更新方式待实现定稿。使用者从版本配置参考填写，不将本表名称当成可直接使用的环境变量。

| 配置类别 | 范围与含义 | 定稿及核对要求 |
| --- | --- | --- |
| 监听与外部访问地址 | Manager 监听、浏览器入口、Agent 入口、代理信任范围 | 区分内部监听与对外地址；端口、TLS 和转发来源匹配实际部署 |
| 数据与工作路径 | 管理库、内容、密钥、Agent 记录、稳定工作目录和暂存 | 明确绝对路径、权限、磁盘预算；改变路径必须核对原数据和挂载 |
| 身份与会话 | 初始化／恢复引导、会话期限、注册期限、Agent 连接材料 | 到期、撤销和恢复失效分别可解释；敏感值通过受保护方式注入 |
| 节点目标 | 明确 Engine endpoint／context、认证及预期身份 | 不依赖交互用户全局环境，改变目标必须重新核对 |
| 协议与连接 | 支持版本、心跳、断线判断、重连退避和流能力 | 时间单位一致，实际间隔用单调时钟；超时不是任务未执行证明 |
| 请求与文件限额 | 消息、单文件、文件包、文件数、分页、转换输入及并发上传 | 声明计数单位及允许范围，各端取有效较严格限额 |
| 执行与输出预算 | 并发执行、受理时限、控制队列、日志与终端缓冲、结果空间 | 输出有界，关键结果单独保障；无可靠持久空间时拒绝新变更 |
| 内容与记录保留 | revision、操作、审计、输出、临时材料、请求去重墓碑和 Agent 记录 | 活跃／未知任务、当前引用、未确认结果和备份占用不能被普通保留策略误删 |
| 备份与密钥保管 | 触发方式、目标、保留、清单校验、解密材料及演练记录 | 由使用需要确定频率和保留；没有配置自动策略时不虚构定期执行 |
| 诊断与告警 | 脱敏日志、观察时间、连接失败、磁盘、备份和未知任务 | 明确阈值、通知方式及负责人；不得用“在线”覆盖各层状态 |

没有明确自动清理策略时，不自动清理正式管理记录；输出和临时空间仍须有有限预算。历史详细结果可以按策略删除，但在原请求作用域仍有效时保留去重墓碑。Agent 的结果只有在 Manager 已持久确认且满足其他保留条件后才进入清理候选。

密钥材料的保留需覆盖仍需恢复的密文和备份。销毁某旧密钥会影响哪些历史备份必须可查，不能只因当前程序已换新密钥就删除旧恢复材料。应用数据的备份频率与保留另按应用需要确定。
