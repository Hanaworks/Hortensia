# Docker Manager 文档编写实施方案

日期：2026-11-01。版本：0.1。状态：供审阅。

本方案用于组织 Docker Manager 后续的需求、设计、验证和交付文档。它规定先写什么、每份文档开始前准备什么、正文应说明什么，以及写完后怎样检查，使用户和 AI 能逐份讨论、编写和完善项目资料。

采用 req42 组织需求内容，以 arc42 组织架构与相关设计，再按需要引用技术写作和专项指南。用户表达需求、判断方案并审核内容；AI 负责查阅资料、组织章节、起草、检查和修订。指南提供默认做法，具体写法随项目内容和用户反馈调整。

**本轮交付为这份实施方案。** 后文的文件名是后续编写建议，不表示这些文档已经创建或其中的产品决策已经确定。

## 一 起点与编写目标

当前工作目录的直接资料是[原始对话](ChatGPT-Docker管理程序推荐-20261030-0119.md)与[讨论脉络](conversation-notes.md)。此前文档已按[归档说明](../archive/2026-11-01-documentation/README.md)保存，作为查阅背景；旧文档里的“已确认”“下一篇”等记录不自动成为本轮编写指令。

现有讨论描述的产品方向是：自托管管理多个独立 Docker 节点，以 Node 下的 Stack 和 Docker 资源为主要对象；用户指定部署节点，在 Web 内编辑和部署 Compose；保留原生 Compose 行为，并方便地将 Stack 配置用于另一节点部署。数据迁移属于可选方向，UI 随功能逐步细化。这些内容需要在后续需求说明中结合用户的新说明重新整理。

最终文档应让接手者能够理解产品目标、解释设计、实施功能并判断结果。需求和设计覆盖目标产品的范围，版本实现顺序另行安排。暂时不实现某项能力，不等于从目标设计中删去它；尚未决定的能力也不为追求“完整”而擅自补成定案。

## 三 文档组成与内容归属

建议从以下八类正文开始。文件数量可以随内容调整：短小内容可先作为章节，只有需要独立阅读、维护或已经影响主线时才拆成专题。

| 文档与拟用文件名 | 主要读者与阅读目的 | 负责展开的内容 |
| --- | --- | --- |
| 需求说明 `requirements.md` | 用户、设计者：理解为什么做和需要什么 | 目标、使用环境、目标范围、功能需求、质量要求、约束、术语和成功标准 |
| 功能设计 `functional-design.md` | 用户、开发者、测试者：理解操作时应发生什么 | 对象关系、操作条件、输入输出、正常与异常流程、状态和必要交互说明 |
| 架构设计 `architecture.md` | 开发者、维护者：理解如何组成系统并实现目标 | 系统边界、组成与职责、运行协作、部署、共同机制、技术取舍和风险 |
| 数据设计 `data-design.md` | 开发者、维护者：理解信息如何保存和保持一致 | 数据模型、标识与约束、配置来源、生命周期、存储结构和迁移要求 |
| 接口设计 `api-design.md` | 各端开发者、测试者：理解各方如何交换信息 | 接口与消息契约、参数和结果、鉴权表达、错误、事件与兼容要求 |
| 测试与验收 `test-plan.md` | 用户、开发者、测试者：理解如何判断实现满足约定 | 验证范围、环境、用例、预期结果、通过条件和结果记录方式 |
| 部署与运维 `operations.md` | 安装者、维护者：完成安装、更新、备份和排障 | 运行前提、操作步骤、配置参考、结果确认和恢复办法 |
| 开发实施计划 `development-plan.md` | 用户、实施者：安排设计如何落地 | 版本范围、任务、依赖、交付物、验证方式和实施次序 |

术语和完整需求主要维护在需求说明中。其他文档用必要摘要帮助理解，再链接到具体定义。功能设计解释用户可见的规则；架构解释实现这些规则的机制；数据和接口分别解释保存形式与交换形式。同一个主题可以跨篇出现，但同一条规则只维护一份完整定义。

例如，Node Cross 在需求中说明跨节点复用配置的目的；功能设计展开操作及来源、目标的结果；架构解释协作；数据设计解释要保存的信息；接口定义交互；测试检查预期结果。复制范围未定时，后面的文档保留这个问题，不各自选择一套范围。

架构正文保留理解整体所需的机制。通信、同步等专题过长时，可以拆出详细说明，但主文仍须说明它解决什么问题、参与者如何协作、关键约束是什么，再给出链接。这个处理也符合 arc42 对需求摘要和共同机制的组织建议。[需求概述](https://docs.arc42.org/section-1/)、[共同机制](https://docs.arc42.org/section-8/)

辅助信息先从简：少量待定问题放在所属文档末尾；跨篇问题增多时再统一到 `open-questions.md`。关键决策在所属设计中说明理由，历史变更需要独立追踪时再增加决策记录。文档入口随首批正文建立，不预先创建空目录和空文件。

## 四 编写顺序与阶段交付

| 阶段 | 工作 | 阶段交付与进入下一步的依据 |
| --- | --- | --- |
| 0 编写准备 | 审阅本方案，确定本轮文档组织方式 | 能说明各篇用途、依赖、写前准备和写后检查 |
| 1 需求整理 | 从现有对话提取目标和场景，整理 Portainer 参照范围及差异，补充质量要求 | 需求初稿能支持讨论功能行为；影响范围的疑问已集中列出 |
| 2 功能与架构 | 先写用户操作与结果，再结合运行环境展开架构；两者相互反馈 | 关键场景可从用户操作讲到系统协作，重大待定项明确影响哪些设计 |
| 3 数据与接口 | 在行为和组件职责的基础上细化保存与交换约定 | 同一场景中的对象、状态和字段含义一致，必要示例可相互对照 |
| 4 验证与交付 | 整理测试与验收、部署与运维，并据此检查前面的设计 | 主要需求有验证办法，安装和维护所需条件有设计依据 |
| 5 开发安排 | 根据目标设计划分版本和开发任务 | 实施者能找到每项任务的设计依据、依赖和完成条件 |

阶段表示依赖关系，不要求上一篇所有细节冻结后才能做下一篇。测试场景从需求阶段就可收集；部署条件应提前反馈架构。发现前文遗漏时回到其主出处修订，再同步受影响的内容。

默认逐份提交可读正文供审阅。每份都允许先形成带明确待定项的初稿；只有某项产品或设计选择确实影响后续结论时，才先讨论该问题。章节名称、措辞、排版和已有事实的整理由 AI 直接完成。

## 五 每份文档开始前的共同准备

AI 在开写前完成下面六项准备，形成一段简短的开写说明即可，无需另外提交一套准备报告。

1. **明确用途。** 用一句话说明本篇给谁看、读完应能理解或完成什么。
2. **读取项目输入。** 读取本篇相关的用户说明、已有正文和讨论来源；有实现时再读取对应代码、配置及测试记录。记录依赖的是哪份资料或哪个版本。
3. **核对结论状态。** 分清用户要求、候选设计、当前实现和实际验证结果。对会改变正文结论的矛盾，列出原话、出处和影响，不自行合并成第三种结论。
4. **查阅对应指南。** 阅读适用章节的目的、内容说明和必要示例，选出本篇要覆盖的项目内容。
5. **安排章节与归属。** 列出简短提纲，检查阅读顺序；确认哪些内容在本篇展开、哪些用摘要和链接承接。
6. **确定检查办法。** 从第七节选取本篇专用检查，加上第八节共同检查；提前准备可用于走查的项目场景或示例。

**能够开写的条件：** 本篇用途明确，相关输入已读，提纲和检查办法已定；未知内容能够标明位置及影响。若未知项决定整篇方向，先整理候选和问题；若只影响一节，则先写其他部分。

可复用的开写说明：

> 本次编写【文档名】，用于帮助【读者】完成【阅读目标】。已读取【项目资料】和【指南章节】。正文拟按【主要章节】展开；【已有定义】通过摘要与链接引用。尚需明确【问题及影响】。完成后重点检查【本篇专用检查】。

## 六 起草时的共同做法

开头先说明读者关心的目标、范围和核心内容，随后按理解或操作顺序展开。段落解释原因、关系与过程；列表用于步骤和并列事项，表格用于对照和重复记录，不把所有说明都压成表格中的短语。[Google 文档组织指导](https://developers.google.com/tech-writing/one/documents)

对关键规则写出适用条件、行为和结果，必要时配一个具体例子。例如，“支持跨节点复制”需要在功能设计中进一步说明选取什么、目标如何确定、操作后应看到什么；这些规则尚未讨论时，列出需要确定的问题即可。

给需要跨篇引用的需求、场景或接口使用稳定名称或简短编号，普通段落无需编号。涉及候选方案时说明理由和取舍；涉及当前实现时给出代码或配置依据；涉及验证时记录条件和结果。不能用“已设计”代替“已实现”，也不能用“已实现”代替“已验证”。

读者理解整体所必需的信息保留在正文，具体字段、长示例和操作细节放到适合的位置，并用有含义的链接衔接。不要为了“单一职责”让读者在多个文件之间反复跳转才能读懂一句话。[Google 长文组织指导](https://developers.google.com/tech-writing/two/large-docs)

## 七 每份文档的专用准备与检查

以下条目是在共同流程上的补充，不要求每篇重复抄写共同检查清单。

### 需求说明

**写前准备：** 读取两份对话资料及用户的新补充，提取目标、使用场景和明确限制；整理实际需要参考的 Portainer 功能，不从产品名称推导全量需求。准备使用者、节点环境、常用操作、配置与数据处理诉求方面的已知信息和问题。主要参考 req42 的目标、范围、功能、质量、约束和术语部分。

**正文交付：** 说明产品目标、使用环境、范围、主要场景、功能需求、质量要求及成功标准。功能按用户任务组织；质量要求说明可观察的效果和条件，未知规模或数值保留为待定。

**写后检查：**

- [ ] 核心诉求能找到对应需求，包括 Web 编辑 Compose、原生行为和 Node Cross；没有新增独立 Service 管理层等未经确认的产品模型。
- [ ] 每项主要需求能说明谁在什么情况下需要什么结果，并能提出验证办法。
- [ ] 目标范围、可选能力和待定内容可区分；没有把首版实现顺序混成完整产品范围。
- [ ] 质量要求足以支持设计讨论；“简单”“快速”“可靠”等表述已补充可观察条件或明确待定问题。
- [ ] 技术栈、Agent、存储位置等候选没有被写成既定需求；竞品能力若用于判断，已有相应版本的可靠依据。

### 功能设计

**写前准备：** 读取需求和术语，选出本轮要展开的用户任务；准备操作前提、输入输出、异常和冲突问题。借助 req42 的支持模型组织场景，按需要使用流程图或状态图；不以视觉稿定稿为开写条件。

**正文交付：** 说明对象关系、信息组织和关键操作流程，包括正常结果、异常反馈与必要的交互示意。重点解释用户如何辨别当前节点、配置与运行状态，以及操作的影响范围。

**写后检查：**

- [ ] 按实际操作走查关键流程，从入口到结果没有缺失的步骤或前提。
- [ ] 每个关键操作有输入、条件和结果；失败、取消或重复操作的适用情形有处理说明或明确问题。
- [ ] 状态名称、转换条件与用户能看到的结果一致；没有只命名状态却不解释其含义。
- [ ] Node Cross 的复制内容、目标调整、来源处理和冲突行为已说明或列为待定，没有悄悄代用户选择。
- [ ] 草图、流程图和正文一致；页面布局和控件细节没有成为未讨论的硬性要求。

### 架构设计

**写前准备：** 读取需求中的质量目标、约束和功能场景，收集节点网络与运行环境。列出真正影响系统组成的选择及依据，如节点接入方式、执行边界、配置来源和故障处理。查阅 arc42 相应章节及 C4 检查表；具体技术能力另查官方文档或安排验证。

**正文交付：** 先说明上下文与整体方案，再展开组件职责、关键运行过程、部署关系、共同机制、质量场景、取舍和风险。相关需求、术语与详细专题通过摘要和链接承接。

**写后检查：**

- [ ] 能沿一个部署场景和一个跨节点场景，解释每一步由谁负责、信息流向哪里。
- [ ] 节点不可达、执行中断等适用场景有处理设计或待解决的风险，用户可见结果与功能设计一致。
- [ ] 重要选择能联系到需求或约束，并说明取舍；候选技术没有被写成已选技术。
- [ ] 组件图、运行图和部署图中的名称、职责、边界一致，箭头有明确含义。
- [ ] 图中的 C4 container 等架构术语有解释，不与本项目所管理的 Docker 容器混用。
- [ ] 质量目标有对应设计办法或验证安排，技术可行性未确认的部分没有表述为已经验证。

### 数据设计

**写前准备：** 读取功能中的对象与状态、架构中的配置来源和存储职责。列出需要长期保存、可以重新获取以及只在运行时存在的信息，明确配置、凭据、日志与容器运行数据的区别。参考 arc42 领域模型相关指导及 [NASA 数据字典](https://swehb.nasa.gov/spaces/SWEHBVD/pages/102695667/5.07%2B-%2BSDD%2B-%2BSoftware%2BData%2BDictionary)。

**正文交付：** 说明信息模型、关系与标识、约束、生命周期和一致性；存储选型确定后再细化物理结构、索引、迁移及备份对象。尚未选择数据库时，可先完成逻辑模型。

**写后检查：**

- [ ] 功能所需的信息都有来源或保存位置，不保存的信息有获取或重建方式。
- [ ] Node、Stack、配置及执行记录等对象的标识和关系清楚；复制、修改、删除后的影响能解释。
- [ ] 需要一致更新的信息、外部修改和并发影响得到说明；没有在本篇另造一套业务状态。
- [ ] 敏感信息、保留和清理规则、备份对象与恢复所需关系相互一致。
- [ ] 用创建、更新和跨节点操作的具体例子检查模型；物理结构不提前替代尚未决定的架构方案。

### 接口设计

**写前准备：** 读取功能行为、架构参与者与通信方式、数据含义，列出实际交互清单。区分请求响应、事件、日志或终端流等可能不同的交互类型。参考 [NASA 接口设计](https://swehb.nasa.gov/spaces/SWEHBVD/pages/102695656/5.02%2B-%2BIDD%2B-%2BInterface%2BDesign%2BDescription)，再按选定协议查官方规范。

**正文交付：** 说明接口参与方、用途、调用条件、输入输出、错误与兼容约定；为关键交互提供完整示例。选型未定时先写逻辑契约，不凭空固定 URL、协议或消息格式。

**写后检查：**

- [ ] 每个接口能对应实际场景，前置条件、必填和可选数据、单位、空值与错误含义清楚。
- [ ] 请求和返回示例与字段定义一致，调用者能据此判断下一步。
- [ ] 权限、异步结果、超时和重复请求等适用情形的外部行为，与功能及架构设计一致。
- [ ] 事件或流式交互如被采用，生命周期、断开和恢复的约定明确。
- [ ] 数据保存格式与接口格式有必要映射；已有机器可读契约时，示例通过其校验，避免维护两份不同定义。

### 测试与验收

**写前准备：** 从需求阶段收集成功标准，结合功能边界、架构风险与数据接口约定完善用例。准备可用环境、样例数据和故障构造方式。参考 [NASA 测试计划](https://swehb.nasa.gov/spaces/SWEHBVD/pages/102695671/5.10%2B-%2BSTP%2B-%2BSoftware%2BTest%2BPlan) 的适用内容。

**正文交付：** 说明验证范围、方法、环境和通过条件；用例给出前提、操作、预期结果及对应需求。规定如何记录实际结果，执行后再增加结果记录。

**写后检查：**

- [ ] 主要需求与重要风险都有相应验证方式，未覆盖部分能说明原因和后续安排。
- [ ] 用例有可判断的预期结果，没有只写“验证正常”“检查成功”。
- [ ] 关键操作同时考虑正常、边界和失败场景；环境与数据足以重现问题。
- [ ] 预期行为引用需求和设计，测试没有自行发明产品规则。
- [ ] 计划、未执行项和实际测试结果明确区分；没有环境时如实保留待执行状态。

### 部署与运维

**写前准备：** 读取架构部署条件、配置接口、数据保存及恢复要求，取得可用安装包或镜像、环境与操作权限。参考 Diátaxis 分离操作步骤和配置参考，并查阅 [NASA 用户手册](https://swehb.nasa.gov/spaces/SWEHBVD/pages/102695673/5.12%2B-%2BSUM%2B-%2BSoftware%2BUser%2BManual) 的适用内容。

**正文交付：** 覆盖实际支持环境下的安装、初始化、更新、备份恢复和排障。每个操作说明前提、步骤、预期结果及必要的故障处理；尚无可运行产物时，先写部署设计与待验证步骤。

**写后检查：**

- [ ] 从准备环境开始，读者能按步骤执行并确认结果；版本、路径、权限和配置前提齐全。
- [ ] 示例与实际交付物一致，占位符可辨认，敏感值没有以真实凭据写入。
- [ ] 更新、备份、恢复及卸载的影响范围清楚；恢复步骤覆盖数据设计要求的完整备份对象。
- [ ] 操作指南可直接完成任务，较长原理解释和配置参考有独立位置或清晰链接。
- [ ] 可执行时在相应环境走查并记录结果；无法执行的步骤标为待验证，不能称为已验证手册。

### 开发实施计划

**写前准备：** 汇总需求、设计、测试和交付约定，列出未决问题及技术验证任务；结合可用资源与用户优先级讨论实现次序。参考 req42 的路线与风险内容，必要时从 NASA Documentation Guidance 查阅开发计划条目。

**正文交付：** 按可交付成果组织任务，列明版本范围、依赖、对应设计和完成标准。工作量有估算依据时才给出估算，同时说明影响估算的条件。

**写后检查：**

- [ ] 每项任务有具体成果、设计出处和验证办法，完成后能判断是否达到约定。
- [ ] 依赖顺序可执行，技术未知项有验证任务，不藏在无依据的工期承诺里。
- [ ] 版本范围与目标需求能对应，延期实现的能力没有从设计中消失。
- [ ] 计划没有新增未讨论的功能、技术选型或产品规则。
- [ ] 实施者能够找到所需的设计和测试资料；尚未解决的问题明确影响哪些任务。

## 八 每份文档写完后的共同检查

AI 先修正能自行处理的问题，再交给用户审阅。检查分为正文检查、关联检查和文件检查，不能用格式通过代替内容正确。

| 检查 | 实际操作 | 合格表现 |
| --- | --- | --- |
| 对照输入 | 将关键要求、结论与来源逐项比对 | 没有遗漏核心要求，也没有改变原意或结论状态 |
| 检查内容覆盖 | 对照本篇提纲和第七节逐项阅读 | 本篇要回答的问题都有正文；不适用项有简短理由，未知项有明确位置 |
| 走查场景 | 使用具体输入，逐步推演正常过程及适用的失败过程 | 前提、过程和结果能够连起来，没有跳步或互相冲突的行为 |
| 检查关联 | 对照引用的需求、术语、状态、数据和接口 | 定义一致；完整规则有主出处，摘要没有形成第二套定义 |
| 按读者顺序通读 | 先只看标题与开头，再从头阅读全文 | 能理解目的和主线；缩写、跳转和长细节不妨碍理解 |
| 检查图表 | 对照正文检查图的范围、元素、箭头和图例 | 图与文一致，读者能看懂关系和层次 |
| 检查文件与示例 | 检查链接、锚点、Markdown 展示；对已有格式使用对应解析或校验工具 | 文件可读，引用可定位，示例与约定相符；未来文件仅标为计划位置 |

自动工具适合检查链接、格式、示例语法和契约一致性；需求含义、设计取舍及阅读连贯性需要人工或 AI 阅读判断。真正的部署、恢复、性能等结论需要实际执行验证。

一次复核应留下具体问题及修改结果。关键设计或较大改写可增加一次独立阅读，重点找遗漏、冲突与难理解之处；小幅文字修改只复查受影响部分，不机械重做全套检查。

## 九 提交审阅与后续修订

每次向用户交付：正文链接、这次完成的内容、检查结果，以及仍需要用户判断的问题。检查结论使用“已通过”“发现问题已修订”“待确认”“未执行”这类直接表述，涉及未执行项时说明原因及影响。

文档可以处于“草稿”“待审阅”“已确认”状态。AI 自检完成后可提交待审阅版本；用户确认后，注明适用范围和日期。正文中的个别待定项继续保留，不因整篇审阅过就自动变为已确定。确认文档也不表示相应软件已经实现或通过测试。

用户反馈到来后，先修改相关内容的主出处，再检查引用该内容的文档，最后复查受影响的场景、示例和链接。只影响当前段落的反馈直接改正文；反复出现、可通用的问题，再补为简短编写约定。正常修订不要求每次增加一份新的规范文件。

可复用的交付说明：

> 已完成【文档链接】，覆盖【内容】。已检查【范围和办法】，修正【主要问题】。仍待明确【问题及影响】；【需要执行的验证】尚未执行，原因是【条件】。建议本次重点审阅【影响产品或设计的事项】。
