# Docker Manager 需求规格

更新日期：2026-11-03。状态：需求整理与细化初稿，待审阅；延续 2026-11-02 归档稿的 R01—R17、Q01—Q11 标识。

Docker Manager 面向维护多台独立 Docker 节点的运维人员。它把节点、Docker 资源及 Compose 配置放在同一个 Web 管理入口中，支持日常部署、诊断、配置复用以及部署位置迁移。本文定义目标产品和验收方向；具体行为方案见[功能设计](functional-design.md)，实现顺序见[开发实施计划](development-plan.md)。

## 1. 背景和成功目标

用户自行指定应用运行节点，日常使用 Compose 维护配置。原有操作方式存在三个不便：节点之间的管理上下文割裂；配置维护可能要求先登录服务器建文件；把满意的配置从 A 带到 B 部署需要手工搬运。

产品应让用户在 Web 中完成配置创建、查看、修改和部署，同时清楚知道当前对象属于哪个节点、哪些内容已保存、哪些已应用。跨节点时应能明确选择迁移部署位置或建立独立副本，并处理目标依赖、权限和结果确认。

节点管理和迁移的使用体验参考 PVE，节点内的 Docker 操作参考 Portainer。参照表达用户熟悉的操作方式，不承诺复制这两个产品的全部能力、代码或迁移机制。没有对竞品当前功能作完备评估，也不以其版本差异作为本项目需求事实。

## 2. 使用者、环境和边界

管理人员维护管理器、账号、节点接入和授权；运维人员在获准节点上管理配置与资源。这是职责划分，角色名称与权限组合由设计确定。用户已确认多人协作，并按节点和操作授权。获准部署任意 Compose 或创建容器的人员属于该节点的可信运维人员；同节点不可信租户的主机级强隔离不属于当前目标。

| 条件 | 已明确的范围 |
| --- | --- |
| 托管与访问 | 使用方自托管，通过 Web 管理 |
| 节点关系 | 各节点独立，不自动调度、不组成 Swarm 或 Kubernetes 集群 |
| 节点规模 | 通常不超过约 20 个，支持分组与标签；20 是设计和验证基线，不是产品硬上限 |
| 网络 | 包含内外网；Agent 主动连接管理端，使用方提供该方向可达路径 |
| 操作环境 | 以 Linux、FreeBSD 等 Unix-like 使用环境为背景，优先实现具备可用 Docker CLI／Compose 时一致的行为，不提前增加复杂跨平台适配 |
| 兼容声明 | 上述环境意向不等于已经认证 FreeBSD 本机可运行 Docker Engine；Agent 所在环境、Docker 端点和文件路径关系需实际验证 |
| Compose | 保持所用版本的原生行为；不提供镜像 Build、Dockerfile、构建上下文管理和构建执行 |
| UI | 功能行为先明确，布局和视觉随实现迭代，不要求先定完整页面设计 |
| 存储迁移 | 希望按需携带数据，前期允许手动打包、传输和恢复；具体机制与中断要求暂缓讨论 |

每节点资源数量、并发用户、延迟目标和数据迁移量尚未确定，不能从节点数推导吞吐承诺。

## 3. 术语和对象模型

| 术语 | 含义 |
| --- | --- |
| Node／节点 | 独立的 Docker 资源管理目标；界面和操作都须能识别其归属 |
| Stack | 某节点上围绕 Compose 应用配置管理的部署对象及资源关系 |
| Compose service | Stack 配置中的服务定义，不新增独立于 Node／Stack 的全局 Service 管理层 |
| Docker 资源 | 容器、镜像、网络、卷等，可属于 Stack，也可独立存在 |
| Stack 配置 | Compose 文件、有序文件组合、环境配置及受管理的附属运行配置；不包括业务运行数据和构建上下文 |
| 配置版本 | 一次已保存的配置内容及其部署输入，区别于当前编辑草稿和实际部署记录 |
| 运行数据 | 卷、绑定目录或外部系统中的应用数据，不能从复制 Compose 推定已经搬迁 |
| Node Cross／迁移 | 将 Stack 的活动部署角色从来源转到目标；执行后验证，通过后由用户选择是否删除来源 |
| Copy／复制 | 建立独立的目标配置，来源不变，两边后续维护和部署不自动同步 |
| Apply／应用 | 把明确的配置应用到明确目标部署，不隐含来源停止或删除 |
| 验证 | 按约定检查配置、资源、运行及业务确认等结果；命令成功不等于业务健康 |
| 外部资源 | 不是管理器创建，或管理器没有掌握完整配置的资源 |

基本关系为 Node → Stack／Docker 资源。多节点汇总不改变归属。Copy 后配置独立不保证应用数据隔离，例如两份配置仍可能连接同一外部数据库。迁移后保留来源材料，不表示同时维持两个活动写入端。

## 4. 功能需求

下列产品方向有用户原话依据；列表、权限分解、错误处理和成功判据是供审阅的需求细化，不能全部反向记为逐项已获用户确认。来源索引见[决策记录](decisions.md)。

### R01 自托管与访问

使用方能够自行部署管理器，初始化账号并通过 Web 登录，维护账号和授权。安装与认证方案由设计确定。验收应实际完成安装、初始化和不同权限账号的登录；目前没有可用安装包或部署结果。

### R02 节点接入与管理

获准人员能够接入、识别、查看和维护节点。节点运行 Agent 并主动连接管理端。失联须区别于节点没有资源，解除管理关系不隐含删除节点上的应用。验收至少接入两个独立节点，一个失联时仍能操作另一获准节点。

### R03 节点视角与多节点查看

用户能查看获准节点及资源概况，筛选后进入节点、Stack 或容器。修改操作必须指向明确节点；同名资源、切换页面或旧请求返回不能改变目标。验收同时覆盖两个节点上的同名 Stack，汇总和计数不暴露未授权对象。

### R04 Stack 配置编辑

在 Web 内创建、粘贴或导入、查看、保存和修改 Compose 及环境配置，并可再次打开维护。单文件、多文件及附属运行配置遵循所用 Compose 版本的原生规则；不能以单一 YAML 文本代替完整配置边界。受管理文件与节点外部路径必须区分，缺少文件要明确反馈。

用户无需先 SSH 创建配置文件；程序可以在后台保存文件。保存与部署分别报告，多人保存不能静默覆盖。验收覆盖创建—保存—重开—修改，以及并发保存和缺失引用。

### R05 Stack 部署与生命周期

用户能够在选定节点部署、更新、重新部署、启动、停止和移除 Stack，并查看结果及相关资源。保存成功、请求受理、命令完成和应用状态分开表达；删除配置、运行资源和持久数据分开处理。验收覆盖完整部署和失败反馈，不能把已受理当作部署成功。

### R06 原生 Compose 行为

配置表达什么，就按受支持的 Docker／Compose 行为执行；管理器不额外注入网络、卷或改写部署含义。Compose 自身创建的默认网络属于原生行为。文件组合、环境解析、项目名称、执行目录和路径关系须明确，不能另造合并规则。

不提供 Build 是已确认的范围例外。遇到需要构建才能部署的输入，应保留原文、解释限制并要求准备可用镜像；不能静默删除 build，也不能让部署意外触发构建。验收在相同输入、版本、目录、环境和项目参数下对照原生 CLI 的关键配置与资源，并检查无构建发生。

### R07 Node Cross 迁移与验证

用户从 A 的 Stack 发起迁移，选择 B，核对配置、数据依赖和目标条件，使 B 接替活动部署角色。只在 B 新建独立部署属于 R17。来源退出活动角色属于迁移切换范围，但停止时点、可接受中断和失败回退尚待设计裁定。

迁移执行后单独验证：检查配置和预期资源、运行状态、可验证的数据依赖及来源切换状态，需要业务判断的项目由用户确认。未验证、验证失败或结果未知，不能报告已验证完成。

验证通过后，由用户选择保留或删除来源；保留来源仍可完成迁移。删除必须说明管理配置、资源和数据的具体范围，并分别检查权限；不默认递归清空持久数据。清理失败单独记录。验收须有两端切换和验证证据，不能用复制或启动成功替代。本项的完整实现受迁移策略未决项阻塞。

### R08 容器管理与诊断

覆盖授权节点上的容器列表、详情、检查、独立创建、启动停止、重启、删除、日志、统计和控制台。Stack 容器显示所属关系，直接资源操作不应被误解为已同步修改 Compose。具体 Portainer 基础操作清单是细化稿。验收定位异常容器并按授权排障，控制台限制同时在后端生效。

### R09 镜像与仓库访问

查看节点镜像、标签和使用情况，支持拉取、标签维护、删除及明确范围的清理；需要认证的仓库须有受控凭据使用方式。只使用已有镜像部署，不含构建。验收覆盖受保护仓库、失败原因和清理范围，具体认证与凭据存储待设计落实。

### R10 网络与卷管理

查看、创建和删除网络与卷，展示可取得的使用关系；未知关系不能视为未使用。数据删除须明确对象、后果和用户选择。迁移数据归 R15，卷文件浏览和编辑尚未纳入当前清单。验收检查节点归属、关联展示及删除数据的独立确认。

### R11 多用户与节点及操作权限

支持同一用户在不同节点具有不同权限，区分资源查看、配置、部署、运行控制、删除、日志、控制台和授权管理。直接请求同样执行限制，读取资源概况不自动授予敏感配置或凭据访问权。

跨节点按实际阶段检查两端：来源配置使用、目标配置维护、目标部署、来源切换控制、验证所需读取及可选清理分别授权；携带数据另检查相应读写权限。分组标签不隐式扩权，前一阶段成功不授予下一阶段权限。验收覆盖直接请求、流会话和撤权，不允许未授权副作用。

### R12 已有资源查看与配置接管

已有资源在授权范围内可见，资源可见不代表掌握了完整 Compose。配置缺失时说明限制；导入、接管和获得编辑／重新部署／跨节点能力有明确前提。接入或只读发现不自动改写资源。验收涵盖非本管理器创建的容器和不完整 Compose 项目。

### R13 操作反馈与管理器维护

重要操作可追查目标、发起者、时间、阶段、结果和错误。浏览器断开、Agent 失联或结果缺失时，区分失败与尚无法确认，不直接报成功。提供管理器更新、管理数据备份与恢复的交付办法；管理器备份不等于应用数据备份。验收包含断线核对、记录查询和隔离恢复演练。

### R14 节点分组与标签

维护分组、标签及归类，并按这些信息查找筛选节点。归类不移动应用，删除分类不移除节点。层级、多重归属、标签结构和维护权限由设计确定；若以后引入按组授权，须另定变化规则。验收检查筛选、受限计数和归类不扩权。

### R15 Node Cross 携带存储数据

希望按需迁移 Stack 所需存储数据，前期允许用户手动打包、传输和恢复。配置准备、数据准备、切换和验证应可区分；用户声明数据已准备，不能替代实际迁移验证。

**存储搬运细节继续暂缓。** 类型、规模、传输方式、一致性、停机要求和恢复行为均未决定；不承诺在线迁移或任意停机。暂缓不阻塞 Copy／Apply，完整自动搬运验收在重新展开支持范围后确定。

### R16 docker run 转 Compose

提供粘贴命令、生成可编辑 Compose、复制或带入 Stack 编辑的工具。只解析文本，不执行命令、shell 展开或自动部署。常用参数映射范围和语法详见[功能设计](functional-design.md)；不支持或不能等价转换的内容逐项可见，不猜测环境文件、变量或宿主机路径的值。

验收覆盖镜像、端口、环境、挂载和启动参数，并检查引号、变量及命令替换输入不会执行，未知选项不会被静默忽略。部署仍经过节点选择和授权。

### R17 独立的 Copy 与 Apply

Copy 以指定的已保存配置建立独立目标配置，来源保持不变；目标配置修改和部署互不自动同步。Copy 成功仅代表保存。Apply 把指定版本部署到明确目标，遵循 R05，不隐含来源停止或删除。

复制内容、目标修改、外部依赖和同名冲突须明确。拥有已保存完整配置时，来源离线不必阻止 Copy，但不能据此判断来源已停机或完成迁移。验收区分复制和部署结果、重复提交去重、同名冲突，以及目标失败时来源不变。

## 5. 代表性场景

| 场景 | 用户所处情境和任务 | 主要要求 |
| --- | --- | --- |
| S01 多节点日常管理 | 内外网约 20 节点，按用途分组后查看某节点异常容器并排障 | R02、R03、R08、R11、R14 |
| S02 Web 维护应用 | 拿到 Compose 和环境文件，在选定节点创建、保存、编辑、部署并核对结果 | R04—R06、R13 |
| S03 独立复用 | A 的配置适合 B，建立独立副本，修改端口或路径后部署，继续保留 A | R17、R11 |
| S04 变更部署位置 | A 的 Stack 需要改由 B 承担，准备依赖、按已定策略切换和验证，再选择来源处理 | R07、R11、R15 |
| S05 接入已有节点 | 节点已有容器和 Compose 项目，先查看，配置不全时补齐再接管 | R12 |
| S06 安装命令转配置 | 获得一条 docker run 命令，希望转换、核对后纳入日常 Compose 管理 | R16、R04 |

## 6. 质量要求和可观察判据

下列为质量细化稿。定量性能指标未确定，当前用场景和不变量表达，不填入未经约定的秒数或容量。

| 标识 | 场景和判据 |
| --- | --- |
| Q01 对象清晰 | 两节点同名 Stack，切换视图后提交或删除，目标仍为用户确认的节点和对象 |
| Q02 结果可解释 | 保存、Copy、Apply、迁移执行、验证及清理分别可辨认，不用一个成功状态覆盖全部结果 |
| Q03 授权有效 | 未授权账号经页面、直接接口或重连流尝试访问，不能取得受限内容或造成副作用 |
| Q04 故障可判断 | 执行中断网或管理端重启，未知显示为未知并可核对，不盲目重放变更 |
| Q05 并发编辑可控 | 两人基于同版编辑，第二次保存提示冲突，保留待解决内容，不静默覆盖 |
| Q06 兼容边界清楚 | 对实际验证的运行组合做原生 CLI 对照；保持文件及环境语义，无意外 Build |
| Q07 敏感信息受控 | 配置、导出、诊断和错误记录按权限展示，系统生成日志不无意泄露凭据 |
| Q08 管理可恢复 | 备份恢复后核对账号、授权、节点身份、配置和操作记录，未知操作不被当作已完成 |
| Q09 日常管理可用 | 约 20 节点包含慢节点、离线节点时，健康节点流程仍可用；资源数、并发及时间判据在负载验证前确定 |
| Q10 迁移可核对 | 验证未通过禁止来源清理；验证通过可保留来源；清理失败与迁移结果分开 |
| Q11 转换可信 | 每项输入有映射、差异提示或不支持诊断，转换不执行输入或自动部署 |

## 7. 范围、风险和后续承接

当前不含自动调度、Kubernetes 管理、镜像构建、不可信租户强隔离，也未承诺 GitOps、插件生态或全量 Portainer 功能。镜像导入导出、卷文件浏览等扩展在有具体需要时另定。迁移完整切换与回退仍需裁定；自动存储搬运按用户要求暂缓。

人员和排期尚未安排；现有资产是历史对话、归档及本轮文档。实现状态和实际测试结果由[实施计划](development-plan.md)与[测试计划](test-plan.md)承接。主要风险是误把配置复制当作迁移、把命令完成当业务可用，以及断线时重复执行。相关策略见[架构](architecture.md)及[待决事项](decisions.md)。

本规格以 [req42](https://req42.de/en/req42-at-a-glance) 组织目标到需求和验收的关系，阅读组织参考 [Google Technical Writing](https://developers.google.com/tech-writing/one/documents)。需求的直接来源和更正顺序集中见[决策记录](decisions.md)，底层 Compose／run 官方行为来源见[文档规划](documentation-plan.md)。
