## 1. 目标、依据与范围

首个版本应能完成：初始化并登录 → 登记、认领及授权节点 → 在Web创建和保存多文件Stack配置 → 选择固定版本部署 → 查看命令结局、资源观察与释放状态 → 重开后继续查询和核对。它包含Manager、Agent及Web的真实运行路径，不能以某一个库、模拟执行页面或单次CLI成功代替。

范围承接[开发实施计划§4](../development-plan.md#4-m1-工程落实与任务依赖)、[需求](../requirements.md)、[功能与交互](../functional-design.md)及[P07—P10工作选择](../decisions.md#21-2026-11-04-的具体技术建议)。HTTP采用[现行规格](../specifications/http-api.md)，Agent采用[协议](../specifications/agent-protocol.md)及[共享Schema](../../contracts/agent-v1.schema.json)，执行及释放采用[执行与恢复](../specifications/execution-recovery.md)。本文安排依赖和可观察退出条件，不复制另一份接口、字段或状态主定义。

当前M1口径包括本地账号及节点动作授权、节点主动接入与撤销、配置新建和版本保存、固定版本Apply、结果查询、取消与未知保护，以及启动说明、最小一致备份和隔离恢复。首轮平台是Linux、Agent与Docker同机、明确的Unix socket及原生Compose插件；实际版本须在验证时记录。

2026-11-12推进中补充用户决定：真正未知／中断任务需要首版受控维护流程，由操作者明确触发；用户接受该流程可能需要停止节点Docker并影响现有容器。此决定确定产品方向，具体终止屏障、维护计划、证据和双端更新仍待实施及真实环境验证，不能表述为已有安全解锁命令或已完成O12。

Copy、多节点分类编辑、广泛的容器／镜像／网络／卷操作、终端与实时诊断、run转Compose、已有项目自动接管、Node Cross及数据搬运，继续按M2—M4推进。多平台兼容、约20节点容量承诺、完整升级矩阵和长期保留策略属于后续验证。排除这些能力不取消产品目标，也不免除M1的跨节点与多用户权限检查。正式名称、许可证及对外发布范围按O01在公开发布前决定，本篇不替代该决定。

## 4. 验证顺序与证据

正常路径先用一个主要测试节点贯通初始化、明确授权、多文件保存、固定版本部署、结果及双端释放，再重启双方核对持久状态并重复查询。随后使用第二节点验证同名、可见范围和目标隔离。Web必须使用正式服务而非内存假接口；执行结果必须来自真实进程与资源观察，不能由受控result夹具代替。

故障验证先在模块内控制事务和消息顺序，验证没有部分提交、假确认或重复开始，再把关键断线、进程终止、取消和输出边界放到真实Compose组合复验。原生对照与故障夹具采用[测试计划§7](../test-plan.md#7-m0m1-验证规格)；结果记录包括软件／协议／Schema及CLI版本、配置摘要、注入位置、消息顺序、提交边界、实际资源变化、预期与实际差异及结论。进程强杀不代表掉电耐久，受控执行器不代表原生Compose验证，重新打开数据库不代表备份恢复完成。

文档阅读检查至少覆盖四种读者任务：部署者能找到实际产物、配置、启动与停止步骤；使用者能区分草稿／已保存／已部署和结果／待释放／需核对；维护者能沿模块职责找到数据、事务及错误定位；后续开发者能查明修改必须保持的规则和对应测试。由阅读者执行首条正常流程，再执行保存回执丢失或节点断线等已实现故障路径，记录步骤、观察、卡点及修订。作者在场解释出的结果不能直接计作独立阅读通过。

本篇不提前填入安装命令、服务名称或交付包位置。它们必须由实际产物的[运行资料](../operations.md#2-首个交付物必须具备的运行资料)承接并执行验证。各模块内部说明继续按[小型程序要求](../development-plan.md#62-模块按小型程序组织规格)维护，不用堆积文档文件数量衡量完成度。
