## 2. 本轮架构和行为提案

以下是可以整体审阅的设计稿，不记作用户已确认的技术方案。模块正文按这些提案保持一致。

| 提案 | 选择、理由与代价 | 替代方案及适用条件 | 状态 |
| --- | --- | --- | --- |
| P01 管理端形态 | 单一 Manager 应用，Web 为独立逻辑构件；配置、授权和协调集中，减少初期运维负担。代价是管理端不可用时不能提交新操作 | 多管理端需另行设计共享锁、会话归属和一致性；当前无高可用指标，不先引入 | 待技术验证与审阅 |
| P02 配置管理 | Manager 保存受管理配置和不可变版本，Agent 物化执行输入；便于编辑和跨节点复用。代价是需要处理敏感信息、备份和外部修改 | 节点文件为权威或 Git 为权威也可支持 Web／跨节点，但需另外的读取、同步和冲突规则 | 待审阅 |
| P03 操作一致性 | 持久操作标识、任务输入摘要、Agent 执行账本、资源串行化和重连核对；不宣称底层 Docker 操作恰好执行一次 | 简单请求重试不能区分已执行未回报，无法满足 Q04 | 待协议原型验证 |
| P04 并发编辑 | 基于版本的条件保存，不自动合并；冲突由用户核对，避免破坏 YAML 与变量含义 | 自动合并可后续增加，但要提供明确冲突策略 | 待审阅 |
| P05 节点分类 | 初期平面分组、允许多重归组，标签为键值；均只用于组织，授权继续以节点和操作为准 | 层级分组、按组授权会改变继承和变更规则，必要时另定 | 待审阅，不是既定需求 |
| P06 转换语法 | 先支持单条 POSIX 风格 docker run／docker container run 文本、常用选项；不执行 shell | 支持完整脚本需要不同解析范围，当前没有此要求 | 待参数样例验证 |

### 2.1 2026-11-04 的具体技术建议

以下推荐作为各篇深化设计的共同基线。提案内给出具体值是为了能够审阅、比较和验证，不意味着已完成选型原型或工程实现。

在用户授权“合理推进下一层”后，P07—P10 于本次落实为 M1 v1 工作规格：当前实现按同源 HTTP JSON、Agent TLS WebSocket、明确字段／状态和双端释放握手接入，不由各端临时另选格式。技术参数属于可修订的工作选择，不登记为用户逐项批准；O02／O03／O04／O07 的运行验证部分仍开放。具体规格入口为 [HTTP](specifications/http-api.md)、[Agent 协议](specifications/agent-protocol.md)和[执行与恢复](specifications/execution-recovery.md)。

| 提案 | 推荐方案与理由 | 替代及代价 | 当前承接 |
| --- | --- | --- | --- |
| P07 运行组合 | Manager、Agent 使用 Go；Web 使用 Vue 3／TypeScript，通过同源 HTTP JSON 接口访问 Manager；Manager 交付 Web 静态产物；Agent 主动建立 TLS WebSocket | TypeScript 管理端可统一语言，但节点仍需独立运行环境；gRPC 流可加强生成契约，但引入另一套构建与代理配置。推荐组合便于分发两个守护程序并检查结构化协议；不声称性能优于替代方案 | [架构](architecture.md#4-方案策略与取舍)、[接口](api-design.md)；具体依赖和版本在 M0 锁定 |
| P08 身份与权限 | 首期本地账号和服务器端会话；Agent 用一次性认领材料换取可撤销的随机长期身份，TLS 校验 Manager；按节点和动作检查授权 | 外部 OIDC 可减少密码管理，但增加身份提供者依赖；mTLS 减少 bearer 使用，但需证书签发与轮换运维。首期选择可独立安装的方案，承担密码、会话和令牌保护责任 | [接口](api-design.md)、[Manager](components/manager.md)；撤权不能撤回已经发出的有效开始许可 |
| P09 持久化 | 单 Manager 使用本地 SQLite；Agent 独立 SQLite 账本。配置正文及冻结输入加密存数据库，版本发布／操作／发送意图分别在事务内提交 | 独立文件或对象存储更适合大包，但增加内容发布与备份的一致性处理；PostgreSQL 适合后续多实例，首期增加运维成本。SQLite 不作为多主或网络共享文件服务 | [数据设计](data-design.md)、[运行准备](operations.md)；密钥独立保管，工作区仍需供 Compose 明文读取 |
| P10 M1 实现范围 | 先完成本地账号、节点接入、配置新建和版本保存、Apply、结果查询及故障核对；用 Linux 同机 Agent／Docker 组合完成首轮验证 | 同时实现全部平台、迁移和资源操作会扩大尚未验证的交互。M1 的取舍不删减产品目标，第二节点用于权限与隔离测试；首版正式发布范围仍单独裁定 | [实施计划](development-plan.md#4-m1-工程落实与任务依赖)、[Agent 支持边界](components/agent.md) |

Web 首期通过轮询读取操作快照，实时事件和控制台在后续需要时接入；编辑器组件、SQLite 驱动和 WebSocket 库在依赖许可证、维护状态及原型核对后锁定。当前不将 Monaco、xterm.js 等候选写成必装依赖。

每项决定记录日期、问题、选项、结论、理由和后果；用户确认后标明来源，再同步需求、架构、所属模块、接口和测试。技术验证记录环境、输入、实际结果及局限，不能把“原型通过”升级为完整产品已验证。

归档与当前稿有差异时，以最新直接决定为准。设计建议获得审阅前继续保持提案状态；改变提案不需要重写原始对话。组织方式参考 [arc42 设计决策](https://docs.arc42.org/section-9/)。
