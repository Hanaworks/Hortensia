# Docker Manager 开发实施计划

更新日期：2026-11-07。状态：M0 通信与独立许可门禁原型切片已验收，整个M0仍未完成，M1 尚未实现，无工期承诺。面向用户与实现者，承接 req42 的[范围、需求和风险](requirements.md)，以及 arc42 的[模块、运行、决策及质量](architecture.md)。文档编写安排另见[文档规划](documentation-plan.md)。

## 1. 已有基础与开工条件

已有资产为原始讨论、11 月决定及归档、需求与设计文档，以及 M1 技术组合和 v1 通信／执行工作规格。2026-11-04 已建立 Git 仓库，初始提交 `c5ea0fc` 保存上一轮全部资料；当前另有协议 Schema、正反例、静态检查脚本及 Go 通信原型。实现与证据见 [M0 实施记录](implementation/m0-agent-channel.md)，尚无完整产品服务。

优先审阅产品行为和 P01—P10，以具体设计开展 O02、O03、O04、O07 的验证。存储自动搬运按用户要求继续暂缓；O05 阻塞完整迁移，不阻塞节点、编辑、部署和 Copy／Apply。M1 是首个内部可验收增量建议，正式首版包含哪些后续切片仍待决定，本计划不把全部目标写成首版排期。

依据用户补充的 D12，后续实现遇到细节未定时，可查阅 Portainer 管理端及其 Agent 源码。参考范围包括 Compose 调用、权限判断，以及 Agent 的接入与鉴权、连接保活与重连、请求／响应交互、结果与异常回报、超时和重试处理；阅读时沿两端相关调用链核对，区分参考实现的连接模式与本项目的主动连接要求。记录所读版本或提交、文件与符号、适用前提，以及本项目采用或调整的理由。参考结论直接落实到所属实现、必要规格和验证用例；节点独立、显式目标、原生 Compose 语义、权限边界和任务恢复要求继续以本项目要求为准。源码阅读与本项目运行验证分别记录，此条仅登记后续参考方式。

交互与行为按 D10 以 PVE 节点管理、Portainer Docker 管理操作为主要参照。已有需求和参考足以决定的细节继续落实；参考有冲突或仍拿不定的取舍按 D13 向用户说明具体场景、选项、影响和推荐，再推进依赖该答案的部分，其他独立工作继续。

## 3. M0 的技术验证

| 验证对象 | 要回答的问题 | 输出及失败影响 |

## 4. M1 工程落实与任务依赖

M1 的目标是一个真正可用的单节点端到端流程，同时预留多节点标识和权限边界。不能仅交付编辑页面或仅验证 CLI 可执行。

### 4.1 范围与明确退出条件

| 能力 | M1 范围建议 | 留给后续增量 |
| --- | --- | --- |
| 账号与权限 | 本地账号、禁用、节点动作授权、会话失效；首位管理员显式取得节点操作权限 | 外部身份提供者、秘密代理使用、更复杂角色模板 |
| 节点 | 一次性接入、主动连接、撤销、状态和能力、断线核对 | 分组标签编辑与更完整多节点概况在 M2；非首轮平台逐一验证 |
| 配置 | 新建受管理 Stack、UTF-8 多文件、环境和附属配置、版本冲突 | 既有项目自动接管、远程引用和未验证组合 |
| 执行 | 固定版本 Apply、禁止 Build、项目冲突检查、结果与观察、取消和未知保护 | 广泛资源生命周期操作、终端、Copy 与迁移分别在 M2—M4 |
| 运行与恢复 | 启动、最小一致备份、隔离恢复、旧任务核对 | 完整发布矩阵、容量承诺和长期保留策略在 M5 |

验收使用一台主要测试节点完成整个流程，并用第二节点及不同权限账号验证目标隔离；单节点主流程不能成为省略多用户／多节点权限检查的理由。退出条件是 T01—T05 的适用子集、T07／T08／T17 的关键故障及 T16 最小恢复均有实际证据；只有文档或正常网络下的一次 Apply 不满足退出条件。

### 4.2 工程任务

| 任务 | 具体工作 | 依赖和接入位置 | 验证断言 |
| --- | --- | --- | --- |
| A 工程与基础契约 | 按选型建立 Manager、Agent、Web 和测试工程，记录实际目录与启动方式，固定物理接口 schema | M0；回填三个模块设计与接口规格 | 三端可启动；协议不兼容有明确反馈 |
| B 存储与授权 | 实现账号、节点、配置版本、操作仓储与权限入口 | A；Manager 身份／配置／操作模块 | 重启记录仍在；未经授权不读取或变更资源 |
| C Agent 接入 | 身份认领、能力、工作区、账本、准备／开始／结果回报 | A、B；Agent 的连接与执行调度 | 同操作同输入不重复开始；断线保持核对依据 |
| D 配置保存 | Web 文件编辑、条件保存、版本与部署输入冻结 | A、B；配置管理与编辑会话 | 重开内容一致、并发保存冲突、秘密不无意进入日志 |
| E 真实部署 | 结构化任务、原生校验、禁止构建、资源观察及操作查询 | C、D；Compose 适配与操作协调 | 固定版本部署到正确目标；命令／运行状态区分 |
| F 恢复和交付 | 故障核对、最小备份恢复、首次运行说明和测试记录 | B—E；运行准备和测试计划 | 受理后崩溃、结果丢失不盲重跑；隔离恢复能核对 |

任务 A 中的应用目录是选型后的工程产物，不从参考项目复制目录宣称存在。当前任务的准确通信定义以 HTTP／Agent 专题和 contracts 为输入；不可再自行创造另一份报文。数据库迁移脚本及私有类型随 B／C 实现，但必须满足现有字段语义、唯一约束、事务与恢复记录。必要约定变化先修改主定义和对应样例，不以“实现细节”为由使两端各自解释。

### 4.3 代码组织与契约交接建议

| 未来位置 | 承接的设计与依赖 | 首次落实内容 |
| --- | --- | --- |
| `cmd/manager`、`internal/manager` | Manager 模块；HTTP、授权、配置和操作协调 | 启动与恢复模式、处理器、仓储事务、outbox 与连接会话 |
| `cmd/agent`、`internal/agent` | Agent 模块；身份、账本、工作区和执行器 | 单实例、连接与核对、固定参数调用、进程生命周期 |
| `internal/protocol`、`api/` | 接口篇共同字段、错误和版本 | 类型及生成 schema，OpenAPI／消息契约校验；避免 Web 和 Go 手抄出两套字段 |
| `internal/storage`、`migrations` | 数据篇的类型、外键和事务 | 驱动锁定、内嵌 SQLite 版本核验、迁移与备份接口 |
| `web/src` | Web 第 8 节的路由与状态 | 登录、节点上下文、编辑保存、操作查询；构建产物由 Manager 提供 |
| `tests/fixtures`、`tests/integration` | 测试篇 M0／M1 夹具与故障矩阵 | 无真实秘密的输入、可重复故障点、资源对照和证据输出 |

### 4.4 v1 规格之后的实际交接

| 顺序 | 直接输入 | 需要交付的下一份实际结果 |
| --- | --- | --- |
| 1. 契约适配 | `contracts/agent-v1.schema.json` 与 HTTP 规格 | Go／TS 类型或验证适配器，20 类消息正反例全通过；HTTP 每条路由的请求／响应测试，不生成另一套字段名称 |
| 2. 可控连接原型 | Agent 协议的会话、关联、许可、finalize 和扫描结束握手 | 两进程通信记录；能暂停、丢消息和重启；重复消息不触发第二次执行 |
| 3. 持久化接入 | 数据设计的事务、冻结安全回执、执行篇的 outbox／归属记录 | 实际迁移脚本、事务失败与重放证据；同 key 不因后续修改返回不同版本 |
| 4. 文件与 Compose 适配 | Agent 支持矩阵及分阶段预检 | 固定 Compose 版本下的输入样例与原生对照；变量文件引用等不支持项可保存但明确拒绝部署 |
| 5. Web 连接真实后端 | HTTP 对象、权限裁剪、单在途保存和释放状态 | 页面完成首条流程；结果未知、终态待释放、编辑冲突均可识别 |

这里的下一步包含实现和原型，不是再补一轮全量文档。M1 自动恢复规格仅覆盖可证明未开始、受监督正常退出和只补观察；真正 unknown／interrupted 保留隔离。该限制允许开展原型，但阻塞宣称故障后可无人干预恢复的可交付产品。发布前必须针对实际 Docker 环境证明维护终止屏障和核对手段，不能用备注或一次资源快照直接解锁。

这些路径是职责映射，不是已经存在的文件。M0 首先锁定 Go、前端构建工具、数据库驱动、WebSocket 库及 Engine／Compose 组合，记录许可证、实际版本与最低能力；不能直接从本文复制“最新版”安装。协议初版只覆盖 M1 必需操作，后续能力必须先扩展契约和能力协商。

本轮文档深化已提供首个技术审阅基线。接下来的实际顺序为：审阅推荐组合与 M1 范围 → 完成 M0 原型和契约定稿 → A／B 基础工程 → C／D 接入及保存 → E 部署 → F 故障与恢复。原型和实现属于下一步实际工程工作，不能用此次文档更新把 M0 或 M1 标为完成。

## 5. 进入迁移实现前的必要设计

O05 需要逐阶段明确：来源何时退出、目标何时启动、业务访问和写入如何切换、允许多长中断、如何判断两端活动角色、验证覆盖什么、何时证据失效，以及每个失败点的恢复动作。为各状态给允许操作和所需权限，特别处理两端状态未知、来源重启、目标失败及同名资源替换。

这部分必须回到用户所接受的运行影响，由用户裁定产品取舍，再由设计给技术机制。数据细节仍可按 R15 暂缓；在手动准备数据的版本中，也需明示哪些一致性由操作者负责，哪些由系统实际验证。只有 Copy／Apply 的 M2 版本不得叫作 Node Cross 已完成。

## 6. 进展、证据与计划维护

当前完成初稿留存、M1 设计深化及 M0 的首个通信／许可门禁实验；2026-11-06 补建[切片验收标准](implementation/m0-agent-channel.md#本轮验收标准)，2026-11-07 按预先保存的补齐计划完成AC01—AC11逐项验证与审阅，代码／测试基线为`94056e0`。当前切片可供技术交接；M0 尚未整体完成，M1—M5 尚未实现。已有 Portainer 固定版本[源码对照](research/portainer-agent-reference.md)，其结论与本项目实测分别记录。每个增量完成时记录版本、已实现功能、适用环境、测试证据和剩余限制，更新 README 与实际使用入口。

整体架构、关键模块或物理契约形成新决定时，复核当前需要的设计深度和文档安排；重要内部机制变复杂可独立成专题，简单部分继续合载。进度按实际能力与证据报告，不按预定文件数或未经估算的百分比判断。

### 6.1 每轮实施的开工与完成条件

实现者负责在对应切片的实施文档中先写清下列约定，并链接具体规格；已有文档能承载时直接补充，不要求每轮另建文件。全局设计可以保留后续细节，当前即将实现的关键行为和完成条件必须可查，不能等用户逐项追问。

| 开工前须确定 | 最少需要写清的内容 |
| --- | --- |
| 目标与范围 | 这一轮解决哪个场景，交给谁用，具体包含什么、做到哪个可观察终点；未做部分留在哪个阶段 |
| 依据与关键取舍 | 对应需求、协议、参考材料和代码基线；哪些已确认、哪些是有理由的技术工作选择、哪些仍待决定 |
| 实施规格 | 对外接口与数据、正常和失败流程、状态变化、幂等／超时／取消／恢复，以及本轮涉及的存储或副作用边界；引用精确定义，不能只有模块名或“接入”字样 |
| 验收标准 | 稳定编号、输入与前提、动作／故障点、预期可观察结果、验证方法和环境；标准先来自要求，再映射到测试，不由写出的测试反推要求 |
| 完成与交付 | 哪些项必须全过，未验证如何处理；交付版本、构建／运行方式、证据和已知限制；区分源码交接、切片验收、阶段完成与产品发布 |
| 顺序与阻塞 | 下一步任务依赖哪些已经成立的结论；未决问题影响哪项工作、由谁决定，其他独立工作能否继续 |

上述信息齐备、影响当前任务的未决行为已有处理方式，才进入依赖它的实现。现有需求和参考足以决定的技术选择由实现者写清理由后推进；需要用户裁定的产品取舍按 D13 提供具体场景与选项。此要求不增加每轮都等待用户批准的流程，也不要求预先设计全部私有函数。

实施中若发现约定不足，先记录新情况、旧规则、新规则及受影响验收项，再按修订基线继续；涉及多端契约的变更同步主定义和样例。发现测试失败要判断实现错误、规格错误或环境问题，不能默默放宽标准以获得通过。探索性实验也要先写明要回答的问题、观察方法和退出条件。

交付时逐项记录“通过／失败／未验证／阻塞”及依据，说明哪些结论仍来自历史记录。测试命令成功只完成其覆盖部分；必须核对规格和范围才可宣布切片完成。依赖此切片的下一轮只使用已成立的结论，不能把暂缺能力当成已交付。当前 M0 的补建验收表明确保留事后形成的时间与缺口，不回写为事前已经完备。

路线承接 req42 的范围与风险，工程安排承接 arc42 构件和质量；任务—依赖—工程接入—断言的写法参考 [Helichrysum 切片计划](../../Helichrysum/docs/slice-2-plan.md)，不采用其项目任务、技术决定和完成状态。
