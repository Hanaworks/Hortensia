# 项目实施规格与验收复盘

复盘日期：2026-11-07。范围：Docker Manager 从项目文档深化进入 M0 通信原型实施，再补齐具体规格、验收依据和交付记录的过程。

每轮实施都应让未参与会话的人能够查明：准备做什么、按照什么做、做到什么程度、怎样验证，以及最终交付了什么。这些内容应由实现者主动写清并维护。本次实现者包括执行开发的助手，不能把遗漏归因于用户没有逐项要求。

因此，本次问题是具体实施约定和完成判断不充分。已有协议与参考确实约束了实现，但一些决定没有及时成为可查的工作依据；后补说明也不能证明这些决定在开工前已经完整确定。

## 问题根源与影响

**没有充分区分全局设计的深度与当前实施所需的深度。** 全局项目定义可以随阶段逐步展开；一旦开始某轮具体工作，就必须明确这轮涉及的接口、数据、行为、失败处理及结束条件。此前对“暂不补齐全部内部细节”的理解，没有充分落实这一层要求。

**把已有文档当作实施准备充分的证明。** 文档数量多、存在协议和模块设计，仍不足以回答本轮具体支持哪些行为、哪些机制尚未接入，以及技术参数为何这样选择。若关键取舍只在代码或会话里，后续接手者难以区分既定要求、临时选择和偶然行为。

**实施、测试与完成结论之间缺少逐项对应。** 测试通过证明的是实际执行的断言。缺少独立验收标准时，容易把已有用例覆盖的部分当作整个交付范围，也难以识别“尚无证据”的行为。一个原型子集、整个 M0 阶段和可部署产品，需要分别判断完成状态。

**对用户的解释没有及时转化为可交接成果。** 反复说明“有方案”“有文档”“后续再细化”，仍不能让用户直接核对具体依据。用户因此需要不断追问，实施者也失去了可以稳定约束后续工作的共同记录。

## 已落实的纠正

目前已把本轮实施范围、具体规则、验收条件、测试入口、证据限制和版本对应起来。新增测试核对了握手期限、异常 welcome、完整冻结应答、消息指纹上限、命令行诊断和输入预算等原有缺口；当前通信与独立门禁切片完成了逐项验收。这轮补齐没有改变运行代码，补上的是原先不足的验证和交接依据，不能把新增用例数量当成修复缺陷数量。

两个具体例子说明为什么需要检查证据本身：

- 原会话替换测试收到旧连接关闭消息后便检查新会话，但旧处理器的清理可能尚未结束。审阅后改为等待清理完成，再验证新连接还能正常应答，避免测试过早通过。
- 命令行使用 `localhost` 后连接失败，可能发生在名称验证之前，因此只能证明失败映射。名称校验的依据改为明确设置错误服务器名称、连接已知端点的用例。

同时保留验证方法的差别：真实 TLS 连接、可控时钟、内存回调和静态审阅各自只能支持相应结论。例如 `server_failed` 的永久监听故障分支只做了静态审阅，不能记成故障注入通过；独立门禁测试也不能证明持久账本或 Docker 执行已经实现。

## 后续每轮实施的要求

具体开工与完成条件统一维护在[开发实施计划第 6.1 节](development-plan.md#61-每轮实施的开工与完成条件)。后续执行应遵守以下要求：

| 时点 | 实现者应做的工作 | 判断依据 |
| --- | --- | --- |
| 开工前 | 写清目标、范围、规格入口、关键行为、依赖、验收方法和交付条件；探索性原型也要写清要回答的问题及退出条件 | 另一位实现者能够据此开展本轮工作，不需要猜测主要行为和结束位置 |
| 实施中 | 新发现影响行为时，记录原因、调整规则及受影响验收项，同步主定义和样例；实现选择说明来源和理由 | 规格与代码持续对应，不能默默降低标准以取得通过 |
| 验证时 | 从要求推导断言，再核对现有测试；拒绝用例保持其他前提有效，竞争用例等待真正的状态边界 | 能说明每项证据证明了什么，失败、未验证和阻塞均可见 |
| 交付时 | 绑定版本、环境、结果、运行方式和剩余限制，更新入口并按标准判断完成 | 接手者可以定位和复验同一份成果，完成结论限定于实际范围 |

参考资料也应落实到具体决定：记录实际查阅的版本或位置、采用的规则及调整理由。竞品参考不能替代本项目的需求与验证；列出资料名称，也不能代替说明某项实施选择的依据。

普通技术选择由实现者在授权范围内写清理由后推进。涉及现有需求无法决定的产品行为时，带着具体场景、选项、影响和建议向用户确认。维护文档是实现责任，不应变成要求用户逐项设计或反复批准的负担。

## 交接前的自查

接手者应能从交付材料中直接回答：

1. 这一轮具体做了什么，哪些内容留在后续阶段？
2. 每个关键行为依据哪份要求、规格或有理由的技术选择？
3. 正常流程、异常流程和关键边界具体怎样运行？
4. 按什么标准验收，每项结果及证据在哪里？
5. 交付对应哪个版本、什么环境，怎样运行和复验？
6. 下一轮可以依赖哪些已成立的结论，还有哪些条件未成立？

若答案仍主要存在于实施者的记忆或会话解释中，交接资料就还不充分。发现缺口后应补齐约定和证据，再按更新后的依据推进。

本次教训要求把当前实施写到足以约束行为、验证结果和完成交接的深度。后续阶段的内部类型、数据库细节和页面设计仍按实际需要展开；无需为了文档齐全而提前写完全部设计。当前切片验收完成，也不改变整个 M0、持久任务、真实 Docker 管理和产品交付尚未完成的状态。
