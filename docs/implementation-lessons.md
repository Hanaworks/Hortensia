# 项目文档编写到实施交付的全过程复盘

复盘日期：2026-11-07。范围：资料阅读、文档规划、初稿编写、深化与归档、阶段和必要性判断、实施规格、原型开发、验证及交接。本文在原实施验收复盘上扩展，保留原路径供已有链接继续查阅。

这次反复出现的问题是：已有资料、计划和产出，没有始终转化为当前阶段足够具体、可查、可验证的工作依据。早期表现为按预定文件写齐后，未充分复查设计深度；后来表现为已有协议和测试，却没有完整定义当前切片的实施与完成条件。问题需要沿整个过程修正。

这些准备、判断和记录应由编写者与实现者主动承担。本次执行者包括助手，不能把遗漏归因于用户没有逐项要求。用户从“还缺什么”进一步追问“当前是否真的需要”，是合理的阶段判断；执行者应帮助分清必要内容与可延后细节。

## 1. 从文档编写到交付的经过

| 阶段 | 实际发生的情况 | 需要保留的判断 |
| --- | --- | --- |

| 深度与组织纠偏 | 用户指出主骨架承接、模块内部协作、计划调整及完成措辞的问题 | 应检查正文，也应检查原提纲本身是否充分 |

## 2. 全过程中的具体教训

### 2.1 先辨认用户正在问什么及所指时点

讨论参考体系、判断现有内容、分析下一阶段需要什么、要求直接编写或实施，是不同任务。相关会话中曾出现把“如何组合参考指南”回答成“如何编写项目文档”，也出现用当前能找到的参考记录回答“最初规划时是否已经列出参考”的情况。

本项目后续追问又从“实施还缺哪些细节”转向“这些细节现在是否必要”。此时应重新判断对象和阶段，而不是沿着之前的补缺列表继续扩写。回答历史问题要核对当时的方案、原话或版本；回答当前问题要查看现行内容；分析下一步则要说明依赖和必要深度。

### 2.2 实际阅读、采用资料和落实内容要分别说明

早期材料有实际参考记录，也有对适用内容核对不足的澄清。因此，不能概括为“所有资料都没读”；同样，列有指南名称或链接，也不能证明深入阅读并充分落实。

编写前应读取当前任务所需的正文、必要上下文及实例，说明实际读到哪里、采用了什么、哪些材料未取得。相关章节需要读懂，不要求每轮机械通读全部资料。阅读之后，还要把获得的方法落实为项目中的具体说明和检查；参考资料越多，不会自动使文档越完整。

“有数据字典的参考”只回答方法是否可用。项目中的字段含义、约束和维护位置是否明确，需要检查正文。这是两个独立问题。

### 2.3 整理需求时保留原意与确定程度

压缩会话时，不能只保留功能名称，把对象、条件、例外、背景和取舍删掉。用户确认、助手建议、参考产品行为、技术工作选择、当前实现和验证结果也不能混为一类。

本项目已有具体纠偏：Web 内编辑配置不等于禁止后台落盘；约 20 个节点是验证基线，不是固定上限；Node Cross 后来明确为迁移，Copy／Apply 保持独立；迁移后需验证并由用户选择来源清理。较新的明确决定应回填主定义，历史意见保留历史状态。存储细节暂缓，也不能写成永久删除该目标。参见[讨论脉络](conversation-notes.md)与[有效决定](decisions.md)。

### 2.4 主骨架要贯穿局部展开

最初总原则已写 req42、arc42 作主骨架，但逐篇准备容易变成“接口用 NASA、测试用 NASA、运维用 Diátaxis”，弱化了这些内容与同一套需求、组件和运行设计的关系。后来另写对照稿，也不能自动修正原方案及原正文。

正确的安排应说明：当前写什么内容，承接哪些需求和设计，专项资料具体补充哪一部分。进入模块、接口、数据、测试或运行资料后，仍要沿主骨架组织已有项目对象；补充资料负责帮助展开和表达。不要求每份文件重抄整套框架，也不应移入参考项目的参数、策略或审批流程。

### 2.5 规划要安排内容深度，不能只安排文件类别

早期八类文档覆盖了常见主题，但整体架构形成后，没有充分重估 Manager、Agent、Web 中需要进一步说明的内部协作、生命周期和异常处理。缺口在具体内容及深度，不在于少了固定数量的文件。

规划一篇文档时应明确：谁读、要继续什么工作、必须回答哪些问题、哪些现有内容可引用、需要深入到哪里。短小内容可留在章节中，复杂或需要独立查询的内容再拆分。初稿可以先服务方向审阅，但应把这一用途与“可据此实施”区分清楚。

### 2.6 计划应随认识加深而调整，检查也应反查提纲

原方案本来允许阶段反馈和合并拆分，后续也确实更新过需求与推进状态。真正不足是：架构认识加深后，设计层次、必要输入和剩余工作没有被同样充分重估。

因此，方案中写有“可调整”还不够。整体架构形成、关键模块展开、需求或验证结论改变时，应主动复查安排。写后既核对是否按计划完成，也要从用户原意、实际场景、适用指南和读者任务出发，检查计划是否漏了当前必需内容。只按自己的提纲检查，容易把提纲的遗漏原样保留下来。

### 2.7 先判断必要性与阶段，再决定补哪些细节

详细程度应由当前工作及依赖决定。跨模块调用、共同数据、持久化结构、兼容性、关键状态和副作用，需要在相应工作开始前有明确约定。纯局部、可替换且不影响这些边界的实现细节，可以随模块实现确定。

模块内部的数据由模块维护，不代表其他使用者可以没有契约；数据库只有一个模块使用，也不代表正式表结构与迁移可以不定义。反过来，某项内容最终必须明确，也不等于现在就要把所有私有类型、字段和未来功能预写完。

本项目应先明确当前 Web—Manager、Manager—Agent 的契约及关键执行规则，其他细节按其所属切片推进。判断缺口要问“不写会阻碍谁现在做什么”，不能仅因缺少名为“数据字典”的独立文件就认定不完整。

### 2.8 定义的内容、归属和存放位置要分别判断

数据模型说明对象关系，数据字典说明语义和约束，数据库规格说明实际存储结构；它们的内容职责不同，文件数量可按维护需要调整。ER 图、表结构或几个字段示例，不能自动替代其他说明任务。

共同约定有统一入口和主定义，模块专属内容由所属模块维护，再通过引用衔接。需要明确“谁负责、谁使用、哪里查”，避免每个模块各写一套，也避免把所有内部细节堆进全局文档。Schema、迁移文件可承载精确结构，必要的语义与行为说明仍应可查。

### 2.9 纠正要落回现行正文，新增内容要能被找到

会话中解释清楚、另写一份对照稿、提出一张修正版表格，都不等于项目正文已经更新。更正影响原方案、模块、接口或测试时，要同步这些位置及入口，明确哪里是当前有效定义。

用户询问“新补的都在哪里”，也提示交付说明必须给出实际位置、修改内容和使用状态。初稿归档应保留原貌，现行版本继续维护；归档中的“当前”“完成”不能直接用于今天。Git 保存逐次变更，压缩包保存特定时点的交接快照，两者都应说明范围，不能混成多套并列有效规格。

### 2.10 进入实施后，主动写清本轮约定与完成条件

全局文档可以逐步深化。具体实施开始前，范围、关键接口与行为、失败处理、依赖、验证方法和交付条件应达到可以执行的程度。这是实现者的责任，不能等用户再次要求“详细设计”才补。

本次 M0 开工前已有目标协议、Schema、实验目标及主要约束，但没有完整集中定义本轮最终行为和验收条件。后来根据代码补出的实际规格能够帮助核对当前实现，却不能追认为事前已完整确定。技术选择在实施中形成时，应当在同轮记录依据并同步规格；需要用户裁定的产品取舍，带着具体场景和选项确认。

### 2.11 完成判断必须对应内容与证据

“预定文件已起草”“当前阶段内容已覆盖”“方案可实施”“软件已实现”“测试通过”“当前切片可交接”分别说明不同状态。最初“八份初稿已齐”确实保留了部分待定项，但仍容易掩盖未被识别的设计深度缺口；后来已有测试全过，也不足以覆盖全部切片验收要求。

应从要求推导验收条件，再映射证据，不能反过来用现有测试决定交付范围。文档检查只证明所检查的内容或结构，源码阅读不等于运行验证；真实连接、可控时钟、内存回调及静态审阅分别记录其适用范围。

本轮审阅还修正了证据本身：会话替换测试需等待旧处理器清理结束，再验证新会话；命令行主机名连接失败不能独自证明名称校验，须引用能够排除其他失败原因的用例。验收不仅检查是否运行成功，也检查断言是否足以支持结论。

### 2.12 主动推进与必要确认都要有边界

助手应主动读取已有材料、补足当前必要说明、处理授权范围内的技术选择、执行检查并维护入口，不能让用户不断充当缺口发现者。也不能把自行选择的参数追记成用户确认，或因用户允许参考 Portainer 就扩展为复制其全部能力。

用户已授权合理推进时，日常组织和技术选择写清理由后继续；真正影响产品行为且现有材料无法决定的问题，再请用户裁定。既要避免把设计工作推给用户，也要避免用流畅的文字掩盖待定事实。

### 2.13 实施规格也必须能支撑接手与维护

2026-11-07用户再次指出，模块内部规格还要给其他开发者和维护者看。此前增加目标、接口、限制和逐项验收，解决了“按什么做、怎样算完成”，但内部职责、从调用到落库的流转、数据来源及生命周期仍分散，读者需要从代码拼接含义。它们是当前已实现模块的必要说明，不能以“内部细节”或“已经有测试”为由推迟。

后续规格要解释实现结构、关键时序、状态／事务／锁边界、重要字段和维护定位；源码链接用于追踪具体实现，不能代替说明。验收还需从接手者视角核对能否理解、排障和安全修改。范围按模块复杂度确定，不逐行翻译代码；设计先形成，实施中修订，交付前按最终代码核对。本次对已交付模块的补充明确标为事后补充。

### 2.14 相对独立模块应按小型程序形成完整说明

用户进一步明确：每个相对独立模块内部，除共同定义外，自己定义和处理的内容应按一个“小型程序”组织文档。前一轮补充结构、字段和维护索引仍只是起点；如果仅从现有章节增补，可能继续遗漏模块如何初始化、如何使用外部契约、怎样把输入转为内部对象并形成输出等整体关系。

模块内部属于谁维护，与它是否需要被完整说明是两回事。共同身份、协议、通用错误等引用主定义，并交代本模块的使用方式；模块自己的对象、字段、状态、算法及存储规则由本模块定义；外部输入到内部表示的校验、转换、处理和输出映射必须明确。只有接口和字段名，接手者仍要猜它们如何串起来。

“小型程序”指职责与说明完整，不要求每个模块单独运行或部署，也不要求复制一套全项目文档。可合载、可分节，复杂后再拆分。文档应连续回答六组问题：目的、边界与依赖；输入输出和调用前提；内部组成与实现理由；数据定义及正常／异常流转；初始化、关闭、恢复和并发；验证、故障定位及修改约束。范围明确后，按这些问题查缺，而不是以目录齐全判断完成。

已实现部分应按实际代码核对，使用一个可追踪的正常／异常实例检验说明是否连贯；尚未实现部分保持设计状态，只落实当前阶段必要的内部约定。无需提前穷举所有临时变量或未来功能，但当前模块必须的定义不能因为“不是通用内容”而省略。检查目标是他人可据此理解和接手，不依赖原作者口头补全。

### 2.15 规格成立还要核对所有入口与实际资源边界

2026-11-12的M1复核说明，单个入口满足规则并不保证模块整体满足：周期恢复枚举会拒绝损坏的退出元数据，但直接补观察仍可能绕过它；会话绑定有先后，网络Welcome完成却可以逆序，按完成顺序替换连接会挤掉真正当前会话。修复须把共同准入放到所有调用路径及最终事务中，并区分持久权威、内存登记和网络完成，不能只在触发反例的入口加一层判断。

同轮初始化漏查WAL／SHM／journal，导致主库缺失时SQLite清掉遗留材料；这也提醒我们，边界集合要按底层程序实际会触及的文件和进程核对，不能只按自己列出的主要文件检查。备份副本、进程退出和Docker端点停止也各自只证明有限事实，需要独立说明还缺哪层证据。

后续把确定反例提升正式回归，先保存规格修订，再验证原路径及可能旁路。独立审阅发现问题后重新打开对应验收，不因整包测试曾通过就保持“已完成”。环境权限跳过、夹具准备失败及中途测试错误如实保留；最终固定源码回归与本机夹具、真实部署分开报告。

## 3. 后续统一执行方式

具体文档方法继续由[文档规划](documentation-plan.md)维护，工程开工与完成要求由[开发实施计划第 6.1 节](development-plan.md#61-每轮实施的开工与完成条件)维护。复盘中的教训落实到以下动作：

| 时点 | 应完成的动作 | 应能回答的问题 |
| --- | --- | --- |
| 接手与阅读 | 核对当前任务、有效原话、历史状态、已有正文和实际读过的参考 | 用户现在要解决什么，哪些材料可以直接作为依据？ |
| 规划与起草 | 确定读者任务、内容深度、主骨架承接及主定义；保留必要条件和待定状态 | 这篇实际要说明什么，写到哪里才够用？ |
| 模块展开 | 按小型程序核对目的／依赖、输入输出、内部组成、数据与流转、生命周期、验证维护；区分共同定义、本地定义与转换处理 | 单独接手该模块，能否从输入追踪到内部处理和输出？ |
| 深化与修订 | 根据新认识复查正文和提纲；判断当前必需、下一阶段或范围外内容；同步相关位置 | 哪些是真缺口，为什么现在需要，原安排是否仍充分？ |
| 具体实施 | 先写本轮范围、行为、内部协作／流转、数据定义、依赖、验收与交付条件，选择和变更同轮记录 | 按照什么做，内部如何工作，做到什么程度，如何判断达标？ |
| 检查与交付 | 逐项核对内容和证据，按最终代码核对维护说明，绑定版本与环境，维护入口和历史边界 | 做了什么、凭什么算完成、他人能否接手维护、下一步还能依赖什么？ |

不为每次文字修改重建一整套计划；不机械增加文件、照抄所有参考栏目，或提前穷举所有内部细节。当前必需内容的缺口应当解决，可延后的内容则明确承接位置和解决时点。
