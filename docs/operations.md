# Docker Manager 部署与运行准备

更新日期：2026-11-04。状态：交付前的运行设计提案，已补充 M1 目录、密钥、备份恢复与故障门槛，尚无可执行安装包、镜像或经过验证的安装命令。本文面向部署和维护者，承接 [arc42 部署视图](https://docs.arc42.org/section-7/)及本项目[运行与共同概念](architecture.md)，落实 R01、R02、R11、R13、Q04、Q07、Q08 的交付要求。

## 1. 部署责任和前提

使用方维护管理端及其数据、访问地址与传输信任，提供各 Agent 到管理端的可达路径，并维护节点上的 Docker／Compose 与访问权限。Manager 暂建议单实例；没有高可用或自动故障转移承诺。节点应用独立运行，管理端停止通常只影响管理能力，不能据此断言进行中的任务没有副作用。

| 区域 | 需确认的条件 | 当前状态 |
| --- | --- | --- |
| 管理端 | 安装产物、版本、访问端口、持久目录、运行用户、身份与密钥保护 | 第 7 节给出 M1 候选目录和运行方式；O02、O03、O07 待验证 |
| 网络 | 浏览器到管理端、Agent 主动到管理端、节点到所需镜像仓库 | 逻辑方向已定；具体反向代理、证书和协议待设计验证 |
| 节点执行 | Agent 服务、账本与工作区、Docker 端点、CLI／Compose 版本和路径关系 | 实际支持组合待 M0 验证；不以 Unix-like 名称替代兼容测试 |
| 权限 | 首次管理账号、节点身份认领／撤销、最小操作授权 | 第 7 节与接口篇已给初始化及认证建议；实际命令随工程交付验证 |
| 备份 | 管理元数据、配置内容、保护材料、版本和恢复环境 | 范围见第 4 节；无实际备份结果 |

Agent 可能具备控制节点的高权限，应按可信运维协作范围部署，身份材料不混入普通分享配置。权限机制承接接口提案，密钥与备份操作见第 7—9 节；交付前仍需实际演练。

## 2. 首个交付物必须具备的运行资料

安装资料需给出实际下载／镜像位置与版本、支持环境、完整配置参数、持久路径、初始化和启动步骤、健康检查、停止与卸载影响、首次接入和撤销。每条步骤在实际环境执行后，记录预期结果和失败处理；没有产物时不填占位命令冒充可运行教程。

节点接入流程为创建接入材料、安装配置 Agent、主动认证连接、核对身份和能力、只读发现资源，再开放获准操作。Agent 重装、身份丢失或轮换时先核对节点和旧任务，不自动按同名认领。解除管理先处理未决任务和会话并撤销身份，不删除应用资源。

首个安装产物出现后，在本篇补齐可执行步骤；操作条目较多时再拆出安装、运维和更新手册，并保持本篇与架构入口的承接。用户使用手册在已有实际界面后编写，当前行为参考[功能设计](functional-design.md)。

## 3. 日常观察与故障处理

维护者区分管理端可达、Agent 连接、Docker 访问、Compose 能力、采集新鲜度及未决操作。操作记录包括发起者、目标、输入版本、阶段、结果和时间，诊断访问受授权，日志保留与容量阈值待 O11。

| 现象 | 核对顺序 | 处理边界 |
| --- | --- | --- |
| 浏览器提交超时 | 用原提交标识查询是否受理，再查 operation_id | 不立即使用新标识再次部署 |
| 节点失联 | 查看最近连接／采集时间、网络与身份、Agent 服务及本地账本 | 不把历史空列表当无资源，不启动未授权新操作 |
| 操作长时间无结果 | 核对 Manager 阶段、Agent 账本、受监督进程和实际资源 | 未知先保留占用，不自动重跑或删除工作区 |
| 部署失败 | 固定版本、文件关系、环境、镜像、路径、外部依赖及 CLI 错误 | 不删除 build 配置来掩盖限制，也不自动触发构建 |
| Agent 重启后账本缺失 | 标记相关操作未知，核对真实资源和身份 | 不按“无账本”等同“从未执行” |
| 迁移验证失败 | 查两端活动状态、具体检查和业务确认 | 不自动删除来源、不盲目重启来源形成双活；按 O05 批准策略处理 |
| 清理失败 | 查本次清理对象与局部结果 | 保留迁移验证记录，不能从迁移开头重新执行 |

具体服务名、日志位置和诊断命令须与实际交付一致，首版安装验收时补入。当前表支持设计审阅，不证明所有情形已有自动恢复能力。

## 4. 管理数据备份与恢复

备份范围包括账号和授权、节点身份与撤销信息、配置原文和不可变版本、秘密保护所需材料、操作／迁移／验证及审计、软件与协议版本。M1 提案将配置正文密文和元数据存于同一数据库，由 SQLite 备份接口取得一致副本，再与全部所需密钥组成备份组。备份管理器不包含所有节点卷、绑定目录或外部数据库。

建议恢复程序先在隔离环境加载备份，核对内容和保护材料，再检查身份及协议兼容；恢复后的旧操作不自动重发。重新连接节点时，核对 Agent 账本和实际资源，再开放变更。旧备份可能遗漏最近的执行，不能用旧协调记录覆盖节点事实。

演练应实际恢复至少一个配置版本及其文件、用户权限和未终结操作，证明仍能正确拒绝越权与重复开始。保留备份生成环境、范围、恢复步骤、核对结果及局限；频率、保留、异地副本和恢复时间目标待 O11，不虚构已满足的 RPO／RTO。

## 5. 更新、停止与回退

首个发布前定义 Manager—Agent 兼容矩阵、schema 迁移、升级顺序、失败回退及不兼容时的行为。更新前核对运行中的变更、备份管理状态和保护材料；执行窗口与是否等待任务结束由实现给出明确步骤。

停止管理端不表示底层 Compose 已停止；停止 Agent 不保证已启动子进程和 Docker 资源自动回滚。发布版必须给出监督与退出行为并通过故障测试。回退旧管理端还需考虑数据库和协议是否可逆，不能仅恢复旧二进制就宣称回退成功。

## 6. 运行交付的完成依据

M1 应交付实际可启动的最小资料和备份核对；M5 扩充正式安装、更新、故障和恢复手册。T01、T07、T08、T16、T18 的实际记录支持相应结论，未执行不记通过。当前待补项详见[决策与待办](decisions.md)，本篇尚不能直接用于生产部署。

## 7. M1 安装布局与首次运行提案

建议 Manager 以一个服务交付 Web 静态产物与管理 API，Agent 为节点上的独立服务。M0 首先验证 Linux 主机上的二进制运行、同机 Docker 端点及 Compose；其他环境继续保留产品意向，只有通过同类用例后才能列入支持矩阵。以下是拟定目录，不是当前项目已经创建的路径或服务。

| 位置 | 建议内容与权限 | 备份／清理责任 |
| --- | --- | --- |
| `/var/lib/docker-manager/manager.db` | Manager 管理数据库；服务私有目录 `0700`，数据库及 WAL 文件不对普通用户开放 | 用 SQLite 备份接口取副本；不能仅复制在线主文件 |
| `/etc/docker-manager/keys/` | KEK 与 HMAC 密钥环；目录 `0700`、文件 `0600`，服务账户可读 | 独立受控备份；仅有数据库无法恢复秘密 |
| `/var/lib/docker-manager-agent/agent.db` | 节点执行账本、ledger_id、结果及本地占用 | 保留持久卷／目录；丢失时隔离变更 |
| `/var/lib/docker-manager-agent/workspaces/` | 固定配置位于 `{stack_id}/{version_id}/package/`；staging 与包外运行材料按 operation_id 组织，运行 manifest／空 env 不进入包内 | 固定版本目录属于运行依赖；不能作为临时缓存随意清除 |
| `/etc/docker-manager-agent/identity.json` | node_id、候选／已认领随机凭据与 Manager 地址／信任配置，`0600` | 不复制给另一节点；丢失后重新认领，不按同名自动恢复 |
| `/etc/docker-manager-agent/keys/` | 独立 K_ledger 及本地敏感结果保护密钥，`0600` 文件 | 与账本匹配恢复；缺钥或错钥停止新操作 |

Manager 服务用户不需要 Docker 控制权限；Agent 仅使用明确配置的 Docker 端点，实际权限须满足 CLI。授予 Docker 控制能力即处于高权限信任范围，不能把普通节点权限界面解释为宿主机隔离。密钥挂载与数据库挂载分离，数据库位于本地可靠文件系统。

首次启动顺序为：生成 Manager 持久身份和密钥环 → 初始化数据库并核验 SQLite 版本／PRAGMA → 通过本机受限初始化流程建立首个管理员 → 开放受 TLS 保护的访问 → 创建限时认领材料 → Agent 先持久保存自身候选凭据再发起认领 → 核对节点身份、ledger_id、CLI 能力和只读观察 → 授予操作能力。初始化不设置通用默认密码，不在命令行参数或日志中打印长期秘密。

重启不得重复创建身份或替换缺失的密钥。已有数据库却缺钥、身份不符或 schema 过新时，服务进入明确失败／核对状态；新安装和恢复安装必须是不同入口。首次部署应能验证一个数据库副本确实可解密，再开放变更。

运行配置至少包含访问地址、TLS 信任、数据库路径、密钥路径、日志策略、Agent 工作根目录、Docker 端点和 CLI 路径；实际配置字段与命令由交付工程生成并在此维护。默认监听范围、端口与反向代理方式须随首个产物验证，不能把本文目录建议拼成未经执行的安装命令。

## 8. 数据库与密钥备份组

M1 备份机制建议通过 SQLite Online Backup API 获取完整数据库副本。WAL 模式的最近提交可能仍在 WAL 文件，禁止只拷贝活动 `manager.db`；采用备份接口后校验副本，而不是声称复制三个活动文件自然形成同一时刻快照。[SQLite 备份接口](https://sqlite.org/backup.html)、[WAL 文件](https://sqlite.org/wal.html)

一次备份按以下步骤生成可恢复组：

1. 记录 manager_id、应用／schema／协议版本、开始时刻；取得密钥轮换维护锁，使备份期间不删除任何密钥。业务可继续进行，备份只声称一个一致数据库快照，不声称停机或零数据损失。
2. 用备份接口写到新的临时目标，处理 busy、磁盘满和取消；只有备份完成且关闭目标连接后，才作为候选副本。失败副本不覆盖上一份有效备份。
3. 从副本枚举全部 `key_id`、`digest_key_id`，连同本次密钥环生成受控密钥副本；验证引用的每把钥匙存在。保留 HMAC 旧钥，否则已有幂等请求无法按原算法比较。
4. 检查数据库结构、外键和全部密文的认证解密；核对至少一个版本的原始文件字节与固定任务输入，禁止把解密结果写到普通日志。记录检查结果和副本校验值。
5. 将数据库、软件版本清单和密钥副本关联为同一个 backup_id。数据库副本与密钥副本分别保护、分别控制访问；备份清单只列 key_id，不含密钥正文。完成后原子发布清单并释放维护锁。

备份密钥材料应使用部署方既有的受控秘密保管位置；M1 安装资料必须指定实际位置、权限与恢复负责人。不能以密钥未放进数据库为理由遗漏密钥备份，也不能把数据库和明文密钥作为普通共享下载包。

Agent 账本、身份和本地密钥有独立备份责任，但它们与 Manager 副本没有天然的跨机器一致时刻。恢复任一端都先冻结变更并核对另一端及 Docker，不能把两份备份拼接成“没有遗漏执行”的证明。业务卷或数据库的数据搬运仍按 O06 暂缓；管理数据备份不替代应用数据备份。

## 9. 恢复与重启的具体边界

| 场景 | 允许恢复的动作 | 重新开放变更前的条件 |
| --- | --- | --- |
| Manager 正常进程重启，数据库／密钥未回退 | 打开数据库，恢复占用；Agent 重连报告账本；先查询，不自动重放已授权许可 | 当前身份、会话与操作事实一致；未核清目标继续阻塞 |
| Manager 从旧备份恢复 | 在隔离环境检查 backup_id、版本、密钥及全部密文；启动 recovery_mode，禁止新受理和开始许可 | 撤销旧浏览器会话，核对备份后的账号／授权／节点撤销变化；按协议 scope=all 分页对照 Agent 全部账本（含终结已 ack 历史），处理本库缺失项后显式解除受影响目标隔离 |
| Agent 正常进程重启，账本／身份未回退 | 回报 ledger_id、未决操作、工作区和实际资源；不因 PID 消失判定未执行 | 与 Manager 核对许可及结果；疑似执行过的操作不重跑 |
| Agent 账本从旧备份恢复、缺失或损坏 | 停止新开始，保留现有工作区；作为恢复事件重新核对；必要时认领新账本身份 | Manager 明确接受恢复身份并核清未知任务；不能默默生成空账本继续 |
| 密钥缺失、错配或密文认证失败 | 阻止读取敏感内容及新部署，报告 key_id／对象 ID 的受控错误 | 找回匹配备份并验证；生成新钥无法解密旧内容，禁止覆盖原材料 |
| 磁盘满或 fsync／事务提交失败 | 拒绝新受理和新开始；正在执行的任务尽力保留结果并报告记录失败 | 恢复存储可写后核对实际执行；不能为了续跑先清账本或操作记录 |

旧 Manager 备份可能恢复已经撤销的凭据。恢复模式下不因旧 token 仍可匹配就直接接受变更；管理员须核对当前节点身份、撤销列表和用户授权，受影响凭据先撤销／轮换。恢复环境只开放维护入口，完成核对前不接入原公开入口。旧密钥用于读取备份内容；恢复后新写入先生成并备份新的加密 key_id，避免把已回退的密钥使用计数当成可靠额度，HMAC 旧钥仍按引用保留。

隔离恢复演练至少覆盖：一个含环境秘密的多文件版本、一个尚未开始的操作、一个已 START_COMMITTED 而 Manager 未收到结果的操作、一个备份后新建且已完成并 ack 的操作、一个备份后已撤权用户，以及旧 HMAC key_id 的幂等重试。通过判据是可读取正确原文、发现并保存缺失历史、拒绝越权和重复开始、保留未知占用；完成记录写实际输入与输出，不以“数据库能打开”代替恢复成功。

## 10. 运行观测与交付门槛

Manager 最少提供存储可读写状态、恢复模式、未决操作数量、Agent 最近连接和采集时间；Agent 最少提供账本可写、Docker 可达、Compose 可用和工作区容量状态。一般日志只包含 ID、阶段与错误码；命令输出可能包含秘密，以独立的 `operation.output.read` 能力控制并加密保存，输出截断要显示截断事实。

M1 暂不自动回收版本、幂等记录、执行账本和受用工作目录。应在新受理／新开始前检查可用空间与写入能力，容量不足时阻止产生更多变更并提示处理；实际空间门槛根据基准部署测定，不能将约 20 节点直接换算成磁盘配置。正式发布前落实保留期限、空间告警、清理前引用核对和可恢复的清理步骤。

更新顺序建议先停止新提交、等待或核对进行中的操作、生成有效备份组，再升级单个 Manager 和对应 Agent。升级必须验证协议兼容；数据库迁移后不支持直接降级时，回退走隔离恢复，不直接换旧二进制并继续发任务。以上均为运行设计，M0／M1 尚需提供实际故障、备份和升级记录。
