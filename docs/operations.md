## 1. 部署责任和前提

使用方维护管理端及其数据、访问地址与传输信任，提供各 Agent 到管理端的可达路径，并维护节点上的 Docker／Compose 与访问权限。Manager 暂建议单实例；没有高可用或自动故障转移承诺。节点应用独立运行，管理端停止通常只影响管理能力，不能据此断言进行中的任务没有副作用。

| 区域 | 需确认的条件 | 当前状态 |
| --- | --- | --- |
| 管理端 | 安装产物、版本、访问端口、持久目录、运行用户、身份与密钥保护 | 已有[源码构建与首次运行步骤](manager-first-run.md)；指定Linux正式CLI／HTTP的init、serve、TLS登录、停机重开与锁释放已验证；完整安装交付仍待验收，第7节目录是部署示例 |
| 网络 | 浏览器到管理端、Agent主动到管理端、节点到所需镜像仓库 | 指定Linux正式TLS、Agent enroll及真实WebSocket空恢复已通过；浏览器流程、双节点及反向代理组合未验证 |
| 节点执行 | Agent服务、账本与工作区、Docker端点、CLI／Compose版本和路径关系 | [Agent接入](agent-first-run.md)和指定Linux正式接入子集已有证据；原生NC子集未调用产品Prepare／Observe或正向Apply，真实Docker精确接受表仍空 |
| 权限 | 首次管理账号、节点身份认领／撤销、最小操作授权 | 本机适用验证与指定Linux正式HTTP的6项授权、配置保存／幂等和unsupported 422零受理已通过；真实两节点权限与目标隔离仍待验证 |
| 备份 | 管理元数据、配置内容、保护材料、版本和恢复环境 | SQLite快照及两端只读检查器已有证据；[通用备份组](implementation/m1-backup-group.md)尚未接入service／CLI和真实领域，完整恢复未实现 |

Agent可能具备控制节点的高权限，应按可信运维协作范围部署，身份材料不混入普通分享配置。权限机制承接[现行HTTP规格](specifications/http-api.md)；密钥布局见第7节，备份以[现行v5规格](specifications/m1-backup-group.md)为准，第8节指向现行备份组及已迁出的旧方案，第9节区分重启行为与尚未实现的隔离恢复。交付前仍需实际演练。

## 2. 首个交付物必须具备的运行资料

安装资料需给出实际下载／镜像位置与版本、支持环境、完整配置参数、持久路径、初始化和启动步骤、健康检查、停止与卸载影响、首次接入和撤销。每条步骤在实际环境执行后，记录预期结果和失败处理；没有产物时不填占位命令冒充可运行教程。

节点接入流程为创建接入材料、安装配置 Agent、主动认证连接、核对身份和能力、只读发现资源，再开放获准操作。Agent 重装、身份丢失或轮换时先核对节点和旧任务，不自动按同名认领。解除管理先处理未决任务和会话并撤销身份，不删除应用资源。

当前源码构建、初始化、启动及接入步骤已分别放入[Manager首次运行](manager-first-run.md)和[Agent接入](agent-first-run.md)。指定Linux正式CLI／HTTP已验证登录／授权、Agent认领及空恢复、5文件2版本保存／幂等、unsupported拒绝且不生成operation、停机重开材料保留及0残留／锁释放，实际步骤见[IB记录](implementation/m1-instabox-debug.md)。本篇继续承接完整安装、浏览器部署、双节点隔离、备份恢复和维护的交付缺口；用户界面行为参考[功能设计](functional-design.md)与已实现模块记录，不能把设计能力清单或上述CLI子集当作完整产品流程已验收。

## 3. 日常观察与故障处理

维护者区分管理端可达、Agent 连接、Docker 访问、Compose 能力、采集新鲜度及未决操作。操作记录包括发起者、目标、输入版本、阶段、结果和时间，诊断访问受授权，日志保留与容量阈值待 O11。

| 现象 | 核对顺序 | 处理边界 |
| --- | --- | --- |
| 浏览器提交超时 | 用原提交标识查询是否受理，再查 operation_id | 不立即使用新标识再次部署 |
| 节点失联 | 查看最近连接／采集时间、网络与身份、Agent 服务及本地账本 | 不把历史空列表当无资源，不启动未授权新操作 |
| 操作长时间无结果 | 核对 Manager 阶段、Agent 账本、受监督进程和实际资源 | 未知先保留占用，不自动重跑或删除工作区 |
| 部署失败 | 固定版本、文件关系、环境、镜像、路径、外部依赖及 CLI 错误 | 不删除 build 配置来掩盖限制，也不自动触发构建 |
| Agent 重启后账本缺失 | 标记相关操作未知，核对真实资源和身份 | 不按“无账本”等同“从未执行” |
| 迁移验证失败 | 查两端活动状态、具体检查和业务确认 | 不自动删除来源、不盲目重启来源形成双活；按 O05 批准策略处理 |
| 清理失败 | 查本次清理对象与局部结果 | 保留迁移验证记录，不能从迁移开头重新执行 |

具体服务名、日志位置和诊断命令须与实际交付一致，首版安装验收时补入。当前表支持设计审阅，不证明所有情形已有自动恢复能力。

## 4. 管理数据备份与恢复

备份范围包括账号和授权、节点身份与撤销信息、配置原文和不可变版本、秘密保护所需材料、操作／迁移／验证及审计、软件与协议版本。M1 提案将配置正文密文和元数据存于同一数据库，由 SQLite 备份接口取得一致副本，再与全部所需密钥组成备份组。备份管理器不包含所有节点卷、绑定目录或外部数据库。

现行v5备份组的材料、清单和离线verify规则见[专门规格](specifications/m1-backup-group.md)，局部实现结果见[BG记录](implementation/m1-backup-group.md)。通用层的145条Windows矩阵与后续P2修复12条专项是分批证据，尚不证明正式两端备份工具已交付。

以下恢复步骤属于尚未实现的设计，不能用普通serve执行：先在隔离环境加载备份，核对内容和保护材料，再检查身份及协议兼容；恢复后的旧操作不自动重发。重新连接节点时，核对Agent账本和实际资源，再开放变更。旧备份可能遗漏最近的执行，不能用旧协调记录覆盖节点事实。

演练应实际恢复至少一个配置版本及其文件、用户权限和未终结操作，证明仍能正确拒绝越权与重复开始。保留备份生成环境、范围、恢复步骤、核对结果及局限；频率、保留、异地副本和恢复时间目标待 O11，不虚构已满足的 RPO／RTO。

## 5. 更新、停止与回退

首个发布前定义 Manager—Agent 兼容矩阵、schema 迁移、升级顺序、失败回退及不兼容时的行为。更新前核对运行中的变更、备份管理状态和保护材料；执行窗口与是否等待任务结束由实现给出明确步骤。

停止管理端不表示底层 Compose 已停止；停止 Agent 不保证已启动子进程和 Docker 资源自动回滚。发布版必须给出监督与退出行为并通过故障测试。回退旧管理端还需考虑数据库和协议是否可逆，不能仅恢复旧二进制就宣称回退成功。

## 7. M1 安装布局与首次运行提案

Manager已由同一服务提供Web静态产物与管理API，Agent为节点上的独立服务。首轮目标是Linux二进制、同机Docker端点及Compose；Linux软件回归已有指定组合证据，原生Docker及产品部署矩阵仍待验证，其他环境继续保留产品意向，只有对应组合通过后才能列入支持矩阵。以下绝对目录为部署布局示例，由实际配置决定；源码运行命令以[Manager](manager-first-run.md)／[Agent](agent-first-run.md)说明为准，不把本表当作已验证的自动安装过程。

| 位置 | 建议内容与权限 | 备份／清理责任 |
| --- | --- | --- |
| `/var/lib/docker-manager/manager.db` | Manager 管理数据库；服务私有目录 `0700`，数据库及 WAL 文件不对普通用户开放 | 用 SQLite 备份接口取副本；不能仅复制在线主文件 |
| `/etc/docker-manager/keys/` | KEK 与 HMAC 密钥环；目录 `0700`、文件 `0600`，服务账户可读 | 独立受控备份；仅有数据库无法恢复秘密 |
| `/var/lib/docker-manager-agent/agent.db` | 节点执行账本、ledger_id、结果及本地占用 | 保留持久卷／目录；丢失时隔离变更 |
| `/var/lib/docker-manager-agent/workspaces/` | 固定配置位于 `{stack_id}/{version_id}/package/`；staging 与包外运行材料按 operation_id 组织，运行 manifest／空 env 不进入包内 | 固定版本目录属于运行依赖；不能作为临时缓存随意清除 |
| `/etc/docker-manager-agent/identity.json` | node_id、候选／已认领随机凭据与 Manager 地址／信任配置，`0600` | 不复制给另一节点；丢失后重新认领，不按同名自动恢复 |
| `/etc/docker-manager-agent/keys/` | 独立 K_ledger 及本地敏感结果保护密钥，`0600` 文件 | 与账本匹配恢复；缺钥或错钥停止新操作 |

Manager 服务用户不需要 Docker 控制权限；Agent 仅使用明确配置的 Docker 端点，实际权限须满足 CLI。授予 Docker 控制能力即处于高权限信任范围，不能把普通节点权限界面解释为宿主机隔离。密钥挂载与数据库挂载分离，数据库位于本地可靠文件系统。

首次启动顺序为：生成 Manager 持久身份和密钥环 → 初始化数据库并核验 SQLite 版本／PRAGMA → 通过本机受限初始化流程建立首个管理员 → 开放受 TLS 保护的访问 → 创建限时认领材料 → Agent 先持久保存自身候选凭据再发起认领 → 核对节点身份、ledger_id、CLI 能力和只读观察 → 授予操作能力。初始化不设置通用默认密码，不在命令行参数或日志中打印长期秘密。

重启不得重复创建身份或替换缺失的密钥。已有数据库却缺钥、身份不符或 schema 过新时，服务进入明确失败／核对状态；新安装和恢复安装必须是不同入口。首次部署应能验证一个数据库副本确实可解密，再开放变更。

首轮运行配置字段在第 10 节明确；安装命令和服务文件须随首个产物验证，不能把目录及配置示例拼成未经执行的安装教程。

## 8. 数据库与密钥备份组

当前schema5／protocol1采用[完整备份组规格](specifications/m1-backup-group.md)的双根清单、固定两钥、材料锁及封闭副本Inspector；[实施记录](implementation/m1-backup-group.md)区分通用库完成与尚未接通的service／CLI／真实两端组合。这里不提供尚不存在的生产备份命令。

数据库、身份和全部所需钥必须匹配；Manager／Agent没有天然跨机一致时刻，管理备份不包含业务卷、绑定数据或外部数据库。隔离恢复／重加密／维护仍按[维护备份规格](specifications/m1-maintenance-backup.md)实施，当前尚未交付。

已被替代的五步算法及在线密钥环提案已迁入[历史归档](../archive/2026-11-14-documentation/superseded-design/backup-generation-proposal.md)，不再留作现行操作步骤。

## 9. 恢复与重启的具体边界

下表是行为边界：正常进程重启已有本机运行库及通道证据；“从旧备份恢复”、`recovery_mode`及显式解除隔离仍是待实现的恢复设计，不能视为现有CLI。现行普通serve不承担隔离恢复；规划中的schema6／protocol2也不是当前schema5／protocol1的能力。

| 场景 | 允许恢复的动作 | 重新开放变更前的条件 |
| --- | --- | --- |
| Manager 正常进程重启，数据库／密钥未回退 | 打开数据库，恢复占用；Agent 重连报告账本；先查询，不自动重放已授权许可 | 当前身份、会话与操作事实一致；未核清目标继续阻塞 |
| Manager 从旧备份恢复 | 在隔离环境检查 backup_id、版本、密钥及全部密文；启动 recovery_mode，禁止新受理和开始许可 | 撤销旧浏览器会话，核对备份后的账号／授权／节点撤销变化；按协议 scope=all 分页对照 Agent 全部账本（含终结已 ack 历史），处理本库缺失项后显式解除受影响目标隔离 |
| Agent 正常进程重启，账本／身份未回退 | 回报 ledger_id、未决操作、工作区和实际资源；不因 PID 消失判定未执行 | 与 Manager 核对许可及结果；疑似执行过的操作不重跑 |
| Agent 账本从旧备份恢复、缺失或损坏 | 停止新开始，保留现有材料与工作区；保持原node／ledger身份，作为恢复事件重新核对 | 核清未知任务及端点副作用；不能用新身份、空账本或删除占用绕过；实际隔离恢复工具仍待实现 |
| 密钥缺失、错配或密文认证失败 | 阻止读取敏感内容及新部署，报告 key_id／对象 ID 的受控错误 | 找回匹配备份并验证；生成新钥无法解密旧内容，禁止覆盖原材料 |
| 磁盘满或 fsync／事务提交失败 | 拒绝新受理和新开始；正在执行的任务尽力保留结果并报告记录失败 | 恢复存储可写后核对实际执行；不能为了续跑先清账本或操作记录 |

旧 Manager 备份可能恢复已经撤销的凭据。恢复设计要求先隔离入口、撤销旧会话及凭据、复核当前授权，再经真实Agent全量核对；当前普通serve尚不是隔离恢复入口。现行两端只有单KEK，密文AAD含key_id，不能只换钥或重置使用计数；计划保留HMAC／K_ledger，对完整副本用全新KEK逐记录重新加密。具体[维护／备份设计](specifications/m1-maintenance-backup.md)和MB记录尚未完成软件交付，不将设计中的恢复命令当作现有功能。

真正 unknown／interrupted 的维护边界详见[执行与恢复](specifications/execution-recovery.md#6-人工恢复的边界与维护要求)。当前规格允许保存证据并持续隔离，没有可直接解除该隔离的现成命令；重新认领、改 node_id 或清空账本均不能绕过旧占用。O12 的维护入口和端点终止屏障必须在可交付安装包前完成设计与实测。

## 10. M0／M1 运行配置工作定义

首轮采用 UTF-8 JSON 配置对象，未知键、重复键、错类型和相对文件路径使启动失败。下面是字段定义，不是已发布的配置文件或启动命令。缺省值只在键省略时使用，null 不代表缺省；秘密内容不直接写入配置，配置只引用私有文件。所有项在进程启动时读取，不支持运行时热更新。环境变量不覆盖这些项，避免服务环境改变实际执行配置。

| 程序／字段 | 类型、默认或必填 | 验证与生效责任 |
| --- | --- | --- |
| Manager `listen` | string，默认 `127.0.0.1:8443` | host:port，端口1—65535；需要远程访问时由部署者明确改监听地址 |
| Manager `external_origin` | 必填 string | 一个 HTTPS origin，含非默认端口，无路径/query/fragment；用于 Origin 精确比较，不根据任意 Forwarded 头推断 |
| Manager `tls_cert_file`／`tls_key_file` | 必填绝对文件路径 | 本期原型由 Manager 直接终结 TLS；证书、私钥和名称必须匹配；密钥缺失不自动生成替代 |
| Manager `database_file` | string，默认 `/var/lib/docker-manager/manager.db` | 本地可靠文件系统；打开已有库时必须匹配 manager_id、schema 及密钥 |
| Manager `keys_dir` | string，默认 `/etc/docker-manager/keys` | 私有密钥目录；权限和备份按第7—8节 |
| Manager `log_level` | `info|warn|error`，默认 info | 禁止凭日志级别开启配置／密码／原始执行输出打印 |
| Manager `web_dir` | 绝对目录，默认 `/usr/share/docker-manager/web` | 2026-11-12实施选择：Manager同源提供已构建的Web目录；与服务二进制一起交付，启动检查index.html。不从网络/CDN下载、不把未知API回退成HTML |
| Agent `manager_origin` | 必填 string | HTTPS origin；认领和轮换附加既定路径，WebSocket使用同一主机端口及 `/agent/v1/connect`，不接受任意重定向转发凭据 |
| Agent `ca_file` | 可省略绝对文件路径 | 省略使用系统 CA；提供则加入明确的附加信任，仍验证主机名；没有 insecure 开关 |
| Agent `state_dir` | string，默认 `/var/lib/docker-manager-agent` | 内含 agent.db、workspaces 和操作目录；单实例锁覆盖该目录 |
| Agent `identity_file`／`keys_dir` | string，默认 `/etc/docker-manager-agent/identity.json`／`/etc/docker-manager-agent/keys` | 现有身份和密钥不可因文件缺失而静默重新认领 |
| Agent `docker_cli` | 必填绝对文件路径 | 只调用经 M0 检查的可执行文件，不接受 Web 请求改变路径 |
| Agent `docker_socket` | string，默认 `unix:///var/run/docker.sock` | M1 仅同机 unix 端点；不接受 tcp、ssh 或由 Compose 改 context |
| Agent `execution_timeout_seconds` | integer，默认1800，范围1—86400 | 仅约束单次执行；到期进入 interrupted/deadline 和核对，不能直接认为失败且无副作用 |
| Agent `log_level` | `info|warn|error`，默认 info | 同样不能打印秘密和原始命令输出 |

启动读取的 Agent 端点和执行相关配置形成 ExecutionProfile。持久 docker_endpoint_id 标识一个实际端点绑定；socket或CLI/执行策略发生变化时停接任务并递增 policy_revision，所有旧 ready 失效。无法证明还是原实际端点时必须隔离并走重新核对，不能只复用相同 socket 字符串。存在未核清操作时不得用配置变更跳过旧端点的维护责任。

协议中的消息上限、许可10秒、探活15／45秒和输出1MiB属于 v1 固定工作参数，首轮不开放普通配置覆盖；M0 调整时同步 Schema、协议、HTTP和对应测试。执行取消的10秒宽限及服务停止应留出的持久化时间由服务集成验证；不能以 supervisor 强制杀进程替代结果核对。反向代理、热更新、远程 Docker 端点和多实例部署在对应能力实现前另行验证，本表不承诺这些组合已支持。

隔离恢复演练至少覆盖：一个含环境秘密的多文件版本、一个尚未开始的操作、一个已 START_COMMITTED 而 Manager 未收到结果的操作、一个备份后新建且已完成并 ack 的操作、一个备份后已撤权用户，以及旧 HMAC key_id 的幂等重试。通过判据是可读取正确原文、发现并保存缺失历史、拒绝越权和重复开始、保留未知占用；完成记录写实际输入与输出，不以“数据库能打开”代替恢复成功。

## 10. 运行观测与交付门槛

Manager 最少提供存储可读写状态、恢复模式、未决操作数量、Agent 最近连接和采集时间；Agent 最少提供账本可写、Docker 可达、Compose 可用和工作区容量状态。一般日志只包含 ID、阶段与错误码；命令输出可能包含秘密，以独立的 `operation.output.read` 能力控制并加密保存，输出截断要显示截断事实。

M1 暂不自动回收版本、幂等记录、执行账本和受用工作目录。应在新受理／新开始前检查可用空间与写入能力，容量不足时阻止产生更多变更并提示处理；实际空间门槛根据基准部署测定，不能将约 20 节点直接换算成磁盘配置。正式发布前落实保留期限、空间告警、清理前引用核对和可恢复的清理步骤。

更新顺序建议先停止新提交、等待或核对进行中的操作、生成有效备份组，再升级单个Manager和对应Agent。升级必须验证协议兼容；数据库迁移后不支持直接降级时，回退走隔离恢复，不直接换旧二进制并继续发任务。此更新流程仍属运行设计；已有本机故障、快照、只读检查与通用备份组证据不替代完整恢复、升级或真实环境验收，暂缺项继续由[首版记录](implementation/m1-first-version.md)维护。
