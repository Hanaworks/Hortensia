# Docker Manager 功能与交互设计

更新日期：2026-11-04。状态：设计草案，待审阅；M1 的交互与范围已有具体建议。本文供用户核对操作规则，承接[需求规格](requirements.md)，按 arc42 运行视图连接到[架构](architecture.md)和各模块；没有冻结页面布局。

## 1. 节点、资源和导航

提供多节点概况和单节点上下文，展示当前账号可见的节点、连接状态、最近采集时间及资源概况。节点内按 Stack、容器、镜像、网络和卷查阅；Stack 内可见 Compose service，不另建全局 Service 管理层。

修改入口同时展示节点、对象名称和操作影响；内部使用节点及资源标识，不依靠名称定位。切换节点可以保留筛选条件，但不能沿用旧目标提交。慢请求返回时，Web 依据请求中的节点与视图标识处理，详见 [Web 设计](components/web.md)。离线节点显示信息时附采集时间，不用空列表表示失联。

分组和标签采用 P05 提案：平面分组允许多重归属，标签为键值。新建、归类、删除分类都不改变运行资源或授权。列表、计数、检索结果先经过可见范围过滤。分组冲突命名、字符限制等随物理契约确定，不先设任意长度。

## 2. 账号、授权和敏感内容

管理器维护账号、禁用状态和按节点划分的操作许可。建议的逻辑权限如下；名称不是已定 API 字段或角色模板。

| 能力 | 允许的动作 | 需要另外取得的能力 |
| --- | --- | --- |
| 节点及资源查看 | 概况、列表、可公开的资源详情 | 配置正文、日志、控制台与凭据 |
| 配置读取／使用 | 查看或在获准流程中复用受管理配置 | 修改目标、部署、来源运行控制 |
| 配置维护 | 新建和修改目标配置 | 实际部署或删除运行资源 |
| 部署与运行控制 | 部署、更新、启动停止、重启 | 资源删除、持久数据删除 |
| 日志／统计／控制台 | 具体获准的诊断能力 | 三者分别检查，控制台不是普通日志读取 |
| 资源删除／数据删除 | 删除明确对象或持久数据 | 二者分别检查，迁移成功不授予权限 |
| 管理设置 | 账号授权、节点接入或分类维护 | 按管理任务拆分，避免普通归类影响授权 |

M1 提案要求部署者具备配置读取权限，配置原文可能包含秘密；首期不提供“可部署但不能读取”的秘密代理能力。实际权限名和组合见[接口规格](api-design.md)，未来如分离读取与使用，需要另行审阅泄漏和代理边界。

请求提交、开始许可和后续敏感阶段均复核授权；尚未得到许可的任务遇撤权应被阻止。若开始许可已经提交，Agent 可能在有效窗口内开始，撤权不能倒转这次授权；系统请求取消并报告实际结果。已开始的底层变更不会因撤权自动回滚，后续需新许可的阶段停止，并记录需要核对的资源。流会话撤权后关闭，不能只隐藏按钮。具体顺序见[Manager](components/manager.md)和[接口规格](api-design.md)，仍需故障验证。

## 3. 节点接入和解除管理

1. 获准人员创建待接入节点，获取受控接入材料。
2. 节点安装 Agent，配置管理端地址和信任材料，主动发起连接。
3. Manager 核对接入身份，绑定唯一节点身份；Agent 报告自身能力和 Docker 端点信息。
4. 接入成功后，先发现现有资源，不自动接管 Compose 或修改容器。

注册材料的一次性使用、响应丢失恢复与重装换身份建议见[接口规格](api-design.md)，O03 继续跟踪验证。节点会话可达、Docker 访问可用、Compose 可用、快照新鲜度分别展示，不压成单一绿色状态。解除管理撤销接入身份和会话并处理未结束操作；节点应用继续存在。未知操作先核对，不能以删除节点记录掩盖未决执行。

## 4. Stack 编辑、文件和保存

编辑对象包含文件集合、有序 Compose 主文件列表、环境输入、项目参数及附属运行配置。保留原文和文件关系；环境变量插值与容器内环境不是同一用途，界面应说明。附属文件与原生 include／extends 引用只在已验证支持的组合内开放，不因支持多文件就声称任意引用可携带。

配置包中的相对路径在受管理工作区内解析；绝对绑定目录、外部卷、外部网络及仓库访问是节点依赖。跨节点时列出需携带的受管理文件和需目标预先准备的依赖，不猜测实际存在。路径越出受管理包时，不自动读取或拷贝宿主机文件；提示用户将所需文件纳入包，或按已验证的外部依赖方式处理。

保存采用基于版本的条件提交：用户打开版本 v，保存时附 v；若已经变为 v+1，返回冲突并保留本地内容供对比，不能静默覆盖。成功保存产生新版本。草稿、已保存版本和最近部署版本分别展示；提交部署时锁定版本，后续保存不改变已提交操作的输入。

校验分两层：编辑时的语法诊断是帮助；目标 Agent 在明确目录、环境及 Compose 版本下的原生校验才用于部署准备。配置可保存但不能部署时，说明限制，不能通过保存状态暗示目标条件成立。

## 5. 部署、生命周期和已有资源

部署前核对目标、配置版本、项目名称、文件顺序、环境、路径、镜像和外部依赖。明确阻断不支持的构建流程。提交后返回操作标识；用户可关闭页面，再通过操作记录核对。详情分别显示命令结果、资源观察、部署版本和需要用户判断的健康信息。

启动、停止、更新及移除沿相同对象、授权和操作机制执行。移除确认分别列出管理配置、容器／网络等运行资源、卷及持久数据；默认不把数据删除混入普通移除。外部资源不因为项目同名就纳入删除集合，执行前核对对象实际归属。

独立容器支持基础管理及诊断；Stack 容器标明关联，提示资源直接修改可能与已保存 Compose 不同。镜像、网络和卷操作返回目标和明确结果，清理采用可检查的范围。仓库凭据可被授权用于拉取，但不会自动作为 Copy 内容泄露。

已有资源首先只读发现。能看到 Compose labels 不代表拥有完整原始文件；无法还原环境文件、附属文件或参数时，说明缺口，允许用户补齐并比对。接管的覆盖行为属于 O10；未定前不自动写入或重部署已有项目。

## 6. Copy 和 Apply

Copy 输入为来源的已保存版本、目标节点、目标名称及明确修改。核对来源读取和目标配置维护权限，预览受管理文件、外部依赖及敏感内容处理。目标同名则要求改名或进入显式替换流程，初期不静默覆盖。

Copy 完成仅创建目标独立配置。来源不变；目标端口、绑定路径或外部数据库没有因此自动满足或隔离。来源离线但 Manager 已有完整配置时可继续复制。相同提交标识重试返回同一结果，改变输入须用新标识。

Apply 是独立部署请求，需要目标部署权限和目标 Agent 可用。Copy 后可显式继续 Apply，界面保留两个结果；部署失败时，目标配置仍可修改重试，不改变来源。Apply 可以使用现有目标配置，不要求总是先 Copy。

## 7. Node Cross 迁移

### 7.1 阶段、证据和未决边界

| 阶段 | 用户与系统的工作 | 推进条件与异常去向 |
| --- | --- | --- |
| 准备 | 选择来源、目标、配置版本和迁移范围，核对权限、冲突、路径、镜像及数据依赖 | 缺依赖或来源状态未知时停在准备，不改节点归属冒充迁移 |
| 数据准备 | 按当前允许方式由用户准备目标数据，并记录声明及可检查项 | 声明不是完整性证明；自动搬运按 R15 暂缓 |
| 切换执行 | 依经批准的策略安排来源退出、目标接替和流量／写入关系 | 具体顺序与中断预算待 O05；没有策略不得执行真实迁移 |
| 验证 | 检查目标配置和资源、运行状态、数据依赖、来源切换及必要业务确认 | 失败、缺证据或失联时不得进入来源删除 |
| 完成与来源选择 | 验证通过后迁移可完成；用户选择保留来源或另行清理 | 保留材料不重新激活来源；清理需要重新授权与确认范围 |
| 来源清理 | 删除明确选定的来源配置、资源或数据 | 清理失败单独记录，不重做迁移；对象改变后必须重新核对 |

本轮没有默认选择停机迁移、双端并行或自动回退。用户当前已允许手动准备数据，但尚未允许任意停机，也未确认应用能够双写。O05 必须先给切换状态和失败矩阵，再进入迁移编码；其他流程可以独立推进。

### 7.2 验证和来源清理

验证记录关联本次迁移、来源与目标、实际配置版本、检查项目、观察时刻、证据与确认人员。容器运行不能替代业务确认。无法自动观察的内容明示人工核对，不生成“全部健康”的推断。

验证后的任一相关变更，例如目标重新部署、来源重新启动或删除范围改变，都会使来源清理前提需要重新核对。清理按实际对象标识和归属执行，不按历史名称误删新部署。用户选择删除时展示范围和数据后果；只有当次检查有效且权限充分时才开始。来源数据的安全处理须等 O05／O06 对应范围明确。

### 7.3 失败和回退

准备失败通常没有运行资源副作用；执行后失败必须展示已发生步骤和两端状态。若无法证明目标已停止，不能盲目重启来源形成双活；若无法证明来源已退出，不能把目标部署标为迁移完成。具体人工恢复动作也要依切换策略，不把“回退”当作无条件按钮。

## 8. docker run 转 Compose

P06 提案先支持单条 `docker run` 或 `docker container run` 的 POSIX 风格命令文本，包括引号和反斜杠续行；拒绝脚本控制结构、管道、多命令连接和重定向。变量或命令替换不执行：需要变量的值时给出诊断，不能读取运行环境猜测。仅作文字值的 shell 元字符也须通过明确引用规则处理。

| 输入类别 | 映射建议 | 必须显示的差异或依赖 |
| --- | --- | --- |
| IMAGE、镜像后的参数 | image；后续参数以列表形式映射 command | 引号分词后仍需保留参数边界；不能重造 shell 字符串 |
| --name | container_name | 不自动承诺跨节点唯一；生成 service 键采用可编辑名称 |
| -p／--publish | ports | 保留地址、端口和协议信息，不补造额外暴露 |
| -e／--env、--env-file | environment、env_file | 无值的环境项需要人工补齐；文件内容未被导入 |
| -v／--volume、--mount | volumes 的已支持挂载类型 | 区分绑定路径与命名卷；外部命名卷应保留真实名称和既有资源意图，不能默认为项目新卷 |
| --network、--network-alias | network_mode 或 networks 的已支持组合 | host／none 与自定义网络分别验证；自定义网络提示 external 依赖，未知组合报不支持 |
| --restart、--user、--workdir | restart、user、working_dir | 逐项保持值；特殊平台项不强行映射 |
| --entrypoint | entrypoint | Compose 可能影响镜像默认 CMD；没有显式启动参数时需诊断并要求用户核对，不宣称等价 |
| -d、--rm、-it 等运行方式 | 显示差异，按支持清单处理 | Compose 生命周期与单次 run 不同；不能因生成 YAML 就忽略行为差异 |
| 未识别参数 | 结构化未转换项 | 不静默丢弃，也不把它拼到应用 command |

例如 `docker run --name web -p 8080:80 nginx:stable` 可生成可编辑的 service、image、container_name 和 ports。示例不证明 stable 标签将来内容固定，也不表示已部署。用户必须审阅后显式选择保存或 Apply。

实现前建立逐参数支持清单与反例，依据 [run 参数](https://docs.docker.com/reference/cli/docker/container/run/)及 [Compose service](https://docs.docker.com/reference/compose-file/services/)做原生对照；复杂挂载、entrypoint 和网络不在未验证时标为无损支持。

## 9. 状态、恢复和可达性反馈

界面分别呈现连接可达性、资源观察时间、配置保存版本、部署操作和迁移阶段。请求超时只表示浏览器未取得响应，使用提交标识查询是否已受理；不立即再发一个新操作。任务状态统一见[数据设计](data-design.md)，模块处理见[Manager](components/manager.md)和[Web](components/web.md)。

日志、统计、控制台是独立授权的流会话。切换对象或撤权关闭对应会话，重连按新上下文建立，不把旧容器输出挂到新页面。管理数据备份与恢复见[运行准备](operations.md)。

## 10. 审阅范围

本文完整表达了当前可起草的主要操作流程；权限组合、分类方案、条件保存和转换语法属于提案。迁移切换／回退与存储策略未定，尚不能据本文实现完整迁移。验收场景见[测试计划](test-plan.md)。组织依据持续为 [arc42 运行视图](https://docs.arc42.org/section-6/)及上游 req42 需求，具体技术参考记录于[文档规划](documentation-plan.md)。

M1 建议先完成登录、节点接入、文件编辑、版本保存、Apply 与操作核对。具体页面和保存冲突／超时／撤权后的行为见 [Web 第 8 节](components/web.md#8-m1-路由组件与状态转换)，配置与运行环境限制见 [Agent 第 9 节](components/agent.md#9-m1-执行方案)，增量边界见[实施计划](development-plan.md#4-m1-工程落实与任务依赖)。本篇中的迁移、Copy、转换与全部资源操作属于产品整体目标，不因在同一篇出现就全部进入 M1。
