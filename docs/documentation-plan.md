## 2. 统一组织与主要维护位置

req42 组织目标、干系人、范围、功能、支持模型、质量、约束、术语及路线与风险；arc42 组织上下文、策略、构件、运行、部署、共同概念、决策及质量风险。模块、接口、数据、实施、测试和运行资料继续承接这两个骨架，独立文件不改变归属。

需求和术语主要维护于 requirements；用户操作主要维护于 functional-design；整体结构及共同机制主要维护于 architecture；模块内部协作维护于所属 components 文档；实体维护于 data-design；跨边界操作维护于 api-design；决定和待定事项维护于 decisions。正文保留理解当前任务所需的摘要，通过链接承接精确定义。

设计正文均为本轮可审阅方案，不等于用户已确认的产品决定。文中的具体设计规则具有草案内的约束作用，用户审阅后可以调整。没有代码和运行证据时，不把设计写成当前实现。

## 3. 文档安排与内容深度

以下安排是本轮正文的写作依据。每篇开头说明读者任务和状态；独立文件以阅读用途拆分，不按模板建立空目录。

### 3.1 项目入口 README.md

面向首次接触项目的人。依次说明用途和参照、核心能力与边界、当前可用状态、逻辑组成和技术选择状态、如何开始阅读及参与、运行资料和历史入口。承接 req42 的目标、范围和资产，以及 arc42 的组成与部署摘要。入口需让读者理解项目，不能只剩文件清单。

### 3.2 需求规格 requirements.md

面向用户和设计者，承接 req42。依次说明实际问题和成功目标、使用者与环境、术语与管理模型、功能范围及 R01—R17、代表性场景、Q01—Q11 质量场景、范围外与待决问题。逐项保留原材料中的条件和例外，尤其是约 20 节点并非硬上限、Unix-like 并非平台认证、迁移不等于复制、自动存储搬运暂缓。直接确认与行为细化稿分开说明，并给出原话索引。

### 3.3 功能与交互设计 functional-design.md

面向审阅操作行为的人，承接上述需求和 arc42 运行视图。依次展开节点与资源导航、账号和权限、文件编辑及保存部署关系、部署与资源操作、Copy／Apply、迁移阶段及验证和来源清理、命令转换、错误与并发反馈。不冻结页面数量、视觉和控件位置。每个重要流程说明前提、操作、结果和异常去向；迁移未决策略保留实际阻塞条件。

### 3.4 架构设计 architecture.md

面向技术审阅和实现者，按 arc42 十二部分的职责展开：目标、约束、上下文、策略、构件、运行、部署、共同概念、决策、质量、风险和术语。解释 Web、Manager、Agent 与 Docker／Compose 的关系及选择原因；给出从整体进入模块的入口。技术候选给出取舍，避免写成已选择的运行组合。启动、失联和恢复与正常部署同样有承接。

### 3.5 Manager 模块设计 components/manager.md

继续展开 arc42 构件和运行视图，承接 R01—R07、R11—R17。说明身份授权、节点会话、配置、操作协调、迁移协调、转换与记录之间的调用和数据责任。深入操作接收、授权开始、Agent 去重、结果确认和恢复的交接，明确持久化边界、锁和撤权。提供与 Agent／Web 的接口通过 api-design 衔接，不另造协议。

### 3.6 Agent 模块设计 components/agent.md

继续展开 arc42 构件、运行及部署视图，承接节点接入、Compose、资源操作和恢复要求。说明连接身份、工作区、执行账本、资源适配器、进程与流会话的内部协作；深入工作区路径、Docker 端点关联、开始前记录、去重和重启恢复。区分执行目录中的配置与应用绑定目录，说明不自动构建的执行约束。平台、进程托管和协议参数待技术验证。

### 3.7 Web 模块与交互状态设计 components/web.md

继续展开 arc42 构件和运行视图，承接节点上下文、多人编辑、操作反馈和权限要求。说明导航、查询缓存、编辑器、提交与任务订阅、诊断会话、转换器的责任和依赖。深入切换节点后的旧响应、草稿与保存版本、提交超时和重连、权限变化的处理。界面实现和组件库仍可后续决定。

### 3.8 数据设计 data-design.md

承接 arc42 共同概念及模块数据责任，面向实体与存储实现者。说明管理对象及关系、管理数据与节点事实的边界、配置版本和部署输入、任务及迁移记录、敏感信息、并发一致性及备份。列出逻辑字段与不变量，不虚构已经存在的表、迁移文件、保留周期或加密实现。

### 3.9 接口规格 api-design.md

承接 arc42 构件接口、运行交互和共同概念，面向前后端和 Agent 接入者。先列边界、调用者和授权，再给共同上下文、主要操作的输入／前提／状态变化／结果／失败，最后说明消息恢复、流和物理契约缺口。保存、Copy、Apply、迁移验证及来源删除保持独立语义。逻辑操作名不冒充已定 URL 或消息格式。

### 3.10 测试计划 test-plan.md

承接 req42 的需求和成功标准，以及 arc42 的运行、质量和风险。面向测试执行者：说明覆盖分层、环境、用例及断言、故障注入、原生对照、权限组合、约 20 节点负载、迁移范围和结果记录。覆盖每个 R 和 Q，并明确尚无应用测试结果。当前文档的检查记录与软件测试分开。

### 3.11 开发实施计划 development-plan.md

承接 req42 的范围、路线和风险，以及 arc42 的模块、决策和质量。面向安排实现的人：说明已有资产、开工所需决定、增量顺序、跨模块接入、各阶段交付和测试断言。详细展开首个完整流程的任务依赖；后续迁移实现受策略确认约束。不给没有依据的日期、人力和工作量比例。

### 3.12 部署与运行准备 operations.md

承接 arc42 部署、运行和共同概念。面向部署和维护者：说明网络和权限前提、安装交付必须提供的内容、接入与撤销、状态核对、备份恢复、升级兼容、故障处理。当前给出可审阅的运行责任和验收办法；无镜像、安装命令或版本组合时，不编写伪安装教程。可执行手册在首个交付物出现后于此补齐，再按篇幅拆分。

### 3.13 决策与待办 decisions.md

承接 req42 风险／假设和 arc42 决策／风险。面向审阅和接手者：集中维护已确认决定、具有理由和代价的技术提案、未决问题、影响和解决时点；附原话索引，确保较新的决定可追溯。产品和技术决定分开，不用文件已写出代替批准。

## 5. 编写顺序和方案复核

1. 核对历史用户回复，建立需求、术语与有效决定，再写功能流程。
2. 形成整体架构，复核是否需要局部展开。本轮明确任务恢复、配置执行和前端异步状态复杂，新增 Manager、Agent、Web 三篇，避免只完成整体职责表。
3. 模块与数据、接口迭代对齐，检查保存版本、操作标识、迁移验证证据和授权的共同含义；出现新共同概念时回填架构。
4. 编写测试、实施和运行承接，核对每项工作是否有设计入口及可观察结果。
5. 返回原始用户回复审查需求，再反查正文与指南：是否还有本阶段必须回答但提纲漏列的问题；同步方案、正文、导航和缺口。

独立章节可以交错编写；当前没有工程实现，不安排编译、构建或部署。需要技术验证的地方明确留给实施阶段，而不是把设计假设写为验证结果。
