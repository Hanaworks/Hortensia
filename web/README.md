# Web 开发与交接

本目录实现M1浏览器客户端，所有运行数据经同源`/api/v1`读取或提交；没有运行时模拟API。范围、状态及维护规则见[Web规格](../docs/specifications/m1-web.md)与[W01—W10验收](../docs/implementation/m1-web.md)。首位管理员在Manager主机初始化，浏览器没有独立初始化入口。

## 构建与验证

已验证Windows／Node 24.15.0／npm 11.12.1。在本目录运行：

```powershell
npm ci
npm test
npm run build
```

`build`先执行Vue／TypeScript检查，再输出`dist/index.html`与带内容hash的本地`dist/assets`。部署时由正式Manager在同一HTTPS origin提供此目录，并处理`/api/v1`；产物没有CDN依赖，也不保存Agent凭据。后端静态服务的具体启动参数由实际Manager运行文档承接，不能只开`vite`就声称完成登录联调。`npm run dev`仅用于本机页面开发；未经正式服务同源接入时接口失败是预期现象。

## 使用顺序

1. 登录。管理员可进入“账号与节点管理”登记节点、签发一次性令牌，在节点上通过Agent完成认领；明确给账号授予该节点所需动作。管理员身份本身不允许部署。
2. 选择节点，新建Stack，编辑包内文件；在文件顺序区填写Compose覆盖文件和插值环境文件顺序、显式插值变量及profiles。保存配置；保存不会执行Compose。
3. 在部署区核对已保存版本、目标节点和项目，明确提交部署。结果区分别查看命令、资源观察、健康及释放状态；待释放和需核对不意味着可以再次部署。
4. 请求响应丢失时使用“核对原提交”。同页还保留原始请求时才能原key重试；刷新后正文已丢失，只保留非秘密提交身份。无回执不证明未执行。操作历史可重新读取已受理操作；输出需要独立权限。

草稿、插值值、密码、token及输出仅在内存；刷新／离开丢弃未保存草稿，权限失效主动清理。sessionStorage仅保留本用户待核对提交的key和目标ID。记录存在时阻止同节点冲突变更，防止新key覆盖未知提交。退出删除这些恢复记录；因此未决操作应先核对或通过操作历史重新查阅。

## 维护入口

`api.ts`负责Cookie／CSRF、超时和HTTP错误；`config.ts`负责UTF-8／Base64及包结构；`submissions.ts`只持久非秘密身份；`model.ts`协调上下文代次、冻结提交、冲突和查询。Vue组件负责文本表单／结果呈现，不能绕过模型重新生成未知请求。测试的fetch替身只在`tests`中，验证延迟和失败边界，不构成正式后台的权限、TLS、Compose及耐久证明。
